01. 무엇을 만들고 있는가?

사진 편집 앱에서 얼굴 주변에 사각형을 그려 본 적이 있나요? 공장 사진에서도 같은 방법으로 “이 부품만 살펴보자”라고 표시할 수 있습니다. 그 표시 영역을 ROI(Region of Interest, 관심 영역)라고 합니다. 이 프로그램에서는 큰 사진을 열고 ROI를 옮기거나 크기를 바꿉니다. 잘못 옮겼다면 Undo로 되돌립니다. 먼저 “사각형 하나를 오른쪽으로 옮긴다”는 장면만 머릿속에 두세요. 뒤의 클래스 이름은 그 일을 나누어 맡은 담당자입니다.

04. 원본 픽셀과 화면 좌표는 다르다

휴대전화에서 지도를 확대해도 학교의 실제 주소는 바뀌지 않습니다. 사진도 같습니다. 원본에서 (100, 80)에 있는 부품은 화면을 확대해도 원본 좌표가 (100, 80)입니다. 달라지는 것은 화면에서 보이는 위치와 크기입니다. 그래서 ROI의 위치는 원본 픽셀(px)로 저장하고, 그릴 때만 화면 좌표(DIP)로 바꿉니다. DIP는 WPF가 화면 배치를 계산할 때 쓰는 길이 단위입니다. 원본 픽셀과 모니터의 실제 픽셀, DIP를 같은 것으로 생각하지 마세요.

화면 위치 = 원본 위치 × Scale + Offset
원본 위치 = (화면 위치 − Offset) ÷ Scale

숫자를 하나씩 넣어 봅시다. Scale은 원본 1픽셀을 화면에서 얼마나 크게 그릴지 정하는 배율입니다. Scale이 0.5이면 원본 가로 100픽셀을 먼저 50 DIP로 줄입니다. Offset은 화면 전체를 밀어 놓은 거리입니다. 가로 이동 20 DIP를 더하면 70 DIP가 됩니다. 세로도 80픽셀을 40 DIP로 줄이고 30 DIP를 더하므로 70 DIP입니다. 거꾸로 원본을 찾을 때는 먼저 이동값을 빼고, 0.5로 나눕니다. 그러면 원래의 (100, 80)으로 돌아옵니다.

여기까지는 WPF의 화면 단위입니다. DPI 배율이 1.5이면 70 DIP를 모니터의 105픽셀에 표시합니다. 이 마지막 변환은 호스트가 맡습니다. 첫 읽기에서는 “원본 위치 → 확대/축소 → 화면 이동” 순서를 설명할 수 있으면 됩니다.

public readonly record struct ViewportTransform(double Scale, PointD Offset)
{
    public static ViewportTransform Identity => new(1, new(0, 0));

    public PointD ImageToScreen(PointD point) => (point * Scale) + Offset;

    public PointD ScreenToImage(PointD point) => (point - Offset) / Scale;

    public ViewportTransform Pan(PointD delta) => this with { Offset = Offset + delta };

    public ViewportTransform ZoomAt(PointD anchor, double factor)
    {
        if (!double.IsFinite(factor) || factor <= 0)
        {
            throw new ArgumentOutOfRangeException(nameof(factor));
        }

        var scale = Math.Clamp(Scale * factor, 0.00001, 128);
        // anchor 아래의 원본 좌표가 확대 후에도 같은 화면 위치에 오도록 Offset을 역산한다.
        return new(scale, anchor - (ScreenToImage(anchor) * scale));
    }

    public static ViewportTransform Fit(double imageWidth, double imageHeight, double viewWidth, double viewHeight)
    {
        if (imageWidth <= 0 || imageHeight <= 0 || viewWidth <= 0 || viewHeight <= 0)
        {
            return Identity;
        }

        // 두 축 모두 들어가는 배율에 여백을 두고, 남은 공간의 절반만큼 이동해 중앙에 둔다.
        var scale = Math.Min(viewWidth / imageWidth, viewHeight / imageHeight) * 0.92;
        return new(scale, new(
            (viewWidth - (imageWidth * scale)) / 2,
            (viewHeight - (imageHeight * scale)) / 2));
    }
}

왜 화면에서 1칸 이동시키는 대신 원본 1px를 움직일까?

검사 영역의 좌표를 일정하게 바꾸기 위해서입니다. Scale=0.25에서 원본 1px 이동은 화면 0.25 DIP로 보입니다. 화면 1 DIP를 무조건 더하면 원본에서는 4px 이동해 확대율마다 결과가 달라집니다.

05. ROI 이동과 Undo가 한 팀인 이유

internal sealed class MoveGesture(InteractionController controller, PointD dragStartScreen) : EditGesture(controller)
{
    private (PointD Translation, bool AllowSlide)? _lastRequest;

    protected override string Name => "ROI 이동";

    public override void Move(PointD screen, InputModifiers modifiers)
    {
        var translationInImage = (screen - dragStartScreen) / InitialViewport.Scale;
        if ((screen - dragStartScreen).Length < MinimumDragDistanceDip)
        {
            translationInImage = new();
        }

        if (modifiers.HasFlag(InputModifiers.Shift))
        {
            translationInImage = Math.Abs(translationInImage.X) > Math.Abs(translationInImage.Y) ? new(translationInImage.X, 0) : new(0, translationInImage.Y);
        }

        var request = (Translation: translationInImage, AllowSlide: !modifiers.HasFlag(InputModifiers.Shift));
        if (_lastRequest == request)
        {
            // 같은 위치의 Mouse Up은 벽 접촉 계산을 반복하지 않고 표시한 결과를 그대로 확정한다.
            return;
        }
        Controller.PreviewTranslation(request.Translation, request.AllowSlide);
        _lastRequest = request;

읽기 쉬운 리팩토링의 기준

“코드를 짧게 만든다”보다 “지금 어떤 단계인지 보인다”가 먼저입니다. 메서드를 나눌 때 반환값·소유권·실행 순서를 명시하고, 포인터·풀링·비동기 완료 같은 성능 조건은 설명을 붙여 보존합니다. 기존 ImageCoordinator.LoadAndCommitAsync, TilePlanner.Visible, EditorSession.Commit처럼 하나의 규칙을 맡은 메서드를 출발점으로 읽으세요.

이번 교육서 작성에서는 제품 C#의 연산·버퍼·렌더 루프를 변경하지 않았습니다. 이미 나뉜 단계와 실제 연속 발췌를 연결해 읽기 부담을 줄였습니다. 이 선택은 “성능을 측정해 더 빨라졌다”는 주장이 아니라 제품 실행 경로에 변경을 넣지 않았다는 뜻입니다.

쉽게 보이는 변경숨은 비용 또는 오류먼저 확인할 것
프레임마다 모든 ROI를 ToArray큰 배열·GC·UI 정지가시 영역, 기존 캐시와 버전 사용
반복 격자를 일반 ROI 목록으로 변환셀 수만큼 시간·메모리 증가압축 범위와 개별 override 유지
GPU 전송 버퍼를 바로 Dispose아직 GPU가 읽는 중일 수 있음슬롯 완료와 Retire 계약
모든 작업에 Task.Run 추가문서 소유 스레드 위반, 순서 경합작업 경계·취소·새 문서 여부 확인
잠금 때 렌더러도 정지검사 영상 갱신까지 중단입력 허용과 프레임 게시 분리
빠른 후보만 남겨 검사 시간 단축누락률·위치/각도 결과 변화같은 입력·점수·후보·전수 결과 기준

실제 성능 변경이 필요하면 같은 Release 빌드와 동일 입력에서 워밍업 후 여러 번 측정하고, 처리시간 중앙값/p95·할당량·픽셀 또는 결과를 함께 비교합니다. 캡처 시간, 명령 처리시간, GPU 시간, 모니터 표시 시간은 서로 다른 수치입니다. 60FPS의 프레임 간격은 약 16.67ms이지만 일부 구간만 그보다 짧다고 전체 60FPS를 증명할 수 없습니다.

12. 직접 실행하고, 설명해 보기

아래 명령은 저장소 루트의 PowerShell에서 실행합니다. Windows x64, 저장소가 요구하는 .NET SDK와 native 의존성이 필요합니다. 첫 실행의 restore에는 네트워크가 필요할 수 있습니다. HTML을 읽는 데에는 .NET·서버·인터넷이 필요하지 않습니다.

dotnet run --project samples/VisionCanvas.Sample -c Release
dotnet test tests/VisionCanvas.Tests -c Release

실제 HWND/GPU 테스트는 Windows 데스크톱 세션과 해당 장치가 필요합니다. 저장소 테스트 중 대형 파일/성능 시험은 선택 실행 조건이 있으므로 백엔드 검증 기록과 샘플 README에서 실행 범위를 확인하세요.

실습 A · 호출 경로 찾기

ROI 하나를 그리고 오른쪽 방향키를 누릅니다. 키 처리, TranslateSelection, VM의 Scene 생성, 렌더러 제출에 중단점을 둡니다. UI와 렌더 스레드가 같은지 확인하고 입력에서 화면까지 경로를 종이에 적으세요.

풀이와 통과 조건

원본 X가 1px 증가하고 선택 ID가 유지되며 Undo 한 번으로 되돌아오면 편집 경로가 맞습니다. Shift라면 10px이며 이미지/부모 벽에서는 허용 이동량으로 제한됩니다. 렌더 스레드에서 EditorSession을 직접 바꾸는 코드가 없어야 합니다.

실습 B · 두 종류의 선택 분리

편집 선택은 A로 둔 채 위치 보기 목록에서 B를 고릅니다. B가 보이는지, A의 선택 ID와 Undo/Redo가 유지되는지 확인합니다. B를 이동한 후 다시 ROI 맞춤을 눌러 현재 경계를 사용하는지도 확인합니다.

풀이와 통과 조건

목록의 Target과 EditorSession의 Selection은 다른 상태입니다. FocusRoi는 ID로 현재 기하를 다시 찾고 Viewport만 바꿉니다. 같은 ROI를 다시 보는 버튼은 캐시된 옛 경계를 그대로 쓰면 안 됩니다.

실습 C · 잠금 중 영상 갱신

제공된 Navigation 관련 테스트를 찾아 잠금 전후 입력과 두 8K 프레임 검증을 읽습니다. 잠금 전에 시작한 preview가 취소되는 경우와 잠금 해제 후 이동이 다시 가능한 경우도 찾으세요. HTML의 새 영상 버튼은 실제 GPU 시험을 대신하지 않습니다.

풀이와 통과 조건

키·포인터·휠과 외부 편집 UI는 차단되고, 원래 문서와 Undo는 보존되며, 프레임은 새 값으로 바뀌어야 합니다. 로딩 중 NavigationOnly와 완전 잠금의 Esc 동작을 혼동하지 않습니다.

실습 D · 실패 원인을 분류하기

ROI는 움직였는데 그림이 그대로인 상황을 상상하세요. 문서, Scene, renderer, Present 가운데 어디의 정보를 먼저 확인할지 정합니다. 타일 파일이 늦게 도착한 경우와 GPU 오류가 난 경우를 각각 설명하세요.

풀이와 통과 조건

먼저 문서 좌표가 바뀌었는지, 다음 Scene이 게시됐는지 확인합니다. 장면이 맞으면 generation·타일 준비/업로드·그리기·표시 경로를 좁혀 갑니다. GPU를 바꾸거나 대기 코드를 제거하기 전에 처음 어긋나는 지점을 재현해야 합니다.

검증 기록을 읽는 방법

공통 입력 검증에는 실제 8K 잠금 중 프레임 교체와 관련 회귀 시험의 범위가 기록되어 있습니다. DX12 검증의 PASS/FAIL/NOT_RUN, 실행 조건과 제외 항목을 함께 읽습니다. HTML 실험 성공, 한 장의 화면 캡처, 합성 정답 일치는 각각 다른 증거입니다. 지속 60FPS·장시간 메모리·실제 카메라 수집·현장 전수 정확도는 이 교육서가 새로 보장하지 않습니다.
