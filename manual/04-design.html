04. 책임을 나누는 설계

SOLID와 GRASP를 실제 파일에 연결하기

왜 프로젝트를 여러 개로 나눌까

어떤 코드를 바꿀 때 함께 고쳐야 하는 부분이 많으면 실수를 찾기 어렵습니다. 좌표 수식은 파일 디코더와 무관하고, PNG 읽기는 ROI Undo와 무관합니다. 그래서 서로 다른 이유로 바뀌는 코드를 다른 책임에 둡니다. 클래스 수를 늘리는 것이 목적은 아닙니다.

프로젝트대답하는 질문알면 안 되는 것
VisionGeometry이 점은 도형 안인가? 어떻게 회전하나?WPF, DX12, 검사 판정
VisionImaging.Abstractions영상 크기·형식·타일·프레임의 계약은?NetVips 실제 디코더
VisionCanvas.Core문서·선택·계층·입력·이력을 어떻게 바꾸나?GPU 핸들, OpenCV Mat
VisionCanvas입력을 전달하고 화면에 무엇을 어떻게 그리나?검사 알고리즘, 제품 합불 기준
VisionImaging파일의 원본 픽셀을 어떻게 읽나?Canvas의 선택·이력

TeachingToolWpf어떤 서비스와 화면을 연결하고 어떻게 판정하나?다른 프로젝트가 앱을 역참조하면 안 됨

이 표는 책임 지도입니다. 실제 참조 목록은 각 .csproj가 기준입니다. 선택형 CUDA는 VisionCompute.ILGPU, 필터 UI는 VisionCanvas.Filters.Wpf, 필터 계산은 IndustrialVision.Filters에 있습니다. Canvas의 파일 입력을 쓰지 않는 호스트는 NetVips를 필수로 붙일 이유가 없습니다.

앱이 조립→Canvas / 파일 I/O / 검사 서비스→작은 계약과 순수 기하

처음 보는 C# 표현 해설

record / with
데이터를 표현하고 비교하기 편한 문법입니다. state with { Viewport = next }는 나머지 값을 공유하는 새 값을 만듭니다. record라고 내부의 List까지 자동으로 불변이 되는 것은 아닙니다.
readonly record struct
작은 값을 표현합니다. PointD나 변환 값처럼 값 자체가 의미를 가집니다. 참조 타입처럼 모두 힙 객체를 새로 만드는 것으로 생각하지 않습니다.
ImmutableDictionary
이전 버전을 바꾸지 않고 새 버전을 만들며 내부 구조를 공유할 수 있는 사전입니다. ‘전체 데이터를 항상 깊은 복사한다’는 뜻이 아닙니다.
interface
소비자가 필요한 행동의 약속입니다. 이름 앞의 I는 프로젝트 관례입니다. 인터페이스 하나가 자동으로 SOLID를 보장하지 않습니다.
event
‘상태가 변했다’고 구독자에게 알립니다. 구독자가 어떤 순서로 어떤 스레드에서 실행되는지도 확인해야 합니다.
Task / CancellationToken
작업 완료를 표현하는 값과 협력적 취소 요청입니다. async라고 항상 새 스레드를 만들지 않고, 취소했다고 이미 시작한 계산이 즉시 사라지지도 않습니다.
Dispose / using
자원의 사용을 끝냈음을 명시합니다. using 블록 끝에서 Dispose를 호출합니다. 소유권을 넘긴 객체를 다시 Dispose하면 안 되는 경우를 6장에서 배웁니다.

SOLID 5개: 질문으로 읽기

원칙쉬운 뜻과 저장소의 예리뷰 질문
SRP · 단일 책임바뀌는 이유를 모은다. TilePlanner는 주소 계산, TileWorker는 읽기와 수명.타일 좌표 계산 함수가 파일까지 열고 있나?
OCP · 개방/폐쇄변형이 실제로 필요한 곳을 계약으로 확장. 다른 소스도 ITileSource 구현 가능.새 형식 때문에 Core에 PNG/TIFF 분기가 필요한가?
LSP · 치환같은 약속의 구현은 교체해도 호출자의 기대를 지킨다.새 소스도 취소, 버퍼 형식, 해제 계약을 지키나?
ISP · 인터페이스 분리쓰는 기능만 작게 요구한다. IFrameSource와 ITileSource의 소비 방식이 다르다.파일 소스에 의미 없는 Play/Stop을 강요하나?
DIP · 의존성 역전핵심 규칙은 플랫폼 구현 대신 계약에 의존. 파일 로더 선택은 호스트가 한다.Core가 WPF 창이나 CUDA 장치를 직접 생성하나?

여기서 ‘닫혀 있다’는 기존 코드를 절대 수정하지 말라는 뜻이 아닙니다. 실제 변화의 경계에서 영향 범위를 줄이라는 뜻입니다. 한 번 쓰는 계산마다 인터페이스·팩터리·매니저를 만들면 읽기만 어려워질 수 있습니다.

GRASP 9개: 일을 누구에게 맡길까

원칙이 프로젝트에서의 판단
Information Expert · 정보 전문가도형 좌표를 가진 RoiGeometry가 Contains를 계산한다. ViewModel이 삼각함수를 다시 구현하지 않는다.
Creator · 생성 책임EditorSession이 문서 규칙을 지켜 ROI를 추가한다. GPU 소유자가 GPU 리소스를 생성·해제한다.
Controller · 요청 조정UI의 편집 요청을 EditorSession이 받는다. 버튼 핸들러 안에서 문서 사전을 직접 고치지 않는다.
Low Coupling · 낮은 결합검사 결과를 중립 표시 데이터로 변환해 Canvas에 전달한다. Canvas는 검사 공급자를 모른다.
High Cohesion · 높은 응집DocumentEdit는 편집 차이, EditHistory는 순서와 커서에 집중한다.
Polymorphism · 다형성파일·합성 소스의 실제 차이는 ITileSource 구현으로 처리한다.
Pure Fabrication · 기술 책임 분리이력, 캐시, 업로드 버퍼는 실제 부품 객체와 별개인 기술 서비스다.
Indirection · 간접 연결원본 reader와 중립 계약의 어댑터가 외부 API 세부를 가린다.
Protected Variations · 변화 보호DX12 타입을 렌더 경계에 두어 GPU 구현 변화가 도메인 규칙으로 퍼지지 않게 한다.

SRP와 응집, DIP와 변화 보호 등은 서로 겹치는 관점입니다. 원칙 이름을 코드에 주석으로 붙이는 것보다 ‘이 변경 때문에 왜 이 파일도 고쳐야 했나’를 설명하는 편이 유용합니다.

패턴은 필요한 문제의 이름

MVVM은 View·ViewModel·상태를 나누어 바인딩과 규칙의 경계를 만듭니다. Command/Memento 관점은 요청과 변경 전후 값을 기록하여 Undo를 가능하게 합니다. State는 드래그 도구의 진행 상태, Strategy/Adapter는 소스·도형·외부 API 변형, Composite는 부모·자식 구조, Observer는 Changed 이벤트에서 읽을 수 있습니다. 구현이 교과서 클래스 모양과 똑같아야 하는 것은 아닙니다.

직접 확인: ‘파일 열기’ 버튼에서 무엇을 직접 하면 안 될까?

픽셀 디코드 반복문, ROI 좌표 보정, GPU fence 대기를 한 버튼 핸들러에 넣지 않습니다. 버튼은 호스트의 이미지 교체 작업을 요청합니다. 디코더가 읽고, 성공한 입력으로 문서를 교체하고, 불변 장면을 게시합니다. 실패했을 때 기존 이미지·문서를 보존하는 경계도 필요합니다.

Canvas 재사용 경계 · 선택형 파일 디코더

작은 계약을 코드로 읽기

Canvas는 파일 이름이나 NetVips 타입 대신 아래 계약을 사용합니다. Info는 영상 규격, Read는 한 타일 읽기, IDisposable은 해제 약속입니다. 렌더러가 디코더 종류를 몰라도 되므로 DIP·Protected Variations를 구체적으로 볼 수 있습니다. 구현은 취소와 버퍼 소유권까지 지켜야 하므로 메서드 이름만 맞추는 것으로 LSP가 성립하지 않습니다.
