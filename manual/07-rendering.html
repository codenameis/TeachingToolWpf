07. WPF와 DX12로 그리기

CPU의 요청과 GPU의 완료를 구별하기

WPF는 도구, DX12는 영상 뷰포트

WPF는 버튼·목록·속성·바인딩을 담당합니다. HwndHost는 WPF 레이아웃 안에 별도 Windows 자식 창(HWND)을 넣습니다. DX12는 그 창의 swap chain에 이미지·ROI·선택 핸들·이름표를 함께 그립니다. ROI마다 WPF Shape를 만들면 많은 객체·레이아웃 비용이 생깁니다.

이 구조의 자식 HWND에는 airspace 제약이 있습니다. WPF 반투명 Canvas나 Adorner를 위에 올려 같은 화면처럼 그릴 수 있다고 가정하지 않습니다. ROI overlay는 같은 GPU 경로에 둡니다. D3DImage를 DX12 texture에 바로 연결하는 설계도 사용하지 않습니다.

소유자하는 일전달물

렌더가 UI 컬렉션을 동시에 읽으면 사용자가 수정하는 순간 열거가 깨질 수 있습니다. 그래서 완성된 불변 장면을 게시합니다. RenderScene의 불변 껍데기만으로 내부 버퍼의 수명이 자동 해결되는 것은 아니므로 별도 소유권 계약도 필요합니다. 정지 화면은 계속 그리지 않고 요청을 합쳐 기다립니다.

GPU 명령을 음식 주문서처럼 읽기

device
사용할 그래픽 장치. 자동 모드는 하드웨어를 우선하고 생성할 수 없으면 WARP CPU 표시를 사용합니다.
command list / queue
복사·그리기 명령을 적은 목록과 GPU에 제출하는 줄입니다. 제출은 완료가 아닙니다.
texture / buffer
영상처럼 2차원으로 읽는 저장소와 일반 데이터 저장소입니다.
descriptor
셰이더가 어떤 자원을 어떤 형태로 읽을지 알려 주는 설명입니다.
shader
GPU에서 정점·픽셀 등에 적용할 작은 프로그램입니다. HLSL로 작성합니다.
swap chain / back buffer
그릴 화면 버퍼와 표시 전환을 관리합니다. 현재 구현은 back buffer 두 개입니다.
fence
제출한 작업이 어느 번호까지 끝났는지 확인하는 완료 표식입니다.

한 프레임을 실제 순서로 읽기

  1. 새 장면·영상·타일 요청을 기다립니다. DXGI 표시 준비 신호를 기다립니다.
  2. 유효한 창 크기를 확인하고 필요하면 resize합니다.
  3. Dx12Surface.Begin에서 사용할 슬롯의 이전 GPU 작업 완료를 확인합니다. 그 뒤에만 명령 메모리와 upload 공간을 재사용합니다.
  4. 대기 중 도착한 최신 장면을 가져옵니다. 타일·필터·라벨을 준비합니다.
  5. ScenePainter가 표시 요소를 만들고 각 Pipeline이 그리기 명령을 기록합니다.
  6. 현재 버퍼를 Present 가능한 상태로 바꾸고 제출·Present합니다. 완료 fence를 슬롯과 지연 해제 목록에 연결합니다.

RenderWorker.Run · Dx12Surface · ScenePainter

DXGI의 표시 준비와 GPU fence 완료는 다른 조건입니다. 앞의 조건만 기다리고 GPU가 읽는 버퍼를 덮어쓰면 안 됩니다. Present(1)을 호출했다는 사실만으로 물리 모니터에 그 픽셀이 나타난 시각을 알 수 있는 것도 아닙니다.

resource barrier와 fence

barrier는 GPU 자원을 복사 대상으로 쓰던 상태에서 셰이더 입력으로 쓰는 상태 등으로 전환합니다. fence는 CPU나 다른 작업이 완료를 관찰할 수 있게 합니다. ‘상태 전환’과 ‘완료 기다리기’를 바꿔 쓰지 않습니다.

GPU texture: COPY_DEST → PIXEL_SHADER_RESOURCE
back buffer: PRESENT → RENDER_TARGET → PRESENT

CPU: 명령 제출 → fence 번호 기록 → 다음 슬롯 작업
GPU: 명령 실행 → 완료 번호 갱신
CPU: 그 슬롯 재사용 시 완료 번호 확인

이 순서를 생략하면 드물게 깜빡임·이전 픽셀·장치 오류가 생길 수 있습니다. C#의 GC는 GPU가 언제 읽기를 끝냈는지 알지 못합니다. Retire가 즉시 해제가 아니라 fence 후 해제 예약인 이유입니다.

Microsoft resource barrier · fence 기반 자원 관리

화면 좌표에서 셰이더 좌표까지

xndc=2xphysicalWphysical−1yndc=1−2yphysicalHphysicalx_ndc = 2x_physical/W_physical − 1; y_ndc = 1 − 2y_physical/H_physical

NDC는 정규화 장치 좌표입니다. 왼쪽은 −1, 오른쪽은 +1, 위쪽은 +1, 아래쪽은 −1입니다. 화면 y가 아래로 증가하므로 두 번째 식의 부호가 반대입니다. DIP와 물리 px를 분자·분모에 섞으면 DPI별로 틀어집니다.

많은 ROI는 인스턴스 데이터로 보관하고 공통 이동·회전 상수만 갱신합니다. 화면 밖 후보는 BVH 공간 트리로 건너뜁니다. 작은 묶음을 LOD로 요약하더라도 문서의 실제 ROI는 그대로 남습니다. C# 구조체와 HLSL 상수의 크기·오프셋은 계약이므로 필드 순서를 ‘보기 좋게’ 바꾸면 안 됩니다.

RoiDrawConstants · Roi.hlsl · GPU 배치 테스트

직접 확인: 명령 제출 직후 texture.Dispose()가 위험한 이유는?

CPU가 제출을 끝내도 GPU는 아직 그 texture를 읽을 수 있습니다. 마지막 사용의 fence가 완료된 뒤 소유자가 해제해야 합니다. UI 스레드에서 기다리는 방식으로 해결하면 입력이 멈출 수 있어 렌더 소유 경계에서 처리합니다.

호스트가 장면을 보내는 실제 코드

렌더 스레드가 UI 컨트롤을 직접 읽게 하지 않고 화면 크기·영상 세대·문서·편집 미리보기를 한 장면으로 보냅니다. 아래 메서드는 9장의 LessonWindow 안에 있으며, 전체 창 코드는 같은 9장에서 펼칠 수 있습니다.

Publish: 현재 상태를 RenderScene으로 게시

현재 저장소 코드 · 발췌 · manual/labs/CanvasHost/LessonWindow.cs

private void Publish()
{
    if (_image is null || _closing)
    {
        return;
    }
    _input.SetViewportSize(_viewport.ViewWidth, _viewport.ViewHeight);
    _viewport.Submit(new RenderScene(_session.State, _image, _generation,
        _viewport.ViewWidth, _viewport.ViewHeight, _viewport.Dpi,
        _input.Overlay, Transform: _session.TransformPreview));
}

Submit 호출은 “장면을 전달했다”는 뜻입니다. GPU 제출, GPU 완료, 실제 모니터 표시는 각각 다른 시점입니다.
