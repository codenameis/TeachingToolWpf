06. 큰 영상과 버퍼의 수명

필요한 조각만 읽고, 소유자를 분명히 하기

1. 타일링은 큰 그림을 작은 조각으로 관리하는 방법

지도 앱에서 지금 보는 동네의 조각을 먼저 읽는다고 생각하세요. 타일(tile)은 영상 격자를 일정 크기로 나눈 조각이고, 뷰포트(viewport)는 현재 창에서 영상을 보여 주는 영역입니다. 타일링의 핵심은 조각내기와 함께 ‘필요한 조각만 읽고, 나중에 다시 쓰고, 예산을 넘으면 버리기’입니다. 전체 영상을 먼저 거대한 배열에 읽은 후 잘라 놓으면 최초 메모리 문제는 여전히 남습니다.

이 프로젝트의 기본 타일은 512×512px입니다. 8192×8192 Gray8 전체는 64MiB, 타일 하나는 512×512×1=262,144bytes=256KiB입니다. 네 개만 필요한 순간의 유효 픽셀은 1MiB입니다. 이는 픽셀 바이트 계산이며, 실제 풀 배열·GPU 정렬·캐시·업로드 메모리와 파일 디코더 비용은 따로 셉니다.

나누는 대상무엇을 뜻하나섞으면 생기는 오해
논리 타일Level, X, Y로 요청하는 영상 조각타일 API라고 원본 파일도 같은 블록으로 압축된 것은 아님
디스크 피라미드여러 축소 단계의 파일을 준비해 부분 읽기최초 변환 시간·디스크 공간이 공짜가 아님
GPU 타일 캐시읽은 조각을 화면에 그릴 텍스처로 보관퇴출 요청과 GPU 실제 해제는 다른 시점

512는 이 저장소의 선택입니다. 작으면 요청·텍스처 수가 늘고, 크면 화면 밖 픽셀까지 더 많이 읽고 업로드할 수 있습니다. 다른 크기가 항상 빠르다고 가정하지 말고 같은 이미지·탐색 경로에서 읽기량, 긴 프레임, 메모리를 비교합니다.

2. 주소와 마지막 조각: 1300×900을 직접 나누기

우선 원본 단계인 level 0만 봅니다. X는 타일 열, Y는 타일 행이며 0부터 시작합니다. TileKey(0, 2, 1)은 원본의 오른쪽 아래 타일입니다. X=2가 원본 x=2px라는 뜻은 아닙니다.

열 수=⌈WT⌉행 수=⌈HT⌉left=X×Ttop=Y×T유효 너비=min⁡(T,W−left)유효 높이=min⁡(T,H−top)열 수 = ceil(W/T); 행 수 = ceil(H/T); left = X×T; top = Y×T; 유효 너비 = min(T,W−left); 유효 높이 = min(T,H−top)

W=1300, H=900, T=512를 넣으면 열은 ⌈2.539…⌉=3, 행은 ⌈1.757…⌉=2입니다. ⌈ ⌉는 올림입니다. 마지막 타일의 시작은 (1024,512), 크기는 276×388입니다. 현재 PixelBuffer는 이 유효 크기만 담습니다. 남은 부분을 검은 원본 픽셀이라고 검사에 넣으면 안 됩니다.

원본 x 범위       [0,512)    [512,1024)   [1024,1300)
y [0,512)         (0,0)       (1,0)          (2,0)
y [512,900)       (0,1)       (1,1)          (2,1)
각 주소 앞의 Level은 모두 0입니다.

[a,b)a 이상 b 미만는 a는 포함하고 b는 포함하지 않는 범위입니다. x=512인 픽셀은 두 타일에 중복 저장하지 않고 두 번째 타일에만 속합니다. 마지막 타일 Gray8의 stride는 276bytes, 유효 길이는 276×388=107,088bytes입니다.

3. 지금 화면에 필요한 타일만 고르기

먼저 화면 왼쪽 위 (0,0)와 오른쪽 아래 (화면 너비,화면 높이)를 ScreenToImage로 원본 좌표로 바꿉니다. 여기서는 ROI만 회전하며 ViewportTransform은 배율·이동만 가지므로 이 두 모서리로 범위를 구할 수 있습니다. 회전 뷰포트를 새로 설계한다면 네 모서리와 교차 판정을 다시 고려해야 합니다.

firstColumn=clamp⁡(⌊leftS⌋,0,열 수)columnEnd=clamp⁡(⌈rightS⌉,0,열 수)요청 열:firstColumn≤column<columnEnd행에도 같은 계산 적용firstColumn = clamp(floor(left/S),0,열 수); columnEnd = clamp(ceil(right/S),0,열 수); firstColumn ≤ column < columnEnd; 행에도 같은 계산 적용

S는 원본 좌표에서 타일 한 칸이 덮는 길이입니다. level 0에서는 512입니다. 화면의 원본 영역이 x=[400,1000), y=[300,700)이면 열 시작 0/끝 2, 행 시작 0/끝 2이므로 (0,0), (1,0), (0,1), (1,1)의 네 타일을 요청합니다. for문의 끝을 ≤로 쓰면 필요 없는 열/행이 하나씩 늘어납니다.

실험: 창을 옮기면서 요청 주소 보기

1300×900 영상, level 0, 배율 1, DPI 1로 고정했습니다. 슬라이더 값은 창 왼쪽 위의 원본 좌표입니다. 실제 ViewportTransform.Offset은 이 값의 음수입니다.

청록색: 계획된 타일 · 주황 점선: 현재 창 · 회색: 이번 계획에 없는 타일. 주소의 Level은 모두 0입니다.

원본 x=[400,1000), y=[300,700). 열 [0,2), 행 [0,2). 4개: (0,0), (1,0), (0,1), (1,1).

창 크기를 512×512, x=512, y=0으로 맞추면 딱 한 타일 (1,0)입니다. 슬라이더에 초점을 둔 뒤 방향키로 1px씩 조절할 수 있습니다. x=1600으로 옮기면 열 시작과 끝이 모두 3이 되어 0개입니다.

실제 Planner는 유효 픽셀 영역보다 큰 타일 격자 범위로 제한합니다. 예를 들어 x=1400, y=0이면 영상은 이미 끝났지만 마지막 격자 셀은 x=1536까지이므로 가장자리 타일을 보수적으로 요청할 수 있습니다. 이 실험도 이 구현을 따릅니다. 그리기는 실제 이미지 끝에서 제한하며, 이 타일은 검사용 가상 검정 영역을 뜻하지 않습니다. 전체 개요 요청과 캐시 적중은 이 계산기에서 제외했습니다.

4. 축소 화면에서는 피라미드가 필요하다

큰 영상을 창에 맞춰 아주 작게 봐도 level 0 타일만 쓰면 결국 원본 전부를 읽게 됩니다. 피라미드는 미리 더 작게 만든 영상들을 단계별로 준비하는 방법입니다. level 0은 원본, level 1은 가로·세로 약 절반, level 2는 약 1/4입니다. 표시용 디스크 피라미드는 NetVips의 Linear 축소를 사용합니다. 검사에서 원본 crop을 면적 평균하는 정책과 구별합니다.

f=2LS=512×fL=clamp⁡(⌊log2⁡(1z·d)⌋,0,Levels−1)축소 계수 f = 2ᴸ; 원본에서 한 타일이 덮는 길이 S = 512×f; L = clamp(floor(log₂(1/(z·d))),0,Levels−1)

L은 단계, z는 DIP/원본 px, d는 물리 px/DIP입니다. z·d는 원본 픽셀 하나가 차지하는 실제 화면 픽셀 수입니다. log₂는 ‘2를 몇 번 곱했는가’를 구합니다. z=0.25, d=1이면 1/(z·d)=4=2²이므로 L=2입니다. d=2이면 L=1로 더 자세한 타일을 선택합니다. 확대해서 z·d≥1이면 원본 L=0을 사용합니다.

8192 정사각형의 단계단계 영상 크기전체 타일 수타일 한 칸의 원본 길이
08192×819216×16=256512px
14096×40968×8=641024px
22048×20484×4=162048px
31024×10242×2=44096px
4512×51218192px

실험: 8192×8192의 표시 단계

L=2, 한 타일은 원본 2048px, 전체 단계 격자는 4×4.

TileKey(2,1,0)의 단계 영상 시작은 (512,0)이지만 원본 시작은 (2048,0)입니다. 이 타일 안의 픽셀 (10,20)의 셀 시작을 원본에 대응시키면 ((512+10)×4,20×4)=(2088,80)입니다. 픽셀 중심·축소 필터의 실제 샘플 위치를 다루는 식은 별도이므로 이 단순 주소식을 정밀 검사 좌표 보정에 그대로 쓰지 않습니다.

정확히 절반씩 줄어드는 충분히 큰 영상의 총 픽셀 수는 WH(1+14+116+⋯)≈4WH3WH × (1+1/4+1/16+…) ≈ 4WH/3입니다. 가로·세로가 모두 반이므로 면적은 1/4입니다. 원본이 64MiB라면 무한 단계 근사는 약85.33MiB, 위 5단계의 정확한 합은 85.25MiB입니다. 홀수 가장자리·파일 헤더·정렬·압축에 따라 실제 파일/메모리 크기는 다릅니다. 저장소는 한 변 최대512 이하에서 멈추므로 1×1까지 만들지 않습니다.

5. 이제 실제 타일 계획 코드를 읽기

수식과 이름을 연결하세요. downsampleFactor는 2L2의 L제곱, tileSpanInImage는 S, firstColumn/columnEnd는 시작/제외 끝입니다. 1 << level은 정수 1을 왼쪽으로 L비트 옮겨 2L을 만드는 표현입니다. 이 메서드는 주소 목록만 계산하며 파일 읽기나 GPU 생성은 하지 않습니다.

TilePlanner 전체: 계산 순서대로 읽기

현재 저장소 코드 · 파일 전체 · src/VisionCanvas/Imaging/TilePlanner.cs

using VisionGeometry;
using VisionImaging.Abstractions;

namespace VisionCanvas.Imaging;

public static class TilePlanner
{
    /// <summary>뷰포트에 필요한 타일 주소를 행 우선 순서로 구한다. 픽셀 읽기와 캐시 관리는 하지 않는다.</summary>
    public static IReadOnlyList<TileKey> Visible(ImageInfo image, ViewportTransform view, double width, double height, double dpi)
    {
        if (width <= 0 || height <= 0 || view.Scale <= 0 || dpi <= 0)
        {
            return [];
        }

        // Scale은 DIP/원본 픽셀, dpi는 물리 픽셀/DIP다. 곱한 값으로 표시 해상도를 고른다.
        var level = Math.Clamp((int)Math.Floor(Math.Log2(1 / (view.Scale * dpi))), 0, image.Levels - 1);
        var downsampleFactor = 1 << level;
        var tileSpanInImage = (double)ImageInfo.TileSize * downsampleFactor;
        var imageTopLeft = view.ScreenToImage(new PointD(0, 0));
        var imageBottomRight = view.ScreenToImage(new PointD(width, height));
        var columnCount = (int)Math.Ceiling(image.Width / tileSpanInImage);
        var rowCount = (int)Math.Ceiling(image.Height / tileSpanInImage);

        // 시작은 포함하고 끝은 제외한다. 이미지 밖 여백에는 타일을 요청하지 않는다.
        var firstColumn = Math.Clamp((int)Math.Floor(imageTopLeft.X / tileSpanInImage), 0, columnCount);
        var firstRow = Math.Clamp((int)Math.Floor(imageTopLeft.Y / tileSpanInImage), 0, rowCount);
        var columnEnd = Math.Clamp((int)Math.Ceiling(imageBottomRight.X / tileSpanInImage), 0, columnCount);
        var rowEnd = Math.Clamp((int)Math.Ceiling(imageBottomRight.Y / tileSpanInImage), 0, rowCount);
        var result = new List<TileKey>();
        for (var row = firstRow; row < rowEnd; row++)
        {
            for (var column = firstColumn; column < columnEnd; column++)
            {
                result.Add(new(level, column, row));
            }
        }

        return result;
    }
}

다음은 파일 소스가 요청받은 단계에서 조각을 읽는 실제 메서드입니다. 여기의 left/top/width/height는 그 단계의 픽셀 좌표입니다. _levels에는 이미 축소 단계별 이미지가 있으므로 원본 축소 계수를 다시 곱하지 않습니다. 앞의 Planner가 만든 유효 key를 받아 쓰며, 임의의 외부 key 검증을 보여 주는 예제는 아닙니다.

DiskPyramidSource.Read: 가장자리 크기와 실패 시 반환

현재 저장소 코드 · 발췌 · src/VisionImaging/Imaging/DiskPyramidSource.cs

public PixelBuffer Read(TileKey key, CancellationToken cancellationToken)
{
    cancellationToken.ThrowIfCancellationRequested();
    var image = _levels[key.Level];
    var left = key.X * 512;
    var top = key.Y * 512;
    var width = Math.Min(512, image.Width - left);
    var height = Math.Min(512, image.Height - top);
    var output = new PixelBuffer(width, height, Info.Pixels);
    try
    {
        // Region은 생성·사용·해제를 같은 호출 스레드에서 한다. 다음 Read는 다른 worker여도 안전하다.
        using var region = Region.New(image);
        VipsRegionPixels.Copy(region, left, top, width, height, output.Bytes, output.Length);
        cancellationToken.ThrowIfCancellationRequested();
        return output;
    }
    catch
    {
        output.Dispose();
        throw;
    }
}

Region은 해당 호출 스레드 안에서 생성·사용·해제합니다. 성공하면 output을 호출자에게 넘기고, 오류나 취소가 생기면 catch에서 직접 반환합니다. return output할 버퍼를 using var output으로 바꾸면 호출자가 읽기 전에 반환되므로 잘못입니다. NetVips 없는 합성 소스 전체는 9장에도 포함했습니다.

6. 파일 열기부터 화면에 붙이기까지

  1. 호스트가 파일을 연다. DiskPyramidSource.Open은 캐시가 없으면 원본을 순차 읽고 디스크의 0.v, 1.v… 단계를 준비합니다. 최초 준비에는 시간과 디스크 공간이 듭니다. 기존 캐시 식별에는 경로·파일 길이·최종 수정 시각이 사용됩니다.
  2. 장면에서 주소를 구한다. GpuImageResources는 가장 작은 전체 개요 타일 (Levels−1,0,0)을 먼저 붙이고, Planner가 구한 상세 타일 목록과 중복을 제거합니다.
  3. 캐시에 없는 주소만 요청한다. 이미 GPU에 있는 타일은 재사용합니다. 현재 목록은 개요 다음에 행/열 순이며, 커서 중심 우선이나 이동 방향 예측을 구현한 것으로 설명하지 않습니다.
  4. TileWorker 한 곳에서 읽는다. 대기 요청은 최신 목록으로 합칩니다. 새 요청이 생겼다고 실행 중인 Read를 즉시 중단하는 것은 아니며, 현재 타일 처리 뒤 최신 요청으로 넘어갑니다. 준비 슬롯 32개가 가득 차면 소비를 기다립니다.
  5. 렌더 측에서 세대를 확인한다. 한 번의 Update에서 준비 결과를 최대16개 꺼내고 현재 세대·중복을 검사해 업로드합니다. 꺼낸 CPU 버퍼는 이 범위가 끝날 때 반환합니다.
  6. 완료된 조각을 그린다. 개요가 준비되어 있으면 상세 타일이 아직 없는 곳의 배경으로 활용합니다. 준비된 불투명 상세 타일이 모두 덮는 경우 개요 중복 그리기를 생략합니다. 개요마저 아직 없다면 즉시 완성 영상을 보장하지 않습니다.

압축 파일의 임의 사각형을 요청하는 API가 있다고 그 부분의 압축 바이트만 읽을 수 있는 것은 아닙니다. 형식과 디코더 접근 방식에 따라 선행 디코드가 필요합니다. 현재 디스크 피라미드 준비를 파일 열기 시간에서 빼고 “24K를 즉시 연다”고 말하면 안 됩니다.

부분 영역을 요구에 맞춰 계산하는 배경: libvips 공식 처리 모델. 위 여섯 단계는 이 저장소의 DiskPyramidSource, TileWorker, GpuImageResources, ScenePainter를 확인한 설명입니다.

7. 캐시와 메모리 예산을 함께 설계하기

캐시는 다시 볼 가능성이 있는 타일을 보관하는 공간입니다. LRU는 Least Recently Used, 즉 가장 오래 사용하지 않은 항목부터 버리는 방식입니다. 현재 구현은 마지막 사용 프레임 번호를 기록하고 현재 프레임에서 사용하는 타일은 퇴출하지 않습니다. 같은 번호의 항목 사이 순서까지 특별한 우선순위라고 해석하지 않습니다.

유효 타일 바이트=너비×높이×픽셀당 바이트Gray8: 5122×1 byte=256 KiBGray16: 5122×2 bytes=512 KiBRGBA32: 5122×4 bytes=1 MiB유효 타일 바이트 = 너비×높이×픽셀당 바이트; Gray8 512²×1 byte=256 KiB; Gray16 512²×2 bytes=512 KiB; RGBA32 512²×4 bytes=1 MiB

하드웨어 타일 예산은 min⁡(256 MiB,max⁡(16 MiB,로컬 메모리 예산5))min(256 MiB, max(16 MiB, 로컬 메모리 예산/5)), WARP는 256MiB입니다. 이것은 활성 타일 퇴출 정책의 기준입니다. 현재 가시 타일은 유지하고, 퇴출된 GPU 리소스도 fence 완료까지 살아 있을 수 있습니다. 업로드·라이브 텍스처·라벨·ROI·CPU 풀·디스크 캐시까지 합친 프로세스 전체 상한이 아닙니다.

UpdateTiles 전체: 개요 추가 → 사용 표시 → 퇴출 → 누락 요청

현재 저장소 코드 · 발췌 · src/VisionCanvas/Rendering/GpuImageResources.cs

private void UpdateTiles(ImageInfo image, RenderScene scene, Dx12Surface surface, long frameNumber)
{
    var visible = TilePlanner.Visible(image, scene.Document.Viewport, scene.Width, scene.Height, scene.Dpi).Prepend(new TileKey(image.Levels - 1, 0, 0)).Distinct().ToArray();
    foreach (var key in visible)
    {
        if (_tiles.ContainsKey(key))
        {
            _lastUsed[key] = frameNumber;
        }
    }

    var bytes = _tiles.Values.Sum(t => t.Bytes);
    if (bytes > gpu.TileBudgetBytes)
    {
        foreach (var entry in _lastUsed.OrderBy(p => p.Value).ToArray())
        {
            if (bytes <= gpu.TileBudgetBytes)
            {
                break;
            }

            if (entry.Value == frameNumber)
            {
                continue;
            }

            var texture = _tiles[entry.Key];
            bytes -= texture.Bytes;
            _tiles.Remove(entry.Key);
            _lastUsed.Remove(entry.Key);
            surface.Retire(texture);
        }
    }
    source.RequestTiles(_generation, visible.Where(key => !_tiles.ContainsKey(key)).ToArray());
}

TileKey만으로는 파일을 식별할 수 없습니다. 서로 다른 파일에도 (0,0,0)이 있습니다. 현재 GPU 사전은 한 세대만 보관하고 세대가 바뀌면 비우므로 안전한 경계를 만듭니다. 여러 이미지의 캐시를 함께 보관하는 설계로 바꾼다면 이미지 버전도 키에 포함해야 합니다.

8. 타일 경계의 줄과 필터 이음새 구별하기

문제가 타일 경계마다 반복되면 먼저 좌표·유효 크기·stride·샘플링을 분리해 확인하세요. 마지막 276px 타일을 512px 폭으로 늘려 그리면 영상 자체가 밀립니다. GPU가 샘플링할 때의 경계 처리와 필터가 이웃 픽셀을 읽는 범위도 서로 다릅니다.

예를 들어 3×3 평균 필터는 좌우·상하 한 픽셀 이웃이 필요합니다. 512×512 출력 타일을 독립 처리하려면 주변까지 514×514를 읽어 계산한 뒤 가운데 512×512만 남길 수 있습니다. 이 추가 테두리를 halo라고 부릅니다. 반경 r이면 내부 타일의 읽기 폭은 T+2r이며, 실제 영상 끝에서만 반사·복제·상수 같은 경계 규칙을 적용합니다. 매 타일 끝을 영상 끝처럼 처리하면 이웃 타일의 실제 픽셀 대신 가짜 경계를 사용합니다.

가로 한 줄의 평균 예로 타일 A의 마지막 값이 0, 타일 B의 앞 두 값이 100,100이라면 B 첫 위치의 3점 평균은 (0+100+100)/3≈66.7입니다. B의 가장자리 값을 복제하면 (100+100+100)/3=100이 되어 경계에 차이가 남습니다. 여러 필터를 연결할 때는 각 연산의 이웃 범위도 누적해서 고려해야 합니다.

이 halo 사례는 직접 타일 필터를 설계할 때의 교육 예이며, 현재 Canvas의 타일 표시 경로에 추가된 기능이 아닙니다. 영상 바깥 padding 규칙은 OpenCV 경계 처리 공식 설명을 참고하세요.

작게 표시한 타일을 검사 원본으로 쓰지 않습니다. 표시 피라미드는 보기 위한 데이터이고, 검사 학습·최종 검증은 별도 원본 reader와 유효 마스크 계약을 따릅니다.
직접 확인: 1300×900의 마지막 타일을 만들 때 512×512를 채우면 왜 문제가 될까?

실제 유효 영역은 276×388입니다. 나머지를 실제 검은 픽셀로 평균·검사하면 값과 도형 경계가 달라집니다. 고정 크기 저장소를 설계할 수는 있지만 유효 너비/높이를 별도로 전달하고 모든 소비자가 지켜야 합니다. 현재 PixelBuffer는 유효 크기로 생성하므로 이런 별도 padding을 영상으로 전달하지 않습니다.

오래된 결과가 새 이미지에 붙으면 안 된다

파일 A를 읽던 중 B를 열었다고 가정하세요. A의 느린 타일이 나중에 완료될 수 있습니다. Generation은 현재 이미지의 세대 번호입니다. 타일 결과에 번호를 붙이고 현재 번호와 다른 결과는 게시하지 않고 버퍼를 반환합니다.

메모리 풀은 주차장처럼 이미 확보한 공간을 빌려주는 도구입니다. 반환은 ‘내가 더는 사용하지 않겠다’는 약속이지 배열을 0으로 지운다는 뜻이 아닙니다. 반환된 배열의 참조를 보관해 읽으면 다른 프레임의 데이터가 보일 수 있습니다.

// 지역 계산에만 쓰면 using이 적절하다.
using var pixels = new PixelBuffer(512, 512, PixelKind.Gray8);
pixels.Span.Fill(64);
// 이 범위에서 다 썼으므로 끝에서 반환한다.

// 소유권을 넘길 때는 using으로 즉시 반환하면 안 된다.
var frame = new VideoFrame(sequence, timestamp, pixelsOwnedForFrame);
viewport.PublishFrame(frame); // 이 호출 이후 frame을 게시자가 해제하지 않는다.

두 예제는 별개의 상황입니다. 첫 번째의 using 변수 pixels를 두 번째로 넘기라는 뜻이 아닙니다. 실제 게시 경로와 실패 시 소유권은 LatestFrameMailbox 및 VideoFrame을 함께 읽습니다.

표시는 최신 완료 프레임 우선

생산자가 60장/초, 표시가 30장/초라면 모든 프레임을 줄 세워 표시할 때 지연이 계속 커집니다. 한 칸 mailbox는 아직 소비되지 않은 프레임을 최신 것으로 바꾸고 이전 lease를 반환합니다. 버린 개수는 Dropped로 셉니다. ‘모든 영상을 저장·검사해야 한다’는 무손실 요구는 다른 파이프라인입니다.

기본 업로드는 CPU 원본 → 재사용 upload buffer → GPU texture입니다. Retain이 전체 픽셀 복사를 피한다고 전체 파이프라인이 zero-copy가 되지는 않습니다. 풀 배열·upload 공간·GPU texture·타일 캐시·디스크 캐시의 메모리는 각각 계산해야 합니다.

직접 확인: A 타일 준비 중 B를 열었다. A 타일이 완료되면?

세대가 다르면 B 장면에 넣지 않고 A의 PixelBuffer를 반환합니다. B의 source는 유지합니다. 취소가 늦게 반영되어 A의 계산이 끝나도 게시 검증이 막아야 합니다. 예외를 무시하는 것으로 이 계약을 대신하지 않습니다.
