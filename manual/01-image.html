사진 속 밝기를 C# 배열에서 꺼내 봅시다

먼저 ROI를 올릴 사진부터 필요합니다. 화면에는 회색 사진이 보이지만 프로그램이 가진 것은 밝기 숫자입니다. 오늘은 두 번째 줄의 첫 픽셀 하나만 읽어 봅니다.

기억할 한 문장이미지에서 읽는 것은 숫자이고, stride는 다음 줄로 건너가는 바이트 수입니다.

  1. 작게 그리기

    가로 3칸, 세로 2칸의 회색 사진을 생각합니다. 첫 줄 밝기는 11·22·33, 둘째 줄은 44·55·66입니다.

  2. 저장된 줄 보기

    한 줄이 4바이트를 차지한다면 밝기 세 개 뒤에 빈 칸 하나가 붙습니다. 이 예에서 빈 칸은 픽셀이 아닙니다.

  3. 하나 꺼내기

    두 번째 줄의 첫 픽셀을 읽으려면 첫 줄 전체를 건너뜁니다. 밝기 세 개뿐 아니라 빈 칸까지 건너뛰어야 44를 읽습니다.

잠깐, 답을 보기 전에 예상해 보세요

한 줄의 밝기 값은 세 개입니다. 다음 줄까지 3바이트만 건너뛰면 무엇을 읽게 될까요?

사진 한 장을 배열로 생각하기

사진을 아주 크게 확대해서 모눈종이처럼 칸을 나눠 봅시다. 컴퓨터는 각 칸에 적힌 숫자를 읽습니다. 회색 사진에서는 숫자가 작으면 어둡고, 크면 밝습니다. 아직 “이것은 부품이다”라고 아는 단계는 아닙니다. 먼저 숫자를 정확히 읽어야 나중에 부품의 경계를 찾을 수 있습니다.

픽셀(pixel)은 격자의 한 칸입니다. Gray8 영상은 칸마다 0~255의 정수를 저장합니다. 0은 어둡고 255는 밝습니다. 예를 들어 아래 3×33×3 영상의 가운데가 밝다는 것은 배열의 가운데 값이 크다는 뜻입니다.

I=[1010101020010101010]영상 I = [10,10,10; 10,200,10; 10,10,10]

바로 위 수식에서 쓰인 기호

기호 / 읽는 법뜻과 단위코드·예시에서 찾기
II아이: 영상의 픽셀 값 또는 값을 모은 행렬. 좌표를 붙이면 그 칸의 밝기Gray8에서는 한 칸이0~255

좌표의 시작은 왼쪽 위 (0,0)(0, 0)입니다. x는 오른쪽, y는 아래로 증가합니다. 너비 W, 높이 H이면 정수 픽셀 인덱스는 0≤x<W0 ≤ x < W, 0≤y<H0 ≤ y < H입니다. 기하 계산에서 이 픽셀의 중심을 사용할 때는 보통 (x+0.5,y+0.5)(x + 0.5, y + 0.5)로 봅니다. 픽셀 인덱스와 연속 좌표를 섞으면 반 픽셀 어긋남이 생깁니다.

행렬을 읽는 데 행렬 곱셈은 아직 필요 없습니다

위 대괄호는 3행 3열의 숫자를 모아 놓은 표입니다. 첫 행은 y=0y=0, 둘째 행은 y=1y=1입니다. 둘째 행에서 x=1x=1인 칸을 찾으면 200입니다. C#의 평평한 배열이라면 [10,10,10, 10,200,10, 10,10,10]이고, 행마다 3칸이므로 위치는 1 * 3 + 1 = 4입니다. 배열의 다섯 번째 원소가 같은 픽셀입니다.

칸 번호 (1,1)과 칸 중심 (1.5,1.5)은 다른 종류의 주소입니다. 바둑판의 ‘둘째 칸’과 그 칸 한가운데에 찍은 점을 구별한다고 생각하세요. 클릭 위치는 소수일 수 있지만 배열 인덱스는 정수여야 합니다.

그렇다면 이 숫자는 누가 만들까요? 카메라의 센서가 받은 빛을 숫자로 바꿉니다. 노출은 빛을 모으는 시간이고, 게인은 얻은 신호를 키우는 정도입니다. 게인을 높이면 원하지 않는 흔들림인 잡음도 커질 수 있습니다. 초점이 맞지 않아 경계가 번졌다면 배열을 정확히 읽어도 선명한 원본이 되지는 않습니다.

비트 수·채널 수·배열 길이

앞에서는 한 칸에 밝기 숫자 하나가 있다고 했습니다. 이제 그 숫자를 컴퓨터가 어디에 넣는지 봅시다. 비트(bit)는 0 또는 1 하나를 담는 자리이고, 바이트(byte)는 비트 8개를 묶은 단위입니다. 채널은 픽셀 하나가 가진 값의 종류입니다. 회색 영상은 밝기 한 종류, 색 영상은 빨강·초록·파랑처럼 여러 종류를 저장합니다.

픽셀 수와 바이트 수는 항상 같지 않습니다. Gray8은 한 픽셀에 1바이트를 쓰고, Gray16은 2바이트를 씁니다. 여기에 행 끝의 빈칸까지 붙을 수 있습니다. 아래 표에서는 “픽셀 하나의 크기”를 먼저 보고, 다음 수식에서는 “한 줄 전체의 크기”를 확인하세요.

형식픽셀당 저장량의미
Gray81 byte28=2562⁸ = 256단계
Gray162 bytes216=65,5362¹⁶ = 65,536단계의 저장 공간
RGBA32 / BGRA324 bytes색 3채널 + 알파 1채널. 채널 순서를 구별

숫자를 담는 상자의 크기와 실제 측정의 세밀함도 다릅니다. 센서가 12비트 값을 만들고 16비트 공간에 담을 수 있습니다. 그래서 Gray16이라는 이름만 보고 센서도 16비트 정밀도라고 판단하면 안 됩니다.

두 바이트로 숫자 하나를 저장할 때는 어느 바이트가 앞인지도 약속해야 합니다. 이를 바이트 순서(endian)라고 합니다. 유효한 비트의 위치와 검정·흰색 기준도 입력 형식의 설명을 확인합니다. 화면을 밝게 보이도록 바꾼 값과 검사에 쓸 원래 값은 구별합니다.

최소 행 바이트=W×B버퍼 바이트=stride×H픽셀 시작 위치=y×stride+x×B최소 행 바이트 = W × B; 버퍼 바이트 = stride × H; 픽셀 시작 위치 = y × stride + x × B

W는 너비(px), H는 높이(px), B는 픽셀당 바이트입니다. stride는 다음 행까지 이동하는 바이트 수입니다. 외부 영상은 행 끝에 정렬용 빈칸이 붙을 수 있으므로 항상 W×BW×B라고 가정하면 안 됩니다. 현재 PixelBuffer는 빈칸 없는 stride를 생성하지만 GPU 업로드의 행 배치는 별도로 계산합니다.

ArrayPool은 사용이 끝난 배열을 모아 두었다가 다시 빌려주는 곳입니다. 6바이트를 요청해도 더 큰 배열을 받을 수 있습니다. 따라서 배열의 끝까지 전부 사진이라고 읽으면 안 됩니다. 이 코드에서는 Length가 실제 사용할 바이트 수이고, Span이 그 부분만 보여 줍니다.

checked는 크기를 곱하다가 int에 담을 수 있는 범위를 넘으면 오류를 내게 합니다. 너무 큰 수가 엉뚱한 작은 수로 바뀌어 작은 배열을 만드는 일을 막기 위한 장치입니다.

주소 수식을 두 번의 이동으로 풀기

기호와 단위뜻위 예제의 값
W, H · px가로·세로 칸 수3, 2
B · bytes/pixel한 칸이 차지하는 바이트Gray8이면 1
stride · bytes/row다음 행 시작까지의 간격4
x, y · 정수 인덱스왼쪽·위에서 건너뛸 칸과 행 수2, 1
  1. y=1y=1이므로 한 행을 건너뜁니다.1×4=4. 1×4=4바이트를 이동합니다.
  2. 그 행에서 x=2x=2칸을 건너뜁니다.2×1=2. 2×1=2바이트를 더 이동합니다.
  3. 합은 6입니다. 배열의 6번 인덱스에서 값 66을 읽습니다.

틀린 계산도 해 보세요. stride 대신 W=3W=3을 쓰면 1×3+2=51×3+2=5여서 55를 읽습니다. 실행 중 예외가 없어도 값은 틀릴 수 있습니다. 이것이 영상이 한 줄씩 밀릴 때 stride를 먼저 확인하는 이유입니다. Gray16이면 한 값을 두 바이트로 해석해야 하며 바이트 순서도 입력 계약에 따라야 합니다.

8K가 왜 부담이 되는가

“사진 한 장인데 왜 복사 한 번을 아끼나요?” 책 한 권을 전달할 때 제목만 전달하는 것과 모든 페이지를 다시 베끼는 것은 비용이 다릅니다. 영상 참조를 넘기는 것과 픽셀 배열을 복사하는 것도 구별해야 합니다. 먼저 실제 바이트 수를 계산합시다.

직접 계산: 한 프레임과 초당 데이터

Gray88192×8192Gray8 8192×8192: 64 MiB/장, 60장/초라면 3.75 GiB/초.

64 MiB를 초당 60번 옮기면 3.75 GiB/초입니다. 두 번 복사하면 데이터 이동량은 더 늘어납니다. 압축 PNG 파일 크기가 5 MB라고 풀린 픽셀도 5 MB인 것은 아닙니다. 가로 24,576×24,576 × 세로 131,072 Gray16의 단순 배열은 6 GiB이므로 타일로 필요한 부분만 읽어야 합니다.

단위를 따라가면 복사 비용이 보입니다

  1. 8192×8192=67,108,8648192×8192 = 67,108,864픽셀입니다. ‘8K’라는 이름 대신 가로와 세로를 모두 적습니다.
  2. Gray8은 픽셀마다 1바이트이므로 같은 수의 바이트입니다.1MiB=1,048,576. 1 MiB=1,048,576바이트로 나누면 64 MiB/장입니다.
  3. 초당 60장이라면 64×60=3840MiB/64×60=3840 MiB/초이고, 1024로 나누면 3.75 GiB/초입니다.
  4. 같은 전체 프레임을 두 번 복사한다면 복사하는 데이터 크기의 합은 7.5 GiB/초입니다. 이 숫자에는 복사에 따른 실제 메모리 읽기·쓰기 트래픽이나 다른 작업을 모두 계산한 것이 아닙니다.

압축 파일의 바이트 수와 디코드된 픽셀 바이트 수는 다릅니다. 가로 24,576×24,576×세로 131,072 Gray16의 단순 배열은 6 GiB입니다. 모든 픽셀을 매번 다루지 않고 필요한 조각을 읽는 타일링으로 이어지는 이유입니다. 이 산술만으로 실제 FPS나 장치 전송 속도를 보장할 수는 없습니다.

실제 코드에서 찾기

TileSource.cs의 PixelKind → ImageInfo → PixelBuffer 순서로 읽습니다. 영상 규격, 타일 읽기 계약, 빌린 배열의 수명이 서로 어떻게 다른지 찾으세요.

아래 코드를 펼치면 먼저 생성자만 읽으세요. Width와 Height는 가로·세로의 픽셀 수입니다. Stride는 한 줄의 바이트 수, Length는 전체의 바이트 수입니다. 이름 옆에 단위를 적으면 무엇끼리 곱하는지 이해하기 쉽습니다.

다음에는 Rent와 Dispose를 짝으로 찾으세요. Rent는 배열을 빌리고, Dispose는 다 쓴 배열을 반환합니다. 빌린 동안 사용할 책임과 다 쓴 뒤 반환할 책임을 이 PixelBuffer 객체가 맡습니다. 아래 짧은 예제에서는 속성 선언을 생략했습니다.

public PixelBuffer(int width, int height, PixelKind kind)
{
    if (width <= 0 || height <= 0)
    {
        throw new ArgumentOutOfRangeException(nameof(width));
    }

    Width = width;
    Height = height;
    Kind = kind;
    Stride = checked(width * (kind == PixelKind.Gray8 ? 1 : kind == PixelKind.Gray16 ? 2 : 4));
    _buffer = ArrayPool<byte>.Shared.Rent(Length);
}

public void Dispose()
{
    var owned = Interlocked.Exchange(ref _buffer, null);
    if (owned is not null)
    {
        ArrayPool<byte>.Shared.Return(owned);
    }
}

using System.Buffers;

namespace VisionImaging.Abstractions;

public enum PixelKind
{
    Gray8, Gray16, Rgba32, Bgra32
}
public readonly record struct TileKey(int Level, int X, int Y);
public sealed record ImageInfo(string Key, string Name, int Width, int Height, PixelKind Pixels, int Levels)
{
    public const int TileSize = 512;

    public int BytesPerPixel => Pixels switch { PixelKind.Gray8 => 1, PixelKind.Gray16 => 2, _ => 4 };

    public static int CalculateLevelCount(int width, int height)
    {
        var count = 1;
        while (Math.Max(width, height) > TileSize)
        {
            width = (width + 1) / 2;
            height = (height + 1) / 2;
            count++;
        }
        return count;
    }
}

/// <summary>A source is owned by the image worker. Reads and disposal must not overlap.</summary>
public interface ITileSource : IDisposable
{
    ImageInfo Info
    {
        get;
    }
    PixelBuffer Read(TileKey key, CancellationToken cancellationToken);
}

/// <summary>One owner transfers or disposes this lease. GPU upload copies before releasing it.</summary>
public sealed class PixelBuffer : IDisposable
{
    private byte[]? _buffer;

    public int Width
    {
        get;
    }

    public int Height
    {
        get;
    }

    public int Stride
    {
        get;
    }

    public PixelKind Kind
    {
        get;
    }

    public int Length => checked(Stride * Height);

    public byte[] Bytes => _buffer ?? throw new ObjectDisposedException(nameof(PixelBuffer));

    public Span<byte> Span => Bytes.AsSpan(0, Length);

    public PixelBuffer(int width, int height, PixelKind kind)
    {
        if (width <= 0 || height <= 0)
        {
            throw new ArgumentOutOfRangeException(nameof(width));
        }

        Width = width;
        Height = height;
        Kind = kind;
        Stride = checked(width * (kind == PixelKind.Gray8 ? 1 : kind == PixelKind.Gray16 ? 2 : 4));
        _buffer = ArrayPool<byte>.Shared.Rent(Length);
    }

    public void Dispose()
    {
        var owned = Interlocked.Exchange(ref _buffer, null);
        if (owned is not null)
        {
            ArrayPool<byte>.Shared.Return(owned);
        }
    }
}

직접 확인: 100×50Gray16,stride=208100×50 Gray16, stride=208의 버퍼 크기와 (3,2) 주소는?

크기는 208×50=10,400bytes208×50 = 10,400 bytes, 주소는 2×208+3×2=4222×208+3×2 = 422입니다. 최소 행 크기 200과 실제 stride 208의 차이 8은 padding입니다. 16bit 값은 주소 422부터 두 바이트를 읽어야 합니다.

더 알아보기 · 픽셀을 실제 길이로 바꾸기

공간 해상도와 실제 길이

사진을 두 배 크게 보여 줘도 새로 촬영한 것은 아닙니다. 원본의 같은 숫자를 더 큰 화면 영역에 그린 것입니다. 실제 길이를 재려면 픽셀과 mm 사이의 관계를 따로 알아야 합니다.

평평한 물체의 100 mm가 사진에서 2,000픽셀을 차지한다고 합시다. 100 mm를 2,000칸으로 나누면 한 칸은 0.05 mm입니다. 같은 조건에서 10칸은 0.5 mm입니다. 하지만 렌즈 왜곡, 원근, 물체 높이가 달라지면 이 비율도 달라질 수 있습니다. 이런 차이를 확인하고 맞추는 과정이 보정입니다. 보정 없이 Canvas의 픽셀 좌표를 mm라고 부르지 않습니다.

가느다란 검정·흰색 줄무늬를 한 칸씩 건너뛰며 읽어 보세요. 검정 칸만 고르면 원래 줄무늬가 온통 검정인 것처럼 보일 수 있습니다. 이렇게 듬성듬성 읽어서 다른 무늬로 보이는 현상을 에일리어싱(aliasing)이라고 합니다. 줄무늬 한 주기에서 2개보다 적게 읽으면 원래 반복을 구별하지 못하는 경우가 생깁니다. 3장에서는 축소하기 전에 이웃 값을 섞는 이유를 숫자로 확인합니다.

책을 덮고, 동료에게 설명해 보세요

먼저 짧은 문제를 자기 말로 설명한 뒤, 아래 종합 문제로 넘어가세요. 계산 결과만 말하지 말고 왜 그 수를 사용했는지 한 문장을 붙여 보세요.

작은 확인: Gray16의 한 픽셀과 한 줄을 같은 단위로 설명할 수 있나요?

한 픽셀은 2바이트입니다. 가로가 3픽셀이면 유효 픽셀은 한 줄에 6바이트를 씁니다. 만약 외부 입력의 stride가 8바이트라면 다음 줄로 갈 때는 빈칸까지 포함해 8바이트를 건너뜁니다. 친구에게 “왜 3도 6도 아닌 8을 건너뛰는지” 말해 보세요. stride는 다음 행 시작까지의 거리라는 설명이 들어가면 됩니다.

설명할 상황: 너비 3, 높이 2인 Gray8 외부 영상의 stride가 4입니다. 동료가 “픽셀은 여섯 개니까 배열도 여섯 바이트면 되죠?”라고 묻습니다. 행 끝 빈칸까지 포함한 저장 공간과 (2,1)의 주소를 설명하세요.

설명 예시와 스스로 확인할 기준

“한 행은 픽셀 3바이트에 빈칸 1바이트가 붙어서 4바이트야. 두 행은 8바이트가 필요해. (2,1)은 한 행 4바이트와 두 칸 2바이트를 건너뛴 인덱스 6이야. 유효 픽셀 수 6과 저장 공간 8은 달라.”

숫자 8과 6을 맞혔는지, 왜 곱셈 두 번과 덧셈 한 번인지 설명했는지 확인합니다.

막혔다면: ‘주소 수식을 두 번의 이동으로 풀기’에서 배열을 종이에 그리고 padding 칸을 표시하세요. 다시 읽은 뒤 예시를 닫고 한 번 더 설명합니다.
