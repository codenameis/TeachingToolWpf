01. 이미지는 숫자다

빛 → 센서 → 픽셀 → 메모리

사진 한 장을 배열로 생각하기

카메라는 빛을 센서에서 전기 신호로 바꿉니다. 노출 시간은 빛을 모으는 시간이고, 게인은 신호를 키우는 정도입니다. 게인을 올리면 잡음도 커질 수 있습니다. 초점이 맞지 않거나 움직임 때문에 번진 경계는 프로그램이 읽기도 전에 정보가 줄어든 상태입니다. 조명·렌즈·노출을 안정화하는 것이 영상처리의 첫 단계입니다.

픽셀(pixel)은 격자의 한 칸입니다. Gray8 영상은 칸마다 0~255의 정수를 저장합니다. 0은 어둡고 255는 밝습니다. 예를 들어 아래 3×3 영상의 가운데가 밝다는 것은 배열의 가운데 값이 크다는 뜻입니다.

I=[1010101020010101010]영상 I = [10,10,10; 10,200,10; 10,10,10]

좌표의 시작은 왼쪽 위 (0, 0)입니다. x는 오른쪽, y는 아래로 증가합니다. 너비 W, 높이 H이면 정수 픽셀 인덱스는 0≤x<W0 ≤ x < W, 0≤y<H0 ≤ y < H입니다. 기하 계산에서 이 픽셀의 중심을 사용할 때는 보통 (x+0.5,y+0.5)(x + 0.5, y + 0.5)로 봅니다. 픽셀 인덱스와 연속 좌표를 섞으면 반 픽셀 어긋남이 생깁니다.

비트 수·채널 수·배열 길이

형식픽셀당 저장량의미
Gray81 byte2⁸ = 256단계
Gray162 bytes2¹⁶ = 65,536단계의 저장 공간
RGBA32 / BGRA324 bytes색 3채널 + 알파 1채널. 채널 순서를 구별

센서가 12bit 값을 16bit 공간에 담을 수도 있습니다. 저장 형식이 Gray16이라고 실제 센서 정밀도가 16bit라는 뜻은 아닙니다. endian(바이트 순서), 유효 비트 위치, 흑백 기준은 입력 계약에서 확인합니다. 화면에서 보기 좋게 밝기를 늘리는 작업과 검사 원본값은 분리합니다.

최소 행 바이트=W×B버퍼 바이트=stride×H픽셀 시작 위치=y×stride+x×B최소 행 바이트 = W × B; 버퍼 바이트 = stride × H; 픽셀 시작 위치 = y × stride + x × B

W는 너비(px), H는 높이(px), B는 픽셀당 바이트입니다. stride는 다음 행까지 이동하는 바이트 수입니다. 외부 영상은 행 끝에 정렬용 빈칸이 붙을 수 있으므로 항상 W×B라고 가정하면 안 됩니다. 현재 PixelBuffer는 빈칸 없는 stride를 생성하지만 GPU 업로드의 행 배치는 별도로 계산합니다.

// 너비 3, Gray8, 외부 버퍼 stride 4인 예: 마지막 칸은 padding
// [11, 22, 33, X, 44, 55, 66, X]
int offset = 1 * 4 + 2 * 1; // (2, 1)의 위치는 6
// buffer[6] == 66

ArrayPool은 요청보다 큰 배열을 빌려줄 수 있습니다. 유효 픽셀은 Length/Span으로 제한하며 배열 전체 길이의 마지막까지 영상이라고 읽지 않습니다. 곱셈에는 checked를 써서 정수 오버플로가 작은 양수로 변하는 일을 막습니다.

8K가 왜 부담이 되는가

‘8K’는 정확한 가로·세로 조합을 대신하지 못합니다. 이 저장소 샘플의 8192×8192 Gray8은 67,108,864 bytes = 64 MiB입니다. 같은 크기의 BGRA32는 256 MiB입니다. 아래는 한 장 전체를 매번 복사한다고 가정한 산술량이며 실제 카메라 FPS나 버스 속도 보장이 아닙니다.

직접 계산: 한 프레임과 초당 데이터

Gray8 8192×8192: 64 MiB/장, 60장/초라면 3.75 GiB/초.

64 MiB를 초당 60번 옮기면 3.75 GiB/초입니다. 두 번 복사하면 데이터 이동량은 더 늘어납니다. 압축 PNG 파일 크기가 5 MB라고 풀린 픽셀도 5 MB인 것은 아닙니다. 가로 24,576 × 세로 131,072 Gray16의 단순 배열은 6 GiB이므로 타일로 필요한 부분만 읽어야 합니다.

공간 해상도와 실제 길이

화면 확대는 새 센서 정보를 만들지 않습니다. 물체 100 mm가 영상에서 2,000 px라면 단순 평면 예제에서 0.05 mm/px입니다. 10px 차이는 0.5mm입니다. 실제 측정에서는 렌즈 왜곡, 원근, 보정판, 물체 높이 때문에 위치별 비율이 달라질 수 있습니다. 이 Canvas의 px 좌표를 보정 없이 mm로 부르면 안 됩니다.

너무 작은 반복 무늬를 듬성듬성 읽으면 다른 무늬처럼 보이는 현상을 aliasing(에일리어싱)이라고 합니다. 줄무늬 한 주기에 2개보다 적은 샘플로는 원래 반복을 구분할 수 없는 경우가 생깁니다. 축소 전에 이웃을 평균하는 이유를 3장에서 계산합니다.

실제 코드에서 찾기

TileSource.cs의 PixelKind → ImageInfo → PixelBuffer 순서로 읽습니다. 영상 규격, 타일 읽기 계약, 빌린 배열의 수명이 서로 어떻게 다른지 찾으세요.

아래 생성자에서 Width/Height는 픽셀, Stride/Length는 바이트입니다. checked는 계산이 int 범위를 넘을 때 잘못된 작은 배열을 만들지 않도록 실패시킵니다. Rent로 빌린 배열은 Dispose에서 한 번 반환합니다. 속성 선언은 생략한 발췌입니다.

PixelBuffer: 크기 계산과 배열 반환

현재 저장소 코드 · 발췌 · src/VisionImaging.Abstractions/TileSource.cs

public PixelBuffer(int width, int height, PixelKind kind)
{
    if (width <= 0 || height <= 0)
    {
        throw new ArgumentOutOfRangeException(nameof(width));
    }

    Width = width;
    Height = height;
    Kind = kind;
    Stride = checked(width * (kind == PixelKind.Gray8 ? 1 : kind == PixelKind.Gray16 ? 2 : 4));
    _buffer = ArrayPool<byte>.Shared.Rent(Length);
}

public void Dispose()
{
    var owned = Interlocked.Exchange(ref _buffer, null);
    if (owned is not null)
    {
        ArrayPool<byte>.Shared.Return(owned);
    }
}
직접 확인: 100×50 Gray16, stride=208의 버퍼 크기와 (3,2) 주소는?

크기는 208×50 = 10,400 bytes, 주소는 2×208+3×2 = 422입니다. 최소 행 크기 200과 실제 stride 208의 차이 8은 padding입니다. 16bit 값은 주소 422부터 두 바이트를 읽어야 합니다.
