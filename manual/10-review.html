10. 리뷰·디버깅·성능

빠르다는 느낌 대신 증거를 남기는 법

신입의 첫 코드 리뷰는 네 가지 질문

  1. 입력: 단위, 범위, null, 이미지 세대는 무엇인가?
  2. 출력: 문서를 바꾸는가, 값을 계산하는가, 소유권을 넘기는가?
  3. 실패: 취소·오류·오래된 결과에서 무엇을 보존하고 누가 버퍼를 반환하는가?
  4. 비용: 이 코드가 프레임마다, 픽셀마다, 편집 한 번마다 몇 번 실행되는가?

모르는 함수가 나오면 호출자 하나와 피호출자 하나씩만 내려가 읽습니다. ‘전체 구조를 이해할 때까지 아무것도 리뷰 못 한다’고 생각하지 마세요. 반대로 의미를 모르는 최적화를 보기 좋다는 이유로 제거하지 않습니다.

실제 리팩터링 예: 이름으로 단위를 드러내기

// 이전: x1이 픽셀인가, 타일인가, 포함 끝인가?
var x1 = Math.Clamp((int)Math.Ceiling(last.X / tileSpan), 0, columns);

// 이후: 원본 좌표에서 계산한 타일 열의 제외 끝
var columnEnd = Math.Clamp(
    (int)Math.Ceiling(imageBottomRight.X / tileSpanInImage), 0, columnCount);

계산 순서·자료구조·반올림·메모리 할당은 같습니다. 새 추상화 없이 의도를 전달합니다. 이름만 바꿀 때는 IDE 심볼 Rename으로 참조를 함께 바꾸고 XAML·리플렉션·직렬화 문자열 영향도 확인합니다. 수식의 연산 순서를 바꾸면 부동소수점 반올림 결과가 달라질 수 있으므로 이름 정리와 수학적 변형을 구별합니다.

작은 LINQ 식을 풀어 쓴다고 무조건 빨라지거나 쉬워지는 것은 아닙니다. 지연 열거를 배열로 바꾸면 메모리를 더 쓰며, 매 프레임 객체를 생성하는 래퍼는 GC를 늘릴 수 있습니다. 읽기 쉬운 코드의 기준은 줄 수가 아니라 독자가 확인해야 할 숨은 전제가 적은가입니다.

시간을 어떤 구간에서 쟀는가

60 FPS의 프레임 예산=1000 ms60≈16.67 ms60 FPS의 프레임 예산 = 1000 ms / 60 ≈ 16.67 ms

작업 전체가 200ms 걸려도 작업 스레드에서 진행하면서 화면은 60FPS일 수 있습니다. 반대로 총시간이 30ms로 짧아도 UI를 한 번에 30ms 막으면 프레임 예산을 넘습니다. 프레임 간격, CPU 작업 시간, GPU 시간, 입력 대기, 표시 완료는 따로 측정합니다.

지표읽는 방법
평균전반적 비용. 드문 긴 멈춤을 숨길 수 있음
p95정렬된 측정값 중 약 95%가 이 값 이하. 최댓값은 아님
최대·예산 초과 개수엄격한 모든 프레임 조건을 확인
할당량·GC pause임시 객체와 수집 때문에 끊기는지 확인
입력 장면 경과렌더 시작 시 장면이 얼마나 오래되었나. 물리 입력→픽셀 지연과 다름
드롭최신 영상 표시 큐에서 버린 프레임. ROI 편집 누락과는 다름

정적 화면에서 렌더를 생략한 시간과 연속 입력 중 프레임이 빠진 시간도 분리합니다. 평균 60FPS 근처라는 이유로 모든 간격 ≤16.67ms를 통과했다고 기록하지 않습니다.

작은 변경의 검증 명령

# 관련 회귀를 빌드한 뒤 실행
dotnet build TeachingToolWpf.slnx -c Release --no-restore -m:1
dotnet test tests/TeachingToolWpf.Core.Tests -c Release --no-build
dotnet test tests/VisionCanvas.Tests -c Release --no-build
dotnet test tests/TeachingToolWpf.Imaging.Tests -c Release --no-build
pwsh -File scripts/Format-Code.ps1 -Verify

Core는 기하·선택·계층·이력, Canvas는 타일·소유권·GPU 전달, Imaging.Tests는 앱 입력·표시 연결을 봅니다. 테스트 이름에 Imaging이 있어도 순수 파일 디코드만 검사하는 것은 아닙니다. 해당 동작과 무관한 모든 테스트를 반복하는 대신 영향 범위를 설명합니다.

성능은 Release, 같은 입력·장치·해상도·빌드, 워밍업과 반복을 구별해 비교합니다. 최초 JIT·장치 준비도 사용자가 기다린 시간에는 포함됩니다. 반복 성능에서 따로 보고하더라도 전체 지연에서 숨기지 않습니다. GPU/WARP를 섞어 비교하거나 합성 영상을 현장 정확도 근거로 쓰지 않습니다.

제출 전에 직접 읽는 체크리스트

  • 입력·출력·오류·취소 계약을 설명했다.
  • 변경 이유에 맞는 책임에 코드를 두었다. SOLID 5개·GRASP 9개를 검토했다.
  • 공개 API·버퍼 레이아웃·평가 순서·이력 원자성이 보존된다.
  • 기존 사용자 변경을 덮어쓰지 않았다.
  • 정확성 검증과 성능 검증을 구별했다.
  • PASS / FAIL / NOT_RUN / BLOCKED를 증거와 함께 기록했다.
직접 확인: 테스트가 모두 통과했으면 60FPS라고 적어도 될까?

아닙니다. 정확성 테스트는 그 입력에서 기능이 맞다는 증거입니다. 프레임 간격·입력 부하·하드웨어·해상도를 포함한 측정이 없으면 성능은 NOT_RUN입니다. 측정해 미달이면 FAIL로 남깁니다.
