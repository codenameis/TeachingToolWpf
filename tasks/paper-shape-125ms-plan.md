# 논문 기반 형상 매칭 — CPU 125 ms / CUDA 80 ms 미만 재계획

작성일: 2026-10-05. 상태: 사용자 실행 요청에 따라 입력·논문 후보 계산·결과 표시를 일부 구현하고 실측했다. **CPU125/CUDA80 ms 수용은 FAIL, 구현 전체는 미완료다.** [구현 실측과 남은 병목](../docs/paper-shape-125ms-validation.md), [작업 목록](todo.md), [ADR-027](../docs/decisions/0027-paper-shape-end-to-end-latency.md)을 따른다. 아래 소스 조사·과거 baseline은 변경 전 이력이며 현재 실행 분기는 구현 기록을 우선한다.

## 1. 이번 요구와 수정 범위

- **논문 기반 형상 방식만 개선한다.** CPU를 먼저 해결하고 같은 방식의 CUDA를 개선한다. OpenCV NCC와 자체 기하 방식의 모델·점수·설정·실행 동작은 보존한다.
- **검사 실행을 누른 뒤 모든 대상의 탐색·원본 검증·판정·결과 게시·표시 완료까지 CPU 125 ms 이하, CUDA 80 ms 미만**이 목표다. 125 ms에 검색을 중단하거나 일부 결과만 먼저 보여주는 것은 성공이 아니다.
- 기존 [500 ms 계획](shape-500ms-plan.md)의 논문 방식 목표를 대체한다. 기존 실측과 실패 이력, 자체 기하 방식의 미완료 작업은 삭제하지 않는다.
- 사용자 제공 MIL CUDA / GTX 1070의 80 ms 미만은 비교 목표다. 현재 장비는 Ryzen 5 5600H와 RTX 3060 Laptop 6 GB다. 서로 다른 입력·옵션·시간 경계 또는 GPU 이름만으로 우열이나 달성 가능성을 확정하지 않는다.
- 구현 가능성은 실측으로 판정한다. C#·전통적 매칭·원본 검사·플랫폼 경계·클린 코드·SOLID·GRASP를 유지한다. 딥러닝, 상용 SDK 도입, 다른 매칭 방식으로 교체는 이번 계획에 넣지 않는다.

## 2. 소스에서 확인한 현재 구조

`Shape_Match`가 `meiqua/shape_based_matching`를 뜻한다면, 현재 코드는 그 원본을 실행하거나 직접 포팅한 것이 아니다. [기존 계획](pattern-matching-plan.md)에 기록한 고정 commit `3df935f8e4b8c8a8ed72984211543e1b7696452e`의 구조·수식과 논문을 참고한 **독립 C# 결합 구현**이다. 참조 저장소의 LINE-MOD/gradient orientation 설명은 [원저자 저장소](https://github.com/meiqua/shape_based_matching/tree/3df935f8e4b8c8a8ed72984211543e1b7696452e)에서 확인했다. 원저자의 작은 영상 실행 수치를 이 앱의 8K 전체 검사 수치로 사용하지 않는다.

현재 흐름:

```text
ShapeMatchingViewModel.SearchAsync
  → ShapeMatchingService.SearchAsync
  → 독립 MatchingImageReader 원본 읽기
  → ShapePyramidSearch / ShapeCoarseSearchScheduler
  → LINE-2D 계열 방향 응답 후보 검색
  → ShapeCandidateRefinement의 후보별 원본 crop
  → ContinuousVerifier / PointToLineRefiner
  → 원본 추가 윤곽 감점 / MatchSuppression
  → 앱 판정·결과 목록·검출 overlay 게시
  → Canvas 결과 렌더·Present
```

크기에 따른 분기도 중요하다. 2 Mpx 초과/모델 3단계 이상은 `ShapePyramidSearch`의 축소 창 스케줄러를 사용하지만, `kensa.png`의 1,572,864 px는 `ShapeMatchingService`의 일반 창 반복문으로 들어간다. 현재 이 분기는 4개 창을 순차 검색한다. 새 논문 전략은 **일반·대용량 두 분기**를 대상으로 해야 하며 8K 스케줄러만 개선해서는 kensa의 지연이 해결되지 않는다.

논문 모드는 `BuildGeometricModel=false`, `BuildClutterModel=true`, `EvaluateGeometry=false`다. 추가 윤곽 감점은 유지한다. 자체 기하 모드와 `ShapeMatchingService`/`ShapeMatcher`를 공유하므로 공통 구현 전체를 교체하면 범위를 넘는다. 앱 조립 지점에서 논문 전용 실행 전략을 선택하고 기존 기하 경로를 보존하는 최소 경계를 먼저 만든다. 공용 저수준 함수 변경이 필요하면 다른 방식의 결과·설정·시간 회귀를 함께 검사한다.

CUDA의 현재 역할은 최고 피라미드 단계의 방향 확산·응답 LUT·템플릿 정수 점수 계산이다. `ShapeMatcher.GetPreprocessor`는 후보 scorer가 있으면 CPU 전처리를 선택한다. 파일 읽기, Gaussian/Sobel·정규화, 후보 추출, 연속 방향 검증, point-to-line, 원본 추가 윤곽 감점, 최종 NMS는 CPU에 남는다. 창별 특징 업로드·전체 점수 격자 다운로드·동기화가 있으며 `SerializedImagePreprocessor`가 장치 호출을 직렬화한다. GPU 모드가 CPU보다 조금만 빠른 현상과 부합하지만 사용자 실행의 병목은 별도 프로파일링으로 확정해야 한다.

## 3. 기존 증거와 새 목표 사이의 차이

아래 값은 [v4 검증 기록](../docs/shape-500ms-validation.md)과 기존 JSON의 **과거 측정**이다. 이번 소스 조사에서 다시 달성한 값이 아니다.

| 조건 | 논문 CPU | 논문 CUDA |
|---|---:|---:|
| 8192² 샘플 서비스 반복 중앙값 | 336.9 ms | 305.6 ms |
| 일반 앱 수동 첫 서비스 표시 | 459.0 ms | 375.0 ms |
| 위 앱 원본 읽기·변환 | 182.3 ms | 185.4 ms |
| 정상 표시 WPF 첫 명령 | 455.7433 ms | 907.6588 ms, 장치 준비 포함 |

- 기존 CUDA 반복 개선 폭은 약 9.3%다. 서비스 중앙값만으로도 CPU 약 2.7배, CUDA 3.8배 이상 단축이 필요하며 새 기준의 표시 비용은 여기에 추가된다.
- 기존 v4 CPU 읽기·변환 반복은 142.8~158.6 ms다. 현재 단일 원본 reader 비용 자체가 125 ms보다 커서 후보 점수 커널만 최적화하는 계획으로는 부족하다.
- 기존 CUDA 후보 계산은 검사당 64회, 전송·대기 포함 반복 누적 약 47.7~56.4 ms다. 이 값과 병렬 worker 진단 합을 전체 wall time 분해처럼 더하지 않는다.
- 별도 Gray8 파일/큰 ROI/CPU4는 과거 약 1.82초, 숨김 WPF 명령은 1.03~2.28초인 실패 기록이 있다. 사용자의 약 2초가 이 사례와 같은 원인인지는 미확정이다. 실제 실행 파일·ROI·옵션을 재현하기 전 구버전 사용이라고 단정하지 않는다.
- 현재 서비스 stopwatch는 `Task.Run` 안에서 시작하며 UI queue, 최초 CUDA 준비, 판정/문자열/overlay 조립·게시·Present를 제외한다. 반환 표현식 뒤 자원 정리도 내부 표시 시간에서 빠질 수 있다. 기존 `TotalMilliseconds`는 새 수용 기준으로 사용하지 않는다.
- `GpuLabelCache.TryGet`은 새 라벨을 프레임당 최대 2개 또는 rasterize 누적 2 ms까지만 준비하고, `ResultOverlayPainter`는 검출별 라벨을 이 지연 경로로 요청한다. `Present(1)`을 사용하므로 화면 내 256개 라벨이 모두 cache miss이고 이 제한이 계속 적용되는 경우 최소 128프레임의 준비가 필요하다(60 Hz 가정 약 2.13초, 코드 기반 추정이며 실측 아님). 처음 보는 번호/점수 라벨의 완료 비용을 측정하고 표시 배치도 개선해야 한다. 이것을 사용자 보고 2초의 확정 원인으로 단정하지 않는다.

## 4. 고정할 입력과 정답

### A. 실제 8K 앱 샘플

- `sample:8192:8192`, 전체 이미지 검색. 핀 ROI 중심 `(759.518,546.178)`, 크기 `105.827×129.459`, 각도 0.
- 기존 정답 256개 모두 일대일 검출, 누락·중복·미할당 0, 위치 오차 1 px 이하.
- 회전 편차 ±180°, 학습 간격 10°, 배율 1, 최소 점수 .72, 지지 .6, 추가 윤곽 비중 1. 후보 2048/원본 검증 64/거친 검증 256/출력 256과 기존 학습 기본값을 고정한다.
- 독립 위치 정답으로 구별한 사선 64핀/깨끗한 192핀의 점수 간격 .02 이상을 유지한다. 점수로 정답 그룹을 역으로 정의하지 않는다.

### B. 사용자 지정 `kensa.png`

- 실제 파일 크기는 **1024×1536**, 2,440,112 byte다. 8K 파일로 표현하지 않는다.
- SHA256: `7EEED204BFE88C79F285D4F0AE195F954880984C58F59282B501965080846E77`.
- 초기 학습 대상은 좌상단 보드의 좌상단 검정 메모리 칩이다. 사각 ROI 초안은 원본 좌표 left 156 / top 158 / width 89 / height 52 / angle 0이다. 이미지 직접 확인으로 지정했으며 학습·원본 overlay 확인 후 recipe에 확정한다.
- 12개 보드에 각 4개씩 **육안상 48개**가 예상된다. matcher 결과에서 정답을 만들지 않고 독립적으로 48개의 중심·경계 annotation을 확인한다. 확정 전에는 48개 완전 검출 PASS를 주장하지 않는다.
- 기본 시험은 A와 같은 회전·배율·점수 조건에서 전체 이미지 검색한다. 실제 부품의 명암·글자·미세 위치 차이를 포함한다. 검출 실패를 숨기려고 ROI/임계값/회전 범위를 반복 조정해 성공한 경우만 보고하지 않는다. 필요한 개선과 모델 조건 변경은 별도 실험으로 기록한다.
- 원본의 정확성·시간 시험을 보존한다. 추후 8K 확대/타일 복제 시험을 추가하면 파생 합성 입력으로 명시하며 실제 8K 촬영 자료로 부르지 않는다.

두 fixture의 초기 CPU/CUDA 실행은 **현재 상태 재현용 baseline**이다. CLI 결과는 알고리즘/서비스 증거이며 버튼부터 표시까지의 성능 PASS를 대신하지 않는다. 실행 도구의 DLL이 v4와 다르면 출처와 해시를 별도로 기록한다.

### 이번 계획 중 실행한 kensa baseline

기존 Release CLI로 논문 방식만 CPU/CUDA 각각 독립 프로세스 4회 실행했다. 구현 변경·재빌드는 하지 않았다. [재현 명령·시간 경계·해시 설명](../artifacts/paper-125ms-baseline-20261005/README.md)과 [원시 증거 ZIP](../docs/data/paper-125ms-baseline-20261005.zip)을 보관한다.

| 모드 | 첫 검색 | 후속 독립 프로세스 3회 중앙값 / 최대 | 4회 모두의 결과 |
|---|---:|---:|---|
| 논문 CPU12 | 1906.5 ms | 1509.1 / 1614.7 ms | 44개, incomplete, exit 2 |
| 논문 CUDA | 3323.3 ms | 2009.4 / 2112.5 ms | 44개, incomplete, exit 2 |

- 4개 창 중 후보 예산 초과 3개, 검증 예산 초과 1개이며 출력 상한 초과가 아니다. 8회의 공개 matches는 정확히 같다. GPU 후보 계산은 4회 약 20~21 ms뿐이다.
- 48개 예상 정답과 44개의 일대일 대응은 아직 검증하지 않았다. 44개라는 수와 불완전 상태를 모두 보존하며 누락의 정확한 원인은 annotation·후보 단계 추적으로 확정한다.
- CLI는 매회 모델·장치가 새로 준비되므로 뒤 3회도 같은 세션의 warm 반복이 아니다. GPU 검색 시간에 최초 CUDA 준비가 포함된다. CPU/GPU의 steady-state 속도 비교나 버튼→화면 시간으로 사용하지 않는다.
- 이 CLI와 과거 v4 게시물의 DLL 해시가 다르며 현재 소스와 CLI build의 완전 일치도 미검증이다. 이를 현재 소스의 확정 성능이나 v4 대비 퇴보라고 단정하지 않는다. 다음 구현의 baseline은 소스/게시물 해시를 다시 일치시킨다.
- 8K 샘플도 아래처럼 기존 v4 benchmark로 재실행했다. 이 도구는 두 형상 방식을 함께 실행하므로 원본 전체를 보존하고 보고에는 논문 행만 사용한다. 다른 방식의 구현은 변경하지 않았다. 다음 P0에서 논문 전용 선택을 추가하면 불필요한 비교 실행 없이 A/B를 같은 build로 반복할 수 있다.

**속도와 불완전 검색을 함께 해결한다.** 현재 44개 결과를 유지하는 것 자체가 정확성 목표가 아니다. 후보 분산·중복 pose 처리·검증 순서/예산 진단을 통해 실제 정답을 복원하고, 새 결과의 CPU/CUDA 동등성과 원본 점수 계약을 검증한다. 필요하다면 후보 예산 확대를 명시적으로 비교하되 그 비용까지 포함해 125/80 ms를 판정한다. 경고만 지우거나 누락 결과를 baseline과 같다는 이유로 합격시키지 않는다.

### 이번 계획 중 실행한 8K 샘플 baseline

기존 v4 게시물의 DLL을 바꾸지 않고 benchmark를 재실행했다. 원본은 증거 ZIP의 `sample-v4-fresh-full-report.json`, 논문 행은 `sample-paper-v4-fresh-report.json`이다. 같은 세션에서 첫 검사와 반복 3회를 구별했다.

| 모드 | 첫 서비스 wall time | 반복3회 중앙값 / 최대 | 논문4회 모두의 결과 |
|---|---:|---:|---|
| 논문 CPU12 | 479.3 ms | 340.3 / 350.4 ms | 256개 일대일, 누락·중복·잘림 없음 |
| 논문 CUDA | 395.9 ms | 296.9 / 316.4 ms | 256개 일대일, CPU와 정확 동등 |

사선 점수 간격은 .0294648458이다. CUDA 최초 준비 626.3 ms는 위 시간과 별도이며 첫 준비+검색은 1022.1 ms다. 구 500 ms 기준 도구의 exit 0은 **새 CPU125/CUDA80 기준의 PASS가 아니다**. 화면 없는 서비스 측정이므로 버튼→표시 완료 증거도 아니다. kensa CLI와 sample v4는 서로 다른 binary이므로 두 수치를 동일 구현의 입력 크기별 성능으로 비교하지 않는다. A/B 모두 현재 새 목표 미달이다.

## 5. 시간을 재는 시작과 끝

전제는 이미지 열기와 모델 학습이 완료된 상태다. 이와 별개로 **검사에 필요한 원본 읽기·명암 변환·피라미드·전처리·탐색·최종 검증을 클릭 이전으로 옮겨 시간을 숨기지 않는다.** 이전 검사 결과를 재사용해 재검사로 표시하지 않는다.

| 시점 | 계측 경계 |
|---|---|
| T0 | 실제 검사 버튼 입력을 앱이 수신한 시점. 키보드/명령 진입도 동일 실행 ID와 연결 |
| T1 | 실행 요청 검증·대기 종료, worker 시작 |
| T2 | 원본 reader/해당 프레임 획득과 필요한 읽기·변환 |
| T3 | 전처리·후보 검색·원본 정밀화·감점·NMS 완료 |
| T4 | worker 종료와 검사별 자원 반환, 현재 실행 ID/소스/모델 검증, 판정·결과 목록·overlay 게시 완료 |
| T5 | 같은 실행 결과의 화면 내 필수 윤곽·라벨이 준비된 DX12 프레임 렌더 완료/Present와 WPF 결과 표시 갱신, 명령 유휴 복귀 중 가장 늦은 시점 |

수용 시간은 **T5−T0**다. 병렬로 겹치는 구간은 실행 trace로 분석하고 누적 CPU 시간을 직렬 단계처럼 더하지 않는다. T3−T1 같은 내부 시간은 보조 진단이다. T5까지 후속 라벨 생성이 남아 있으면 완료가 아니다. 화면 밖 결과는 전체 목록/데이터로 완성되어야 하며 사용자 화면에 보일 필요 없는 픽셀까지 강제로 그리는 것은 아니다.

Canvas에는 검사 공급자나 판정 정책을 넣지 않는다. 기존 불변 장면 revision과 연결된 공급자 비의존 표시 완료 통지를 사용하고, 앱이 이를 run ID에 대응시킨다. `ResultOverlayPainter`의 지연 라벨과 `RenderWorker`의 frame 제출/완료를 구분한다. Present 호출 반환은 물리 모니터 scan-out과 동일하지 않으므로 renderer 완료·Present 계측 한계를 공개하고 필요하면 별도 표시 trace로 검증한다.

현재 `Dx12Surface.Present()`의 fence Signal은 해당 프레임 GPU 완료 대기와 다르다. P1b는 필요한 라벨 준비·그 결과 프레임의 GPU fence 완료·Present 제출·WPF 갱신을 각각 기록한다. UI 동기 대기 없이 완료를 통지하고 정지 화면의 다음 프레임을 기다리느라 완료 통지가 늦어지지 않게 한다. 앱에서 source generation/run ID와 결과 overlay identity를 검증하며 장면 revision이 더 크다는 이유만으로 취소/교체된 결과를 완료 처리하지 않는다.

WPF의 `PropertyChanged`나 Dispatcher callback 반환만으로 목록 표시 완료를 판정하지 않는다. P1b에서 해당 결과 revision의 layout/render 반영을 관측하는 지점과 한계를 확정한다. 공통 라벨 정책을 일괄 완화하는 대신 결과용 숫자/glyph atlas 또는 공급자 비의존 배치 텍스트 준비를 검토하고, 논문 결과에서 먼저 사용한다. 번호·점수·판정색·기존 표시를 생략하지 않으며 다른 방식과 일반 ROI 라벨 정책의 회귀를 확인한다. glyph의 불변 준비는 가능하지만 현재 검사 결과 라벨 조립/업로드 비용은 T0 이후에 포함한다.

장치·커널 및 모델 불변 자료는 앱 시작/모드 선택/학습에서 명시적으로 준비할 수 있다. 준비 상태와 소요 시간은 공개한다. 준비 전 클릭을 허용해 클릭 이후 JIT·CUDA 초기화가 발생하면 **전부 T5−T0에 포함**하며 첫 클릭 실패를 warm 결과로 덮지 않는다. 이미지별 실제 검사 작업을 준비 단계로 전가하지 않는다. 준비 완료 이후 첫 검사와 반복 검사도 따로 측정한다.

검사 시간 제한을 125/80 ms로 줄이는 수정, 결과 잘림, 임계값 상승, 특징 삭제, 회전·배율 범위 축소는 목표 달성으로 인정하지 않는다.

## 7. 정확성·메모리·수명 계약

- 전체 검색은 이미지 전체를 대상으로 같은 학습 모델의 모든 정답 인스턴스를 찾는 뜻이다. A/B 완전 검출을 임의의 모든 영상·모든 ROI/각도/배율에 대한 보장으로 확대하지 않는다. 큰 ROI·회전·배율·잡음·가림·저대비·타일 경계의 기존 회귀를 유지한다.
- 정답 개수뿐 아니라 일대일 대응, pose, 방향 점수, 원본 추가 윤곽 에너지/감점, 지지, 판정, 실제 ROI 검출 경계와 CPU/GPU 동등성을 확인한다. 합격 허용 오차는 실행 전에 고정하고 실패 후 완화하지 않는다.
- 정답 pose의 허용 오차와 CPU/CUDA 수치 동등성은 다르다. 기존 exact pose/score/순서 동등성 회귀를 새 tolerance로 바꾸지 않는다. 불완전 baseline에서 확인된 올바른 결과의 품질과 추가 정답 회복은 따로 검증하며, 기존 44개의 불완전 목록을 정답 oracle로 삼지 않는다.
- 후보의 수학적 동치나 점수 상한을 입증한 경우에만 무손실 계산 생략을 사용한다. 메모리 배치 용량과 총 검색/검증 예산을 구별하고 예산 설정의 의미를 조용히 재해석하지 않는다. 논리창 변경은 국소 최대·ownership·창별 top-k·예산의 의미가 달라질 수 있어 독립 정확성 실험으로 다룬다.
- `Truncated=false`, `MatchLimitExceeded=false`, timeout/cancel/error 없음이 완전 검색 PASS의 전제다. 결과 상한 256이 충분한 A/B에서 먼저 확인하되 더 많은 대상의 테스트는 명시적으로 설정을 올리고 경고 계약을 유지한다.
- 현재 검사별 원본 16 MiB/축소 4 MiB LRU, 거친 활성 영상 2 Mpx, 병렬 crop 합 2 Mpx/단일 crop 최대 8 Mpx를 기본으로 유지한다. native scratch·gradient·GPU buffer·pool 보유량은 별도로 계측한다. LRU 한도를 프로세스 메모리 상한으로 부르지 않는다.
- 검사 간 또는 renderer와 원본 cache를 공유하지 않는다. 새 prepared block은 한 검사 안의 명시적 소유 자료로 제한한다. 전처리 공유 때문에 crop 경계 값이 달라지면 그대로 채택하지 않고 halo/유효영역으로 기존 값을 재현한다.
- 8K 전체 float 응답 평면 상주나 영구 원본 cache는 이번 계획의 기본안이 아니다. 필요한 경우 기존 메모리·수명 계약 변경을 별도 제안하고 총 byte와 무효화·실패 원자성을 먼저 설계한다. 설계 원칙 예외가 불가피할 때만 AGENTS의 명시적 사전 승인 절차를 적용한다.
- CPU는 제한된 worker와 메모리 예산을 함께 사용한다. 입력 owner는 하나다. GPU는 세션 소유 장치와 작업 lease, 제출 작업 완료 후 취소 반환, 오류 장치 재사용 금지, 종료 순서를 보존한다. 오류를 숨기는 CPU fallback은 금지한다.

## 8. 최종 검증과 보고

1. Release, 동일 소스/게시물 DLL SHA256, 실제 CPU/adapter/드라이버/전원/병렬도/입력/recipe를 고정한다. 성능 실행 중 별도 benchmark나 빌드로 장비에 부하를 주지 않는다.
2. fixture A/B 각각 CPU/CUDA의 독립 프로세스 첫 실행 최소 10회와 반복 각 100회를 계획한다. 준비 전/준비 완료 후 첫 실행과 첫 이미지 접근/재접근을 구별한다. 두 모드는 교대 실행한다.
3. T5−T0 원시 표본과 p50/p95/p99/최대를 공개한다. **수용 시리즈에서 단 한 번이라도 CPU 125 ms 초과 또는 CUDA 80 ms 이상이면 해당 항목 FAIL**이다. 평균만 통과로 표시하지 않는다. 일반 데스크톱의 모든 미래 실행을 보장하는 hard real-time 인증으로 표현하지 않는다.
4. 정상 표시 앱의 첫 버튼·반복 버튼, 이미지/모델 변경 후, pan/zoom 직후를 시험한다. 기존 진단의 750 ms 사전 안정화나 숨김 창 결과만으로 대표하지 않는다. 표시 장치 refresh/present 정책도 기록한다.
5. 입력 누락·취소·오류·오래된 결과·출력/후보 한도와 자원 반환 회귀, 논문/기하/OpenCV 간 독립 상태, 큰 ROI·회전·배율·잡음·마스크·점수 회귀를 실행한다. 변경 범위의 집중 테스트 후 최종 관련 suite, Release 빌드, `scripts/Format-Code.ps1 -Verify`를 확인한다.
6. 변경마다 전후 숫자·정확성·유지/폐기 이유를 기록한다. 동일 DLL 해시의 두 실행 차이를 코드 개선 효과로 해석하지 않는다. 이번 계획만으로 성능 PASS를 체크하지 않는다.

| SRP | 입력·모델 준비·후보 계산·원본 검증·장치 수명·UI 완료 계측 분리 |
| OCP | 논문 실행 전략과 중립 backend를 선택적으로 연결, 기존 방식 유지 |
| LSP | CPU/CUDA 결과·오류·취소·buffer 소유·완료 시점 계약 동일 |
| ISP | 후보/배치 검증/표시 완료의 소비자별 작은 계약, 범용 plugin 엔진 금지 |
| DIP | Algorithm/Core에 WPF·CUDA·DX12 참조 없음, 앱/CLI에서 조립 |
| Information Expert | 원본 변환은 영상 어댑터, 수치/점수는 알고리즘, 실제 표시 완료는 renderer |
| Creator | 모델과 장치/작업 buffer를 각각 학습 자산·세션 소유자가 생성/해제 |
| Controller | UI는 실행 요청과 현재 결과 게시, 검색/판정 연산을 컨트롤러에 추가하지 않음 |
| Low Coupling | 불변 crop·모델·결과·revision/lease로 모듈 연결 |
| High Cohesion | I/O 최적화와 matcher 수식, 장치 정책과 앱 판정을 혼합하지 않음 |
| Polymorphism | 실제 논문 CPU/CUDA 실행 변형만 계약으로 분리 |
| Pure Fabrication | 제한된 스케줄러·세션·계측 어댑터에 기술 책임 배치 |
| Indirection | 앱 조립·native 영상 어댑터·CUDA backend·viewport 통지로 외부 API 격리 |
| Protected Variations | 파일 형식·SIMD 지원·장치 변화와 기존 기하/OpenCV 경로를 안정 계약으로 보호 |

현재 설계 원칙 예외는 없다. 성능을 이유로 정확성·검출 범위·Undo/Redo·오류 표시를 조용히 줄이지 않는다.

## 10. 실행 후 checkpoint

P0·논문 전략·선택형 원본 Gray·국소 정수 SIMD·작은 영상 피라미드·라벨 atlas/가상 목록을 구현했다. 8K 256개 결과는 기존과 정확히 같고 kensa는44개/잘림에서48개/잘림 없음으로 개선했다. kensa 한 개는 정밀화 Rejected이므로 기존 CHECK 판정을 유지한다. 두 입력의 서비스 CPU/CUDA 결과는 정확히 일치했다.

서비스 반복 중앙값은 8K CPU261.7/CUDA227.3 ms, kensa CPU168.7/CUDA158.8 ms다. 최초 준비·앱 표시를 포함하면 추가 비용이 있어 C1/C2는 FAIL이다. P1의 명령/renderer/WPF 관측은 구현했지만 물리 입력·DWM 완료까지는 미검증이다. P4의 연속 자세 보정/전처리·UI 잔여 지연, P5 CUDA 범위 확대는 남았다. 전체 수용에 실패한 상태를 구현 완료로 바꾸지 않는다. 자세한 전후·폐기 실험·회귀·재현은 [검증 기록](../docs/paper-shape-125ms-validation.md)에 둔다.
