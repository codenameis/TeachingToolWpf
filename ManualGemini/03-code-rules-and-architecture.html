CHAPTER 03 · CLEAN C# RULES & UML CLASS DIAGRAMS

읽기 좋은 코드 규칙과 클래스·시퀀스 다이어그램

큰 프로젝트를 혼자 또는 팀으로 만들 때 가장 무서운 적은 '스파게티처럼 엉킨 코드'입니다.
누가 읽어도 책처럼 술술 읽히는 Microsoft C# 명명 규칙과 Kent Beck의 짧은 메서드 원칙, 그리고 클래스들이 서로 어떻게 협력하는지 보여주는 UML 클래스·시퀀스 다이어그램을 살펴봅니다.

RULE 1 · NAMING & FORMATTING

1. 이름만 봐도 역할이 보이는 C# 명명 규칙

왜 규칙을 정할까요? 변수 이름이 _rois처럼 밑줄로 시작하면 "아, 이 클래스 안에서만 쓰는 비공개 필드구나!" 하고 위아래를 뒤져보지 않아도 0.1초 만에 알 수 있기 때문입니다.
대상 표기 규칙 실제 코드 예시 이렇게 쓰는 이유
클래스·구조체·메서드·속성 PascalCase EditorSession, ViewportTransform, ZoomAt 외부에 공개되는 계약과 동작을 명확히 드러냅니다.
인터페이스 IPascalCase ITileSource, ICanvasRenderBackend 교체 가능한 추상 부품(플러그인)임을 즉시 알려줍니다.
비공개 인스턴스 필드 _camelCase _history, _document, _hwnd 지역 변수나 매개변수와 절대 헷갈리지 않습니다.
비공개 정적(static) 필드 s_camelCase s_emptyTiles, s_defaultPalette 모든 인스턴스가 공유하는 정적 자원임을 표시합니다.
지역 변수·매개변수 camelCase screenAnchor, newScale, imagePoint 메서드 안에서 잠깐 쓰이는 값임을 구분합니다.
RULE 2 · COMPOSED METHOD

2. 메서드는 왜 20줄 이내로 짧게 나눌까요?

Kent Beck의 조언: "한 메서드 안에서는 같은 추상화 단계의 일만 하세요. 목차 역할을 하는 메서드가 세부 단계 메서드를 차례대로 부르면 주석이 없어도 코드가 문장처럼 읽힙니다."
Composed Method 패턴 예시 (OnPointerMove) 1. 입력 변환 → 2. 미리보기 갱신 → 3. 렌더링 요청 
public void OnPointerMove(PointD screenPoint)
{
    if (!IsEnabled || NavigationOnly)
    {
        return;
    }

    PointD imagePoint = _viewport.ScreenToImage(screenPoint);
    UpdateDragPreviewOrHover(imagePoint);
    RequestFrameRender();
}

UML SEQUENCE DIAGRAM

5. 왜 드래그 도중에는 Undo 기록을 만들지 않을까요?

핵심 아이디어: 마우스를 1초 동안 드래그하면 WM_MOUSEMOVE 신호가 60번 넘게 들어옵니다.
그때마다 문서를 복사하면 메모리가 낭비되고 Ctrl+Z를 60번 눌러야 원래 자리로 돌아갑니다!

그래서 VisionCanvas는 드래그하는 동안에는 가벼운 RoiTransformPreview 값만 바꾸어 화면을 그리고, 마우스 버튼을 놓는 순간(PointerUp) 딱 한 번만 새 DocumentState 스냅샷을 만들어 UndoRedoHistory에 넣습니다.

⏱️ ROI 드래그 이동 및 Undo 스냅샷 커밋 시퀀스 다이어그램
PointerDown → PointerMove (60FPS Preview) → PointerUp (Single Commit)
