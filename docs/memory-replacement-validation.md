# 이미지 반복 교체 메모리 검증 · 2026-10-02

8K/24K 파일 교체와 ROI 필터 처리 조합을 수정 전 120회, 수정 후 120회 및 600회 실행했다. 모두 종료 코드 0이고 렌더 오류가 없었다. **이 시험 범위에서는 지속 증가하는 누수 징후를 발견하지 못했다.** 누수 원인이 확인되지 않아 추측에 근거한 리소스 수명 변경이나 일반 실행 경로의 강제 GC를 추가하지 않았다.

## 재현 조건

- 장비: Ryzen 5 5600H, RAM 32 GB, RTX 3060 Laptop. DXGI 전용 5.9 GiB / 당시 예산 5.1 GiB. Release, .NET 10, DX12 debug layer 활성, 화면 밖 실제 HWND.
- 실제 파일: 7680×4320 RGBA8 PNG와 24576×4096 Gray16 tiled/Deflate TIFF. 가로 계조 패턴을 가진 완성 파일이며 카메라 입력이나 수집/라인 조립 시험이 아니다.
- 한 주기에 두 파일을 차례로 교체하고 매번 2000×1200 / 17° ROI를 생성한 뒤 Binarize 또는 Edge를 처리한다. 소스 교체와 미리보기 완료를 단언하고 렌더링을 기다린다.
- 5주기마다 작업을 안정시킨 뒤 진단 코드에서만 GC/finalizer 완료를 기다리고 Private Bytes, working set, 관리 힙, 핸들, 추정 이력 크기를 기록한다. 워밍업 10주기 이후 같은 24K 소스가 열린 시점을 비교한다. 디스크 피라미드 캐시를 재사용한다.
- 수정 전은 전역 미리보기 설정, 수정 후는 ROI에 등록된 필터를 사용한다. 모든 시험은 이력 기능을 켠 상태이며 수정 후 이력에 필터 등록도 포함된다.

```powershell
.\artifacts\publish\TeachingToolWpf.exe --memory-check --gpu-debug --memory-cycles 300 --memory-report artifacts\memory-replacement.json --metrics artifacts\memory-replacement-frames.csv
```

`--memory-cycles` 기본값은 60이다. 최초 실행은 `artifacts/memory-fixtures`에 두 파일과 `artifacts/image-cache`에 피라미드를 만든다. `--memory-cycles 300`은 600회 교체다. 재현 로그는 실행 디렉터리의 `artifacts`에 생성되며 큰 테스트 이미지/캐시는 Git에 포함하지 않는다.

## 측정 결과

모두 MiB(2²⁰ bytes)이며 아래 범위는 워밍업 10주기 시점부터 마지막까지의 체크포인트다. Private Bytes는 GPU VRAM과 다른 프로세스 지표이며 관리 힙은 강제 수거 후 보유량이다.

| 실행 | 교체 횟수 | Private Bytes 범위 / 마지막 | 관리 힙 범위 / 마지막 | 핸들 범위 / 마지막 |
|---|---:|---:|---:|---:|
| 수정 전 | 120 | 318.25–330.89 / 330.89 | 19.29–22.85 / 22.85 | 1307–1318 / 1318 |
| 수정 후 | 120 | 300.54–307.50 / 307.50 | 21.28–21.86 / 21.86 | 1301–1304 / 1302 |
| 수정 후 반복 확대 | 600 | 295.72–309.05 / 307.48 | 20.78–24.39 / 22.89 | 1290–1316 / 1295 |

600회 실행의 프레임 기록 구간은 약 218.8초다. 중간 체크포인트는 다음과 같다.

| 주기(교체는 2배) | Private MiB | 관리 힙 MiB | 핸들 | 추정 이력 bytes |
|---:|---:|---:|---:|---:|
| 10 | 295.72 | 20.78 | 1314 | 37874 |
| 50 | 301.96 | 21.86 | 1303 | 127482 |
| 100 | 305.60 | 23.37 | 1308 | 127482 |
| 150 | 307.52 | 22.89 | 1299 | 127482 |
| 200 | 307.26 | 22.89 | 1304 | 127482 |
| 250 | 306.82 | 22.89 | 1290 | 127482 |
| 300 | 307.48 | 22.89 | 1295 | 127482 |

초기 보유량 증가 이후 마지막 150주기에서는 Private Bytes가 약 307 MiB, 관리 힙은 약 22.89 MiB에 머물렀다. 이력도 건수 상한에서 추정 127,482 bytes로 유지됐다. 수정 전후 절대값 차이는 별도 프로세스의 할당/캐시 차이를 포함하므로 메모리 최적화 성과로 주장하지 않는다.

원시 체크포인트: [수정 전](../artifacts/memory-before.json), [수정 후](../artifacts/memory-after.json), [600회](../artifacts/memory-long.json). 로컬 측정 산출물이며 publish 스크립트도 존재하는 JSON을 배포 폴더에 복사한다. 프레임 CSV의 `texture_bytes`는 이미지 캐시의 논리 크기만 포함한다. 마지막 값 835,584 bytes를 전체 VRAM 사용량으로 해석하지 않는다.

## 소유권과 한계

자동 회귀 시험에서 타일 큐를 32개로 가득 채운 뒤 소스를 100회 바꾸고 종료했다. 모든 소스는 정확히 한 번 해제되고 큐의 모든 픽셀 버퍼는 접근 시 ObjectDisposedException을 발생시켰다. 필터의 원본 lease, 취소/늦은 결과 폐기 및 등록 이력도 별도 자동 검증을 통과했다.

600회 결과는 약 3.6분의 같은 두 파일 교체 시험이다. 수 시간/10분 이상 지속 부하, 수천 개의 서로 다른 파일, 실제 카메라, 모든 압축/멀티페이지 조합을 검증한 결과가 아니다. native heap/GPU live object 전체 추적은 수행하지 않았으며 OS 파일 매핑 working set, 제한된 버퍼 풀, 드라이버 보유량을 누수와 동일시하지 않는다. 디스크 피라미드 캐시의 자동 용량 정리는 별도 미구현 사항이다.
