# 자체 피라미드·타일 엔진과 NetVips 비교

**후속:** 이 문서의 표는 최초 구현 측정이다. 이후 [메모리·성능 검토](pyramid-memory-review.md)에서 컬러 변환의 반복 native 호출을 제거했고, 독립5회 비교에서 JPEG 준비를1.364초→0.980초로 줄였다. 최초 결과를 덮어쓰지 않고 구별한다.

2026-10-13. 사용자 요청에 따라 별도 [실험 솔루션](../experiments/PyramidComparison.slnx)을 만들고 **OpenCV 디코딩 + 자체 C# 피라미드·raw 캐시·타일 읽기**를 구현했다. 기존 NetVips 파일 경로와 Canvas·검사·ROI 코드는 변경하지 않았다. [재현 명령·설계 검토](../experiments/PyramidComparison/README.md), [측정 값·실행물 SHA256·픽셀 비교](pyramid-decoder-comparison-results.json).

## 결론

**피라미드와 타일 읽기는 NetVips 없이 구현할 수 있고, 현재 구현에서는 캐시 타일 읽기가 빨랐다. 파일 로더 전체를 지금 교체할 근거는 부족하다.** 자체 경로는 Gray16 TIFF 준비에서 유리했지만 JPEG에서는 느렸고 디코드 메모리가 증가했다. 실제 초대형 24,576×131,072 TIFF는 OpenCV 기본 제한에 막혔다.

이번 공통 엔진은 `net10.0`이고 Windows 전용 API·WPF·DX12·NetVips·OpenCV를 참조하지 않는다. 별도 `VisionImaging.OpenCv` 어댑터와 실행 호스트에 native 의존성을 모았다. **NetVips 제거와 모든 외부 라이브러리 제거는 다르다.** 압축 코덱은 OpenCV/OpenCvSharp에 의존한다. 이 실험이 OpenCvSharp 유지보수 주체에 대한 우려까지 없애는 것은 아니다.

Linux x64용 배포물 생성과 의존성 검사는 PASS다. `libOpenCvSharpExtern.so`가 포함되고 NetVips·Windows runtime·WPF 참조는 없었다. 현재 PC에 WSL/Docker 실행 환경이 없어 **실제 Linux 실행·성능은 NOT_RUN**이다. 기존 VisionCanvas 화면은 WPF/DX12이므로 Windows 전용이며, Linux 화면 구현은 이번 실험의 범위가 아니다.

## 측정 방법

- Windows 11 Home `10.0.26200`, .NET 10, Ryzen 5 5600H 6코어/12스레드, 물리 메모리 약31.35GiB. GPU 렌더링을 포함하지 않은 CPU 파일 처리 비교다.
- 모든 관련 실행물은 Release 최적화가 켜졌음을 JSON에 기록했다. 최초 시험에서 실험 솔루션에 빠진 프로젝트 참조가 Debug로 빌드되어 그 결과는 제외했다. 아래 수치는 참조를 모두 포함한 최종 실행만 사용한다.
- NetVips `3.2.0` / Native.win-x64 `8.18.6`, OpenCvSharp4 / Windows slim runtime `4.13.0.20260627`. 기존 NetVips 캐시 설정을 그대로 사용했다. 자체 축소는 최대8개 CPU 작업을 사용한다. 동일 스레드 수로 튜닝한 라이브러리 자체 대결이 아니라 현재 두 파일 경로의 비교다.
- 새 프로세스·새 디스크 캐시로 각 입력/구현을3회 실행하며 순서를 번갈아 배치했다. 최초 준비는 디코드·원본 캐시·모든 피라미드 단계 작성·초기 JIT를 포함한다. fixture 생성과 빌드는 측정 밖이다. 초대형 입력은 지원 범위 확인용으로 각1회다.
- 파일을 닫고 같은 프로세스에서 캐시를 다시 연 뒤 각 단계의 첫/끝 타일과 결정적 난수 타일을 읽었다. 단계당 난수 요청은 최대128개, 세 pass를 수행했다. 아래 p95는 **세 번째 pass의 p95를 실행3회에서 중앙값**으로 집계했다. 타일 Read 안의 풀 버퍼 대여/복사는 포함하고, 해제와 checksum은 타일별 타이머 밖이다.
- OS 파일 캐시를 비우지 않았다. 최초 준비도 cold-disk 수치가 아니며, 반복 타일은 warm-cache 수치다. 난수 요청에 중복이 있고 Canvas의 별도 타일 캐시는 사용하지 않는다. 단순 checksum과 별도로 픽셀 비교를 수행했다.
- 메모리는20ms 간격의 프로세스 Private Bytes와 Working Set 최고값이다. 각 실행 전체 구간의 최대값이며 디코드 단독 측정이나 RAM 상한이 아니다. 짧은 피크를 놓칠 수 있다. memory map과 파일 캐시 때문에 두 지표가 다르다.
- 합성 입력은 고정 난수512×512 타일을 반복한 고엔트로피 패턴이다. 실제 카메라/현장 파일을 대표하지 않는다. 초대형 TIFF는 기존 열 패턴의 압축 BigTIFF를 재사용했다.

원본 로그: `artifacts/pyramid-comparison/run-20261013-202036-c1175fa4/reports.json`. 삭제하지 않은 실험 캐시가 남으며 자동 정리 코드는 없다.

## 최초 준비 시간

단위 ms. 중앙값, 괄호는 실행3회의 최소~최대다.

| 입력 | NetVips | 자체 + OpenCV | 해석 |
|---|---:|---:|---|
| 8192×8192 Gray8 PNG | 263.9 (253.6~392.7) | 254.0 (251.4~283.0) | 겹치는 범위, 우열 단정 어려움 |
| 8192×8192 RGB JPEG → RGBA | 900.5 (880.5~932.3) | 1383.3 (1354.3~1398.1) | 자체 약54% 느림 |
| 24576×8192 Gray8 TIFF | 723.0 (708.6~728.9) | 832.5 (802.5~855.8) | 자체 약15% 느림 |
| 24576×8192 Gray16 TIFF | 1330.4 (1311.1~1379.6) | 783.5 (746.7~795.7) | 자체 약41% 짧음 |

JPEG 디코딩·채널 변환·축소·쓰기 각각의 세부 병목을 프로파일링한 결과는 아니다. 이 표만으로 특정 코덱이나 필터가 원인이라고 확정하지 않는다. 실행 횟수가 작으므로 통계적 일반화보다 후속 비교의 기준으로 사용한다.

## 캐시 재사용과 타일 읽기

단위 ms. 실행3회 중앙값.

| 입력 | 재열기 NetVips / 자체 | 반복 타일 p95 NetVips / 자체 | 자체 캐시 MiB |
|---|---:|---:|---:|
| 8K Gray8 PNG | 14.08 / 8.42 | 1.396 / 0.095 | 85.3 |
| 8K RGB JPEG | 13.54 / 8.16 | 2.420 / 0.188 | 341.0 |
| 24K×8K Gray8 TIFF | 16.27 / 8.33 | 1.512 / 0.099 | 256.0 |
| 24K×8K Gray16 TIFF | 16.35 / 8.68 | 1.590 / 0.121 | 512.0 |

현재 NetVips 구현은 타일마다 Region을 만들어 `vips_region_fetch`로 읽고, 자체 구현은 준비한 raw memory map에서 행을 복사한다. 이 조건에서는 자체 Read의 p95가 약13~15배 짧았다. **libvips의 최선 구현 대비 우위나 화면 FPS 향상 수치로 해석하면 안 된다.** 동일한 원본·단계가 이미 디스크에 있을 때 두 현재 구현이 쓰는 읽기 경로의 차이다. 기존 NetVips 경로도 캐시/Region 재사용 등 별도 개선 가능성을 평가할 수 있다.

양쪽 디스크 캐시 크기는 표의 반올림 정밀도에서 같았다. 자체 raw와 기존 `.v` 모두 비압축 단계를 보관하며, 자체 구현이 디스크 용량을 줄인 것은 아니다.

## 메모리와 초대형 파일

MiB, 프로세스 최대값의 실행3회 중앙값. 표의 총 프로세스 수치를 추가 할당량으로 읽지 않는다.

| 입력 | Private Bytes NetVips / 자체 | Working Set NetVips / 자체 |
|---|---:|---:|
| 8K Gray8 PNG | 32.0 / 77.0 | 81.7 / 128.9 |
| 8K RGB JPEG | 77.7 / 212.0 | 365.7 / 297.6 |
| 24K×8K Gray8 TIFF | 78.2 / 218.7 | 228.7 / 410.0 |
| 24K×8K Gray16 TIFF | 125.8 / 403.7 | 517.2 / 794.4 |

OpenCV 어댑터는 전체 Mat을 디코딩한다. 원본 raw 저장 후 Mat을 해제하고 자체 축소를 시작하지만, 최초 디코드 비용은 피할 수 없다. 캐시를 memory map으로 읽는 것만으로 낮은 메모리의 스트리밍 디코더가 되지는 않는다.

| 24576×131072 입력, 각1회 | NetVips 최초 준비 | 자체 + OpenCV |
|---|---:|---|
| Gray8, 원본3GiB | 8.114초 | FAIL: `pixels <= CV_IO_MAX_IMAGE_PIXELS` |
| Gray16, 원본6GiB | 22.393초 | FAIL: 동일 제한 |

OpenCV 공식 문서는 기본 읽기 픽셀 제한을 약2^30으로 설명한다. 이 입력은3,221,225,472px다. 제한을 환경변수로 올리는 실험은 하지 않았다. 올려도 전체 Mat의3/6GiB 메모리와 TIFF 구현의 다른 제한을 검증해야 한다. 따라서 **현재 실험 경로는 초대형 파일 요구를 충족하지 못한다.** [OpenCV 이미지 읽기 문서](https://docs.opencv.org/4.13.0/d4/da8/group__imgcodecs.html).

## 정확성·경계·검증

- **PASS:** 공통 엔진14개 테스트. Gray8/Gray16/RGBA 원본과 홀수 가장자리, 상수 보존, 홀수/짝수 축소 정렬, 캐시 재열기 시 디코더 미호출, 취소 시 미완성 캐시 미게시와 reader 해제, 손상 파일 거부, 잘못된 타일/해제 후 호출, 원본 변경 시 별도 캐시, 외부 의존성 경계.
- **PASS:** 축소 홀수/짝수 조건을 임시 반전하면 관련4개 테스트가 실패한다. 원본 복원 후14개 모두 통과. 복원 DLL SHA256은 측정한 실행물과 동일했다.
- **PASS:** 네 개 대형 fixture와 홀수 Gray16/RGBA 두 개의 모든 단계에서 결정적 타일 표본을 비교했다. 각각 약6893만·6893만·1억7302만·4325만·70만·281만 채널 값에서 오차0. 작은 홀수 입력은 전체 픽셀을 포함한다. 큰 입력 전체를 전수 비교하거나 실제 JPEG 일반 동등성을 확인한 것은 아니다.
- **PASS:** 실험 솔루션 Release 경고0/오류0. Linux x64 publish 성공. 전체 Windows 실행28회 중 자체14개 프로세스 기록에서 NetVips/libvips가 로드되지 않았다(12개 일반 성공 + 초대형2개 실패). 의존성 없는 엔진과 OpenCV native 호스트를 구별한다.
- **NOT_RUN:** Linux native 실실행, Linux 화면, ARM64, 현장 이미지/색상 프로파일/다중 페이지 전체/모든 압축 종류, 장시간 캐시 운영, GPU/WARP 렌더링과 ROI 편집60FPS. 이번 실험은 기존 렌더러를 수정하지 않아 제품 전체 회귀·프레임 재측정은 수행하지 않았다.

삼각 필터는 축마다 정수 반올림과 경계 복제를 적용한다. 짝수 길이는 `[1,3,3,1]/8`, 홀수 길이는 출력 크기 올림에 맞춰 `[1,2,1]/4`로 중심을 정렬했다. 최초 홀수 입력 차이는 이 위상 차이였으며 수정 후 검증했다. NetVips 기준은 기존 코드의 `Resize(0.5, Linear)`다. [libvips resize 문서](https://www.libvips.org/API/current/method.Image.resize.html).

## 다음 판단

현재 생산 파일 로더는 NetVips를 유지하는 것이 합리적이다. 별도 자체 엔진은 **제한된 픽셀 형식·충분한 RAM·반복 타일 읽기** 조건에서 유효한 후보로 남긴다. 초대형 파일까지 대체하려면 전체 Mat이 아닌 TIFF strip/tile 또는 행 기반 스트리밍 디코더를 이 경계에 붙이고 다시 측정해야 한다. 단순 제한 해제나 압축 코덱 전체 재구현을 이번 성능 결과로 정당화하지 않는다.

카메라 메모리 프레임의 표시에는 이 파일 어댑터도 필요 없다. 카메라 SDK → 중립 프레임 계약 → Canvas의 기존 경로를 유지한다. ROI 이동·회전·확대·이력은 파일 코덱과 분리되어 있으며 이번 구현이 이 연산을 NetVips/OpenCV에 종속시키지 않는다.
