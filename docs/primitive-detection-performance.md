# 일반 도형 검출 — 생성 비용을 뺀 32K 성능

2026-10-16. 정확도 우선, CPU와 선택형 CUDA, 로컬 수정·검증 범위다. 기존 PCB 검증의 33.987초/41.905초에는 읽을 때마다 합성 마크를 그리는 비용이 들어 있었다. 그 숫자에서 병렬 작업 시간의 합을 빼서 순수 검출 시간을 추정하지 않는다.

## 최종 32K 비교

Ryzen 5 5600H/32GB/RTX3060 Laptop, Release. 동일32,768² 원본, PCB 마크16,384개, 점수0.8·크기12~256px·4작업·결과 상한0(전체). 1,849개 창에서 겹침을 포함해2,982,033,664픽셀을 처리한다. 생성·읽기·GPU 초기화·평가 후처리를 제외하고 **GPU 전송과 대기는 포함**한 순수 검출 시간이다.

| 경로 | 변경 전 중앙값 (범위) | 변경 후 중앙값 (범위) | 시간 감소 |
| --- | ---: | ---: | ---: |
| CPU · 각3회 | 6.014초 (5.989~6.024) | **4.370초 (4.362~4.430)** | 27.3% |
| CPU + CUDA · 각6회 | 7.545초 (6.568~10.295) | **5.600초 (5.172~5.818)** | 25.8% |

CPU는 전/후, GPU는 전/후/전/후의 별도 프로세스를 순차 실행하고 각 프로세스의 첫 `run=0`을 제외했다. 같은 평가 호스트에 변경 전후 알고리즘 바이너리를 사용했다. 빌드·테스트·프로파일러와 겹치지 않았다. 최종 GPU 시간의 변동이 커3회씩 한 쌍을 더 측정했으며, 느린 표본도 모두 포함했다. 위 가속률은 이 반복 집합의 관측값이고 고정 보장값이 아니다. **CUDA는 최적화 뒤에도 CPU보다 느리다.**

처음 분리한 기준 측정은 CPU4.530~4.907초(중앙값4.800), CUDA5.874~5.918초(중앙값5.879)였다. 개발 중 CPU 변경 후에는3.479~3.854초도 관측됐다. 다른 시점의 최솟값만 골라 비교하지 않고, 위 표에는 마지막 연속 비교를 사용했다. 개발 PC의 다른 앱·열 상태·GPU 스케줄링을 통제하지 않았으므로34초에서4초로 줄었다는 것을 알고리즘만의8배 가속으로 표현하지 않는다.

입력 읽기·초기화·해제까지 포함한 최종 호출 중앙값은 CPU7.092→5.428초, CUDA8.779→6.760초다. 최종 읽기 중앙값은 CPU1.057초, CUDA.993초다. 검사 호출의 managed 할당은 CPU3.951→2.858GB, CUDA3.966→2.870GB이며 대부분 약1.09GB의 임시 배열 할당이 줄었다. 메모리 원본1GiB를 포함한 프로세스 peak working set은 최종 CPU 약1.45GB, CUDA 최대1.62GB다. 영구 잔류량/VRAM 사용량과 구별한다.

원시JSONL, 올바른 중앙값 집계 코드/결과, 전후 소스 두 파일, 프로파일, 시험·빌드·형식 로그는 [검증 묶음](data/primitive-performance-validation.zip)에 보존한다.

## 측정 경계

평가 도구의 `--prefill`은 기존 생성기의 **동일한 Gray8 타일**을 한 번 만들어 메모리에 보관한 뒤 검사를 시작한다. 32K 입력만 1GiB다. 제품의 원본 창/메모리 예산을 바꾸거나 검출 결과를 캐시한 것이 아니다.

| 항목 | 포함하는 작업 |
| --- | --- |
| `preparationMilliseconds` | 합성 원본 타일 생성과 메모리 준비. 검사 반복 밖에서 한 번만 실행 |
| `ReadMilliseconds` | 원본 타일 읽기·캐시·검사 창 조립 |
| `ComputeInitializationMilliseconds` | 검사별 CUDA 장치/커널 준비. CPU에서는 거의 0 |
| `DetectionMilliseconds` | 각 묶음의 병렬 검출 시작부터 결과 병합까지의 실제 경과 시간 합. GPU 전송·커널·대기도 포함 |
| `DetectionWorkMilliseconds` | 개별 창 작업의 시간 합. 병렬 시간과 GPU 잠금 대기가 겹치므로 벽시계 시간이 아님 |
| `Milliseconds` | 기존 서비스 내부 시간. 읽기·장치 준비 포함, 최종 자원 해제 직전까지 |
| `requestMilliseconds` | 평가 호스트가 `DetectAsync`를 호출해서 반환받기까지. 자원 해제 포함, UI 제외 |
| `detectionAllocatedBytes` | 호출 전후 프로세스 전체 managed 할당 증가. GC 후 잔류량/VRAM이 아님 |

최종 결과 해시/정답 대조/JSON 직렬화는 검출 시간 밖이다. 기존 `allocatedBytes`는 이 평가 후처리도 포함하므로 검출 할당과 구분한다. `--prefill`은 Gray8 평가용이며 실시간 수집·PNG 디코딩·32K 화면 표시 시간으로 해석하지 않는다.

## 실제 병목과 변경

8K 고정 입력 반복을 `dotnet-trace`로 샘플링했다. 검출 스택의 누적 표본 시간 중 분류 약49%, 윤곽 추출 약46%, 별표 분류 약31%, 양방향 경계 거리 루프 약18%였다. 부모/자식 호출 비중은 겹치며 합산하지 않는다. 프로파일러를 켠 시간은 가속률 계산에 사용하지 않았다.

1. **윤곽 검사:** 이웃 표본은 같은 상대 변과 맞는 경우가 많다. 이전에 맞은 변을 먼저 검사하고, 실패하면 모든 변을 원래 순서로 검사한다. 동일한 거리 함수·3개 표본·양방향 검사·허용치를 유지한다. 존재 여부를 확인하는 순서만 바뀐다.
2. **별표 폭/길이:** 한 획의 회전 방향은 모든 표본에 공통이다. sin/cos를 획마다 한 번 계산하고, 같은 순서로 길이 최대값과 폭 목록을 모은다. 표본마다 회전한 배열을 만들고 다시 순회하는 일을 없앴다. 평균·중앙값·점수 계산 순서는 유지한다.
3. **CUDA 전송:** 연속 Gray8 창은 원본 메모리에서 바로 전송한다. stride가 넓은 입력만 행을 포장한다. ILGPU의 동기 복사 API가 이미 기다리는 stream을 다시 기다리지 않는다. 커널 뒤 완료 대기, 취소/오류 때 drain, 반환 버퍼 소유권은 유지한다. [ILGPU 1.5.3 복사 구현](https://github.com/m4rs-mt/ILGPU/blob/v1.5.3/Src/ILGPU/Runtime/ArrayViewExtensions.cs#L1153)을 확인했다.

점수 .8, 최소/최대 크기, 원본 2Mpx 창, halo, 최대4작업, Otsu/극성, 전체 윤곽, 후보/결과 수, ROI/마스크/취소 계약은 그대로다. GPU는 median을 실행하고 나머지 단계는 공통 CPU 코드다.

- 알고리즘53 + 실제CUDA14 + 검사/CLI21 = **88건 PASS**. CUDA 새 시험은 동시 호출, 큰/작은 창으로 버퍼 재사용, stride, 목적지 부분 메모리, 앞서 반환한 결과 보존을 독립 정렬 median과 비교한다. 기존 마스크/취소/원본/중첩/한도 시험도 유지했다.

- Computer Use로 새 앱에서1024² PNG를 열어 CPU16개/첫524.1ms, CUDA16개/첫773.4ms, CPU 재실행16개/41.5ms와 모든 결과 문구 일치를 확인했다. # 구멍과 분리 더블스퀘어 윤곽도 표시됐다. [UI 상태 증거](data/primitive-perf-ui-validation.json). 이 숫자는 서비스 표시 시간이며 순수 검출/버튼→물리 scan-out 시간이 아니다.

### 원칙 검토

새 의존성·공개 전략 인터페이스·전역 캐시를 추가하지 않았다. 알고리즘은 기하 판단, 서비스는 입력 창/병합, CUDA 객체는 장치 수명, 외부 평가 도구는 계측/정답 대조를 맡는다. SOLID의 책임 분리·기존 확장 지점·동일 전처리 계약·작은 인터페이스·주입 경계를 유지했다. GRASP의 Controller/Creator/Information Expert는 각각 서비스/장치 소유자/분류기에 남고, Low Coupling/High Cohesion은 파일별 책임으로 유지한다. Polymorphism/Indirection/Protected Variations는 기존 `IPrimitivePreprocessor`, Pure Fabrication은 기존 검사 서비스가 담당하며 이번 작업을 위해 새 패턴을 만들지 않았다.

## 코드를 공부하는 순서

| 순서 | 파일/단계 | 이유 |
| --- | --- | --- |
| 1 | `PrimitiveShapeDetectionService` | 원본을 halo가 있는 작은 창으로 읽고, 중심 소유권으로 중복 없이 원본 좌표에 병합 |
| 2 | `PrimitiveContourExtractor` | 3×3 median → 이진화 → CComp 윤곽/구멍. 구멍 안의 독립 물체는 별도 전경 |
| 3 | `PrimitiveShapeDetector` | 마스크·크기·잘림을 검사하고 분류/복합 도형 결합/최종 필터 순서 유지 |
| 4 | `PrimitiveContourClassifier`와 `.Pcb` | 꼭짓점/직선/반경으로 가설을 세우고, 면적과 전체 경계로 확인 |
| 5 | `DoubleSquareClassifier` | 서로 유일한 사각형 짝만 결합하고 떨어진 윤곽 보존 |
| 6 | `CudaPrimitivePreprocessor` | CPU와 같은 정수 median. 전송/실행/수신 수명과 시간 분리 |

“빠른 가설”만으로 판정하지 않고 최종 경계 검증을 유지한다. 이번 최적화도 검증을 생략하는 방식이 아니다. 읽기·병렬 실행·기하 판정·장치 수명을 다른 책임으로 유지하며 새로운 알고리즘 계층이나 의존성을 추가하지 않았다.

## 재현

```powershell
dotnet build tools/PrimitiveDetection.Evaluation -c Release --artifacts-path artifacts/primitive-perf-final
# 빌드/테스트가 끝난 후 순차 실행. run=0은 워밍업, run=1..3 비교.
& artifacts/primitive-perf-final/bin/PrimitiveDetection.Evaluation/release/PrimitiveDetection.Evaluation.exe 32768 0 3 --pcb --prefill
& artifacts/primitive-perf-final/bin/PrimitiveDetection.Evaluation/release/PrimitiveDetection.Evaluation.exe 32768 0 3 --pcb --prefill --gpu
& artifacts/primitive-perf-final/bin/PrimitiveDetection.Evaluation/release/PrimitiveDetection.Evaluation.exe --poses
```

`--poses`는 3,015개 회전/크기/밝기/잡음/접촉 간격 조건의 **전체 결과 JSON**을 순서대로 해시한다. 변경 전후 바이너리에 같은 평가 호스트를 사용해 위치·각도·점수·면적·모든 윤곽과 잘림/한도까지 비교한다. 속도에 맞춰 기준을 낮추거나 기대 개수를 바꾸지 않는다.

실제 PCB 정답 라벨에서의 누락/오검출률, 모든 제조사/촬영 조건, 물리 정밀도,32K 버튼→화면 표시 시간은 이번 검증 범위가 아니다. 기존 합성 정확도와 지원 형상/크기 범위를 유지한 성능 개선이다.
