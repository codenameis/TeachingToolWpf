# 메인 편집기의 1억 ROI·30만 개 부분 선택 검증

2026-10-13, `main` 로컬 변경·검증. 사용자가 [공통 문서 확장 범위](../tasks/main-editor-billion-roi-scope.md)를 승인했다. 구현/원칙 검토는 [ADR-042](decisions/0042-main-editor-repeated-rois.md)에 기록한다. **엄격한 모든 프레임 16.67ms 이내·60FPS 이상 조건은 아직 FAIL**이다.

## 사용법

1. TeachingToolWpf에서 8K 샘플 또는 이미지를 연다. 상단 **1억 ROI 테스트**를 누르면 현재 이미지 중심에100,020,001개 반복 사각형을 추가한다. 별도 창을 열지 않는다. 최소 변 길이556px 이상이 필요하다.
2. 빈 곳에서 마퀴를 그려 일부를 선택한다. Ctrl+A, Ctrl+C/V, Delete, 이동·회전, Ctrl+Z/Y가 일반 ROI와 같은 문서·이력을 사용한다. 반복 배치 전체를 붙이면 새 배치 ID가 생긴다.
3. 확대 후 원하는 ROI를 더블클릭한다. 기존 선택을 교체하며 오른쪽 속성에서 위치·크기·각도를 수정한다. 겹친 배치/일반 ROI는 Alt 클릭으로 순환한다. 목록은 배치 한 행으로 표시하며 부분 선택 상태에서 Ctrl로 다른 행을 추가해도 기존 셀 범위를 유지한다.
4. 축소 화면의 격자 윤곽은 요약 표시다. 회전 후 부분 선택의 미세한 계단 경계도 점유 요약 셀로 합치므로 부분 경계의 색 구분은 근사다. 확대하면 정확한 개별 윤곽을 그린다. 실제 선택·hit·편집 형상은 요약으로 바꾸지 않는다. 색·두께 설정은 기본 ROI 스타일을 따른다. 반복 셀의 그룹·이름/검색 범위·필터·마스크·검사는 지원하지 않으며 패널에 안내하고 혼합 선택 명령도 차단한다. 일반 ROI의 해당 기능은 유지한다.

## 측정 방법

- 기준 장비: Ryzen5 5600H,12논리 프로세서,32GB RAM, RTX3060 Laptop6GB, Windows x64. 강제 WARP는 표시를 CPU로 실행하며 이 장비 이외의 CPU 성능 보장은 아니다.
- Release,8192×8192 기본 샘플, 메인 viewport877.333×540DIP/DPI1.5(1316×810pixel). 작업 완료 wall time, UI dispatch/dispatcher gap, 렌더 제출 간격, 프로세스 CPU 시간, DXGI 표시 카운터를 구별한다.
- `SelectionRun`: 일반 ROI100,000개 생성 후 실제 Copy/Paste 두 번으로300,000개. 빈 선택에서 정확히150,000/200,000개를 생산 마퀴 입력 경로로 선택한다. iteration0은 첫 실행,1/2는 반복이다. 선택 개수와 기존 ROI 참조 불변을 검사한다. `captureReadyMs`에는 PNG 인코딩·디스크 쓰기가 포함되어 물리 표시 시간으로 해석하지 않는다.
- `RepeatedDocumentRun`: 메인 버튼과 명령으로100,020,001개+일반 ROI1개, 절반50,005,001개 선택·복붙, Undo/Redo, 전체 복붙 후200,040,004개, native 더블클릭 교체·기존 속성 편집/Undo를 검사한다. 전체/부분×요약/상세×수평/수직/대각선/회전16구간과 개별 이동/회전2구간을 측정한다. 각 구간0.5초 준비 후3초 연속 입력이며 90% 이상 pose가 실제 바뀌었는지 검사해 경계 제한으로 멈춘 입력을 제외한다.
- 추가 `--fragmented-selection`: 전체를37도 회전한 후 절반을 선택한다.50,005,495개 선택/7,537개 원래 점유 블록에서 요약/상세의 이동·회전4구간을 측정한다. 실제 부분 선택과 요약 표시의 차이를 명시하고, 이 조건을 단순 직사각형 절반 시험으로 대신하지 않는다.
- `ProcessCpuMs`는 앱의 user+kernel CPU 시간 합이다. 여러 코어에서 동시에 실행하므로 프레임당 값이16.67ms보다 클 수 있다. 기존 `cpu_ms`(대기 포함 wall time)와 구별한다. DXGI 주기 추정도 물리 입력→화면 촬영이 아니다.
- 결과와 실행물/셰이더 해시는 `main-editor-repeated-roi-results.json`에 보존한다. 원시 CSV·PNG는 로컬 `artifacts/`에 둔다.

## 일반 ROI30만 개 선택 개선

같은 메인 창에서 일반 ROI100,000개를 두 번 복붙한300,000개 문서다. GPU 반복1/2의 마퀴 입력부터 준비·게시 완료까지 wall time을 비교했다.

| 빈 선택 → 선택 개수 | 개선 전(ms) | 개선 후 GPU(ms) | 개선 후 WARP(ms) |
|---|---:|---:|---:|
| 150,000 | 996.90 / 833.44 | 250.49 / 261.91 | 272.72 / 273.23 |
| 200,000 | 998.70 / 1020.18 | 270.38 / 282.33 | 277.74 / 312.93 |

GPU 반복 평균 기준 약72%/73% 단축이다. 최초 실행도 GPU246.56/255.13ms, WARP251.78/260.52ms였다. 반복 입력 dispatch는GPU1.33~2.04ms/WARP1.07~2.23ms지만 dispatcher 최대 틈은GPU32.09~38.87ms/WARP31.81~40.65ms다. 선택 준비를 빨리 마치는 것과 모든 입력/프레임이16.67ms 이내인 것은 다르며 후자는 FAIL이다.

원인별 개선: 선택 BVH의 ID 경로 표 지연 생성, flat ROI의 자손 집합 공유, FrozenSet membership과 작은 Ctrl 토글 delta, 큰 선택 사실 확인의 순차 조회, 공간 색인이 반환한 유효 ID의 중복 검증 제거. 일반 ROI를 반복 배치로 자동 변경하지 않았다. 원본 ROI·계층·수정·이력 표현은 유지한다.

## 메인1억 ROI의 최종 결과

`main-repeated-warp-verified`/`main-repeated-gpu-verified` 실행은 모두 오류 없이 종료했다. 실제 메인 버튼과 혼합 문서에서 선택·복붙·native 드래그·속성·Undo/Redo 검증을 통과했다. 아래 값은 입력/명령부터 준비·문서 게시 완료까지의 wall time이며 물리 표시 완료 시간은 아니다.

| 작업 | GPU(ms) | WARP(ms) |
|---|---:|---:|
| 100,020,001개 추가 | 28.76 | 28.25 |
| 약5천만 개 부분 선택 첫 실행 | 62.01 | 64.02 |
| 같은 부분 선택 반복1 / 2 | 17.81 / 17.10 | 16.88 / 16.77 |
| 부분 복사 / 붙여넣기 | 16.19 / 34.29 | 16.99 / 35.01 |
| 전체 선택 | 8.99 | 9.50 |
| 전체 복사 / 붙여넣기 | 0.28 / 12.76 | 0.30 / 13.02 |
| 붙여넣기 Undo / Redo | 18.03 / 12.62 | 19.08 / 13.01 |
| native 전체 이동 / 회전 확정 | 8.59 / 4.32 | 8.59 / 3.99 |

전체·절반×요약·상세×수평·수직·대각선·회전 및 개별 이동/회전의18개 구간에서:

| 장치 | 구간별 평균 FPS 범위 | 구간 p95 최대(ms) | 프레임 간격 최대(ms) | 입력 처리 최대(ms) | 엄격한60FPS |
|---|---:|---:|---:|---:|---|
| RTX3060 | 59.639~60.006 | 20.833 | 32.573 | 3.167 | FAIL |
| CPU WARP | 59.929~60.085 | 21.492 | 22.311 | 3.151 | FAIL |

측정 구간의 GC pause 합은 GPU16.876ms/WARP14.410ms였다. GC를 제외하거나 평균을 반올림해60FPS 통과로 만들지 않는다. 초기 후보 실행의GPU 개별 이동58.66FPS/최대51.74ms도 JSON에 보존한다. 최신 실행으로 이전 긴 멈춤이 모든 환경에서 사라졌다고 보장하지 않는다.

## 회전 후 부분 선택의 추가 병목

단순 직사각형 절반의 이동/회전만으로 충분하다고 보지 않고,37도 회전 후 새로 절반을 선택했다. 개선 후 선택 준비는 WARP77.84ms/GPU84.00ms였고, 실제 셀50,005,495개를7,537개의 점유 블록이 표현했다.

| WARP 구간 | 블록 병합 전 FPS | 병합 후 FPS | 프레임당 프로세스 CPU 합 전→후(ms) |
|---|---:|---:|---:|
| 축소·대각선 이동 | 15.93 | 59.94 | 510.42 → 36.55 |
| 축소·회전 | 15.28 | 59.99 | 510.87 → 38.59 |
| 상세·대각선 이동 | 60.08 | 60.08 | 90.62 → 82.64 |
| 상세·회전 | 60.00 | 59.94 | 85.12 → 80.30 |

축소 화면의 subpixel 계단마다 quad와 두꺼운 외곽을 그려 같은 픽셀을 반복 처리한 것이 병목이었다. 표시용 점유 요약 셀만 합쳐 캐시했다. WARP 축소 구간의 평균 사용 코어 상당치는8.13/7.75→2.19/2.32였다. 상세 경로는 그대로이므로 그 CPU 시간 차이는 반복 변동과 구별한다. GPU는 후속4구간59.41~60.00FPS였다. WARP p95최대21.51ms/GPU 최대 프레임 간격33.53ms로 엄격한 기준은 계속 FAIL이다. 최악 조건 전반이나 처음 새 배율 캐시를 만드는 비용의 상한을 보장하지 않는다.

```powershell
dotnet build TeachingToolWpf.slnx -c Release --no-restore --disable-build-servers -m:1

./scripts/Measure-RepeatedRoi.ps1 -Prefix artifacts/main-repeated-warp

```

앱은 성능 시험 종료 후 스스로 닫히며 오류 시 exit1/JSON error를 남긴다. 다른 앱 시험이나 빌드와 동시에 실행하지 않는다. 출력 prefix는 실행마다 다르게 사용한다.

## 정확성·검토

- Core296개, 앱 연동274개, Canvas222개 회귀 통과(실패·건너뜀0). 셀 범위 집합과 실제 열거 비교, 회전된 부분 선택/이미지 경계, 혼합 복붙 생성 순서/선택색, 최소 크기/미포함 override, 개별 수정/삭제/이미지 교체의 이력, 취소·오래된 준비 결과 배제, 부분 목록 선택, 기존 속성 연동을 포함한다.
- 실제 WARP 캡처로 작은 부분 블록의 축소 가시성, 두께 설정, pitch 밖으로 나가는 두꺼운 외곽을 검사한다. 요약 경계 조건을 이전 동작으로 변이하면 이 테스트가 실패하고 원본 복원 후 통과함을 확인했다.
- 전체 Release 솔루션 빌드 경고0/오류0. 변경 C#의 whitespace/style·명명과 `git diff --check`를 검사했다. 원래 미수정 영역 전체에 대한 이전 컨벤션 FAIL을 이번 변경 파일 검사로 PASS로 바꾸지 않는다.
- 독립 리뷰와 SOLID5/GRASP9 검토. 지적된 결함을 수정했으며 새 의존성·장치 교체·원칙 예외 없음. 기존 사용자 변경 및 `dotnet-anti-slop/`를 보존하고 커밋/푸시하지 않는다.

## 한계

1억 논리 셀의 선택/복붙은 압축 반복 구조 덕분이다. 모든 셀이 제각각 수정되거나 부분 편집을 무수히 반복하여 구간/part가 크게 늘어난 최악 조건을 같은 속도로 보장하지 않는다. 셀 전체를 전개하지 않아도 구조의 조각 수·개별 수정 수에 비례하는 비용은 남는다. 다른 CPU/모니터, 실제24K 파일과 함께 장시간 작업, 물리 입력→픽셀 지연, 임의 사용자 문서는 NOT_RUN이다. 일반30만 개 선택 완료 지연과 렌더 프레임 예산의 남은 초과를 숨기지 않는다.

이전 `artifacts/main-repeated-warp.json`의 회전 구간은 일반 ROI가 이미지 가장자리에 있어 변환이 경계에서 제한되므로 성능 비교에서 제외했다. `selection-ui-after.json`도 마퀴 시작점이 실제 ROI hit 허용 거리 안에 있었던 잘못된 fixture로 제외했다. 수정 후 개수/실제 pose 변화 검사를 통과한 실행만 수치로 사용한다.
