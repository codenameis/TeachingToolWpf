# kensa 전압 글자와 검사 로그 검증 — 2026-10-05

이 변경은 작은 전압 글자의 오검출·180° 자세 오류를 개선하고 논문 검사 로그를 추가한다. CPU 125 ms/CUDA 80 ms 미만 목표 달성 보고가 아니다.

## 입력과 재현

- `kensa.png`: 1024×1536, SHA256 `7EEED204BFE88C79F285D4F0AE195F954880984C58F59282B501965080846E77`.
- 학습 ROI: 중심 `(194.5,371)`, 크기 `19×12`, 각도 0°. 여백 비교 ROI는 같은 중심 `25×16`.
- 최소 점수 .72, 후보 점수 .65, 방향 지지 .6, 회전 ±180°/10° 간격, 고정 배율 1, 후보 2048, 검증 64, 출력 256. 기준 CPU의 논리 프로세서 12개 사용.
- 비교 위치: X=`194.5/459/723`, Y=`371/686/1000/1315`의 12개 전압 글자. 3 px는 개체 대응용이며 측정 정밀도 보장이 아니다. 문자의 OCR 정답이나 일반 현장 검출률을 평가하지 않는다.

기존 한 단계·26 특징 모델은 118개를 반환했다. 전압 글자 위치 12개 이외에 다른 인쇄 글자 106개가 포함되었고, 마지막 행 가운데 전압 글자는 180° 자세였다. 현재는 원본 세부 에너지와 허용 범위 내 반대 방향을 함께 확인한다.

## 결과와 한계

별도 Release benchmark의 동일 ROI 전체 검색에서 12개 전압 글자 위치에 일대일 대응하고 다른 위치는 반환하지 않았다. 수정 직후 반복 3회는 305.4/314.4/314.5 ms였다. 이는 서비스 측정이며 버튼→표시 시간이 아니다. 추가 세부 검증의 계산 비용이 있으므로 이 변경을 속도 개선으로 표현하지 않는다.

실제 WPF 앱의 CPU 최초+반복 3회, CUDA 최초+반복 3회에서 12개 위치·점수·표시 경계와 순서가 동일했다. 네 창 모두 후보/검증 예산 초과를 기록하므로 **검색 불완전 WARN**을 유지한다. 특정 12개 위치가 검출되었다는 사실을 모든 후보의 완전 검색으로 바꾸지 않는다. 전체 성능 수용은 FAIL이다.

최종 ReadyToRun/AVX2·tiered compilation off 실행본의 앱 실측(반복3회 중앙값, ms):

| 입력/방식 | 서비스 | 명령 await 완료 | WPF 표시 관측까지 | 정확도/완전성 |
|---|---:|---:|---:|---|
| kensa 18V CPU | 386.9 | 392.6 | 492.0 | 12개 위치 대응, 예산 WARN |
| kensa 18V CUDA | 375.6 | 380.4 | 429.5 | CPU와 exact, 예산 WARN |
| 8192² 샘플 CPU | 288.6 | 295.2 | 664.3 | 256핀 일대일·사선 점수 구분·잘림 없음 |
| 8192² 샘플 CUDA | 255.4 | 260.9 | 473.2 | CPU와 exact·잘림 없음 |

18V의 모드별 최초 명령/표시 관측은 CPU504.2/810.0 ms, CUDA989.2/1073.9 ms다. 8K는 CPU426.2/671.0 ms, CUDA653.9/729.7 ms다. 장치 준비는 JSON에 별도 보존하고 명령 전체에도 포함한다. 독립 첫10회·반복100회 수용 검증은 하지 않았다.

18V 마지막 CPU 검사의 작업 누적은 읽기11.8, 전처리67.3, 후보88.7(격자49.2/자세39.5), 방향/미세 획121.9, 윤곽 점수94.4 ms다. CUDA 후보의 전송/대기 포함5.46 ms와 전체 서비스373.4 ms의 차이는 CPU 잔여 작업에서 나온다. 이 창 검색은 순차 실행이지만 일반 피라미드의 worker 합에도 같은 해석을 적용하면 안 된다.

로그의 `WorkerDiagnostics`에서 방향/미세 획 검증 및 원본 윤곽 점수의 CPU 비용이 확인된다. CUDA 후보 커널 시간은 서비스 전체가 아니며 전송/대기를 포함해 따로 기록한다. 첫 장치 준비도 명령 전체 시간에 포함한다. 최신 원시 측정은 증거 ZIP의 `app-text.json`, `app-text.inspection-log.json`, `app-8k.json`에 보관한다.

## 사용법

새 실행본에서 논문 형상을 선택하고 18V ROI를 다시 학습한다. 검사 후 오른쪽 패널의 **검사 시간 로그 · 최근 20회**를 펼치면 마지막 검사 시간이 나온다. **로그 JSON 저장**은 최근 20회 전체와 학습/검색 조건을 파일로 저장한다. 세션을 닫기 전에 저장해야 한다.

`CommandMilliseconds`는 VM 검사 명령 처리 완료, `ResultPublishedMilliseconds`는 결과 게시, `RendererPresentationMilliseconds`는 같은 overlay의 라벨 준비/Present/fence 완료다. 마지막 값은 WPF 패널 렌더 완료나 물리 모니터 표시 완료가 아니다. diagnostic smoke의 `CommandThroughDisplayMilliseconds`도 WPF Rendering/ContextIdle 관측이며 물리 입력/DWM 완료 보장은 없다.

`WallPhases`는 순차 단계의 wall time이며 해당 단계 읽기/worker 대기를 포함한다. `ReadAccumulatedMilliseconds`와 `WorkerDiagnostics`는 단계 시간에 다시 합산하지 않는다. 각 창·병렬 작업 시간의 합을 전체 지연으로 해석하지 않는다. 미완료/미측정 필드는 null이며 성공으로 위장하지 않는다.

## 검증 범위

- Algorithm 최종 전체248 PASS: 미세 획·조명/극성·마스크·180°/허용 범위·최종 pose 점수·회전 학습/배율·원본 마지막 행/열 보존 및 기존 매칭 회귀.
- Inspection 103 PASS: 원본 I/O, 창 경계, 취소, 메모리/소유권 및 단계 wall time 범위.
- 앱 218 PASS: 기존 모드/학습/검사와 로그 20회 상한, JSON 직렬화, run/overlay ID, timeout·장치 준비 실패 기록.
- 실제 UI의 로그 패널, 전압 글자 12개 위치, CPU/CUDA 표시 동등성 및 JSON 내보내기 데이터 확인.
- 기존 Gaussian을 raw Sobel로 교체하거나 창 크기를 128로 줄인 실험은 누락/오검출/지연 증가로 폐기했다. 채택하지 않은 실험과 최종 동작을 구별한다.
- 최종 서비스 재현 도구(실제 학습 옵션과 DLL SHA 포함): `tight-final.json` 반복312.8/310.3/335.5 ms, `margin-final.json` 반복396.3/390.2/386.9 ms. 두 ROI 모두12개, 후보 예산 경고 유지. 앱의 시간과 혼합하지 않는다.
- 로그 저장 대화상자의 실제 수동 파일 선택은 NOT_RUN. 같은 직렬화 경로의 실제 파일 출력 및 읽기와 WPF 핸들러 빌드는 확인했다. Linux·다른 실제 글자/조명/회전/배율 일반화와 125/80 최종 수용은 미완료다.
