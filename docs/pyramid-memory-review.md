# 자체 파일 엔진의 메모리·추가 성능 검토

2026-10-13. [최초 비교](pyramid-decoder-comparison.md)의 후속이다. 생산 코드 대신 기존 실험 프로젝트에서 메모리 구간을 추가 측정했고, 컬러 변환의 불필요한 native 호출을 제거했다. **메모리를 크게 줄일 지점은 전체 원본 디코딩이며, 작은 코드 변경으로 JPEG 준비 시간은 약28% 줄었다.** [이번 원본 수치·SHA256·픽셀 비교](pyramid-memory-review-results.json).

## 메모리 비교

먼저 두 지표를 구별한다. **Private Bytes**는 프로세스가 전용으로 할당한 메모리이며 RAM 상주량과 같지 않다. **Working Set**은 그 시점에 물리 RAM에 상주하는 프로세스 페이지로 공유/파일 매핑 페이지도 포함한다. 두 수치를 더하지 않는다. OS 전체 파일 캐시와 GPU 메모리를 합산한 수치도 아니다. [Microsoft PrivateMemorySize64](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.privatememorysize64?view=net-10.0), [WorkingSet64](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.workingset64?view=net-10.0).

아래는 최초 비교의 **프로세스 전체 구간 최고값, 실행3회 중앙값, MiB**다. 이번 변경은 디코드 버퍼 구조를 바꾸지 않았으며, 별도5회 비교에서도 메모리 감소는 확인하지 못했다.

| 입력 | 전용 할당 NetVips | 전용 할당 자체 | RAM 상주 NetVips | RAM 상주 자체 |
|---|---:|---:|---:|---:|
| 8192² Gray8 PNG | 32.0 | 77.0 | 81.7 | 128.9 |
| 8192² 컬러 JPEG | 77.7 | 212.0 | 365.7 | 297.6 |
| 24576×8192 Gray8 TIFF | 78.2 | 218.7 | 228.7 | 410.0 |
| 24576×8192 Gray16 TIFF | 125.8 | 403.7 | 517.2 | 794.4 |

전용 할당은 자체 경로가 약2.4~3.2배 크다. 그러나 컬러 JPEG의 전체 구간 최고 RAM 상주는 자체가 더 낮았다. 따라서 “메모리를 항상3배 쓴다” 또는 “전용 할당이 낮으니 실제 RAM도 낮다”고 일반화하면 안 된다.

## 언제 메모리가 커지는가

`inspect` 모드로 일반 시간 측정과 분리해 확인했다. 각 입력/구현1회이며, 경계 값과 구간 사이20ms 표본 최고값을 함께 남겼다. 강제 GC·프로세스 메모리 강제 축소·OS 캐시 비우기는 하지 않았다. 경계 관측 오버헤드가 있어 아래 구간 시간은 병목 진단용이며5회 전체 준비 시간과 분리한다.

24K×8K Gray16의 자체 경로:

| 시점 | 전용 할당 MiB | RAM 상주 MiB |
|---|---:|---:|
| 디코드 완료, Mat 보유 | 394.8 | 414.9 |
| 원본 raw 저장 완료, Mat 보유 | 402.9 | 423.1 |
| Mat 해제 직후 | 18.1 | 39.2 |
| 피라미드 준비 완료 | 32.3 | 52.5 |
| 캐시 재열기 후 타일3회 읽음 | 32.5 | 363.2 |
| 타일 source 해제 | 31.7 | 53.4 |

- **원본 Mat:** 24576×8192×2 = **384MiB**다. 해제 전후 전용 할당이 약385MiB 내려가 실제 원본 버퍼 비용과 맞는다. 관리 힙은 이때 약9MiB였으므로 C# GC만 튜닝해서384MiB를 없앨 수 없다.
- **디코드 도중 일시적 상주량:** 같은 실행에서 디코드 구간의 RAM 표본 피크는796.1MiB, 전용 할당 피크는401.5MiB였다. 디코드 완료 시점 값보다 높다. 매핑/공유 페이지를 포함한 차이이며, native 내부 페이지별 추적은 하지 않아 그 차이 전체의 세부 소유자를 확정하지 않는다.
- **반복 타일의 파일 매핑:** raw 단계의 페이지를 읽으면 상주량이 커진다. source 해제 후363→53MiB로 내려갔다. 이번 관측은 매핑 수명과 연동되는 비용을 보여주지만 장시간 누수 검증을 대신하지 않는다. OS가 회수할 수 있는 파일 페이지라는 사실도 프로세스 RAM 상한을 보장하지 않는다.
- **풀 버퍼:** 원본 저장용 최대8MiB 버퍼, 단계 출력/스크래치, 타일 버퍼가 ArrayPool에 남을 수 있다. source 해제 후 관리 힙 약19MiB가 남았으며 강제 GC로 수치를 작게 만들지 않았다.

메모리 피크와 준비 후 비용은 다르다. 아래는 같은 진단에서 **타일3회 읽기 직후의 경계 값**이며 최고값/3회 중앙값이 아니다.

| 입력 | 전용 할당 NetVips / 자체 MiB | RAM 상주 NetVips / 자체 MiB |
|---|---:|---:|
| 8K Gray8 | 17.7 / 19.2 | 39.2 / 127.9 |
| 8K 컬러 | 18.2 / 27.9 | 40.7 / 297.3 |
| 24K×8K Gray8 | 22.6 / 30.7 | 43.9 / 256.0 |
| 24K×8K Gray16 | 19.9 / 32.5 | 44.2 / 363.2 |

기존 NetVips 경로는 이 읽기 패턴에서 프로세스 상주량을 낮게 유지했고, 자체는 메모리 매핑을 유지하며 타일을 빨리 읽었다. 속도 이득과 이 메모리 비용을 같이 판단해야 한다. 다른 viewport·탐색 패턴·메모리 압박 상태에서 동일한 값은 보장하지 않는다.

## 확인한 속도 개선

실험 `OpenCvRasterDecoder.ReadRows`의 컬러 루프가 `x < Width`를 매 픽셀 검사했다. `Width → Mat.Width → Cols`는 고정 버전 OpenCvSharp에서 native 호출이다. 이를 ReadRows 시작의 지역 변수로 보관했다. 원본 Mat은 reader 내부 단일 소유이며 읽는 중 크기가 바뀌지 않는다. 픽셀 복사·채널 순서·취소 확인·소유권은 동일하다. 새 버퍼·의존성·플랫폼 분기를 추가하지 않았다. [해당 버전 Mat 구현](https://github.com/shimat/opencvsharp/blob/4.13.0.20260627/src/OpenCvSharp/Modules/core/Mat/Mat.cs#L2738).

변경 전/후 Release 실행물을 따로 보관하고 독립 프로세스·새 캐시로5회씩 측정했다. 실행 순서는 번갈아 배치하고 OS 캐시는 비우지 않았다. 측정 중 빌드/다른 성능 실험을 병렬 실행하지 않았다. 원본 입력·일반 측정기는 동일하며 디코더 DLL 해시는 서로 다르고 공통 피라미드 DLL 해시는 같다.

| 입력 | 변경 전 준비 ms | 변경 후 준비 ms | 판정 |
|---|---:|---:|---|
| 8K 컬러 JPEG | **1363.8** (1328.6~1380.3) | **979.6** (974.6~991.6) | 중앙값28.2% 단축, 범위가 분리됨 |
| 24K×8K Gray16 | 752.3 (728.0~1021.8) | 764.3 (734.3~786.6) | 유의미한 개선 근거 없음 |

괄호는5회의 최소~최대다. 컬러 개선이 확인돼 이 작은 변경을 유지한다. Gray16 개선이나 타일 읽기 개선으로 표현하지 않는다. 타일 엔진의 실행물은 동일하므로 부수적으로 변한 타일 p95를 이 변경의 효과로 주장하지 않는다.

별도 JPEG 구간 진단에서는 디코드가490→470ms, 채널 변환/원본 저장이599→196ms였다. 원래 가장 컸던 변환/저장 구간이 줄어든 것을 뒷받침한다. 한 번씩의 구간 값이므로 이 차이를 여러 단계의 독립적인 최적화 효과로 합산하지 않는다.

JPEG 전용 할당 피크는5회 중앙값211.5→210.9MiB, RAM 상주는296.8→296.3MiB였다. Gray16은 전용 할당403.2→403.2MiB다. **메모리 개선은 없다.** 최초 NetVips JPEG 약0.90초와도 세션/반복 조건이 다르므로, 개선 후 NetVips보다 빨라졌다고 주장하지 않는다.

## 추가 개선의 우선순위

| 순서 | 후보 | 기대하는 변화와 검증할 대가 | 현재 상태 |
|---|---|---|---|
| 1 | TIFF/라인 스캔 파일을 strip/tile 또는 행 단위로 디코딩하는 어댑터 | 전체384MiB 또는3/6GiB Mat을 제거할 수 있는 방향. 코덱 작업 버퍼·OS 캐시·취소·압축 TIFF/BigTIFF 호환성과 속도는 별도 측정 필요 | 설계 검토만 수행 |
| 2 | C# 피라미드의 정수 SIMD | JPEG 진단의 축소 단계 약220ms, Gray16 약239ms가 후보. 축별 반올림·홀수 중심·Gray16 원본 범위를 보존해야 함. 전체 시간 중 일부라 전체 속도가 SIMD 배수만큼 빨라지지는 않음 | 미구현·성능 미측정 |
| 3 | 타일 읽기에 제한된 매핑 창 또는 명시적 파일 읽기 사용 | RAM 상주 페이지를 제한하기 쉬워지지만 매핑 생성/해제·읽기 호출이 늘어 현재 타일 지연 이득을 잃을 수 있음. OS 전체 캐시 상한과 구별 | 미구현·성능 미측정 |
| 4 | 원본 기록과 하위 단계 생성을 스트리밍으로 결합 | 현재 단계별 raw 재읽기와 대형 입력 매핑을 줄일 후보. 경계 행/병렬도/취소·완료 캐시 게시를 보존해야 하며 변경 범위가 큼 | 미구현·성능 미측정 |
| 5 | 기존 NetVips reader의 Region 수명 재사용 | 현재 타일마다 Region 생성/해제. 단일 소유 worker 안에서의 재사용 후보이며 스레드 소유권·native 해제 계약 확인 필요. NetVips를 유지하는 쪽의 별도 개선 가능성 | 생산 코드 변경 없음 |

현재 권장은 **메모리와 초대형 파일 지원에는 스트리밍 디코더를 먼저 검증하고, 자체 엔진 계산 최적화는 그 다음에 하는 것**이다. `ImRead`의 픽셀 제한을 올리는 것만으로 메모리를 개선할 수는 없다. Windows 전용 디코더로 옮기지 않고 기존 `IRasterDecoder/IRasterReader` 경계에 Windows/Linux 공통 구현을 붙이는 방향을 유지한다. 이 후보들의 예상 수치를 실측 성과로 표현하지 않으며 이번에 구현하지 않았다.

구체적인 후속 후보로 LibTIFF는 사용자 버퍼에 [타일을 디코딩](https://libtiff.gitlab.io/libtiff/functions/TIFFReadEncodedTile.html)하거나 [행을 읽는 API](https://libtiff.gitlab.io/libtiff/functions/TIFFReadScanline.html)를 제공한다. 다만 압축 strip의 비순차 읽기와 일부 YCbCr 행 읽기에는 제약이 있어 실제 파일 형식을 검증해야 한다. 새 의존성을 도입한 것은 아니다. NetVips Region 재사용도 [같은 스레드에서 생성·사용·해제](https://www.libvips.org/API/current/class.Region.html)해야 한다. 논리적으로 호출이 직렬이라는 사실만으로 async worker의 물리 스레드가 같다고 가정하면 안 된다.

## 검증·재현·범위

- PASS: 6개 fixture의 원본·피라미드 결정적 픽셀 표본 오차0, 공통 엔진14개 테스트, Windows Release 빌드, Linux x64 publish. Linux 실실행은 NOT_RUN이다.
- PASS: 변경 전/후5회씩20개 일반 성능 실행. 별도 메모리 진단8개와 JPEG 변경 후1개. 재현 스크립트는 추가1회씩의 smoke로 동작 확인했으며5회 통계에 혼합하지 않았다.
- 원본 성능: `artifacts/pyramid-memory/paired-width/reports.json`. 진단: 같은 상위 폴더의 `phases-*.json`. [실행 명령](../experiments/PyramidComparison/README.md).
- [SOLID5/GRASP9 검토표](../experiments/PyramidComparison/README.md#설계-검토)를 이 변경에도 재확인했다. reader 내부 지역값 재사용으로 SRP·응집·소유권을 보존하고, 진단은 콘솔 호스트에 두어 공통 계약·플랫폼 경계를 바꾸지 않았다. 기존 예외·취소·픽셀 동등성으로 LSP를 확인했다. 원칙 예외 없음.
- 생산 앱/렌더러/검사 수정 없음. 원본 전체 Mat과 초대형 OpenCV 제한은 남는다. Linux 실제 동작, 다른 장비, 현장 이미지, 메모리 압박/장시간 반복, 화면60FPS는 이번 검증의 범위가 아니다. 커밋·푸시 없음.
