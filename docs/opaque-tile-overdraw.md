# 불투명 타일의 중복 그리기 제거

2026-10-13, `main` 로컬 변경·검증. 사용자의 범용 개선 요청에 따라 기존 `ScenePainter.cs`, `SpritePipeline.cs` 두 파일 안에서 화면에 기여하지 않는 개요 이미지 그리기를 줄였다. 새 의존성·CPU 모델별 분기·병렬도 상수·문서 구조 변경·설계 원칙 예외·커밋/푸시는 없다.

## 변경과 정확성 조건

기존에는 개요 이미지를 먼저 그리고 준비된 상세 타일을 그 위에 그렸다. 가시 영역의 타일이 전부 불투명하면 개요 이미지는 완전히 가려지는데도 매 프레임 샘플링·블렌딩했다. 이제 가시 타일 전체가 업로드됐고, 불투명하고, 필요한 타일 크기를 채울 때만 이 첫 그리기를 생략한다. 반복 ROI 시험과 일반 파일 이미지가 같은 경로를 사용한다.

Gray8/Gray16은 기존 셰이더가 알파1을 출력한다. RGBA/BGRA는 정적 업로드에서 유효 픽셀의 알파를 한 번 검사해 텍스처에 기록한다. 추가 비용은 업로드 픽셀 수에 비례하고, 퇴출 후 재업로드하면 다시 검사한다. 라이브 `Update`에는 이 순회를 추가하지 않고 색상 텍스처의 불투명 정보를 보수적으로 초기화한다. 초기 로딩이 더 빨라졌다고 주장하지 않는다.

투명 타일·로딩 누락·미업로드·부족한 크기는 기존 개요 표시를 유지한다. 기존 샘플링, 이미지/타일 좌표, 미니맵의 개요 이미지, ROI 윤곽·ID·이력, 두 frame slot·fence·Present(1)은 보존한다. 화면 축소 요약을 실제 개별 ROI 전체 그리기로 표현하지 않는다.

## 측정 조건과 결과

[앞선 CPU 챌린지](repeated-roi-cpu-challenge.md)의 최종 코드를 비교 기준으로 사용했다. Ryzen 5 5600H/논리 프로세서12/RAM32GB, RTX3060 Laptop, 8192×8192 PCB,100,020,001개 반복 ROI, 개별 수정1개,1171.33×698.15DIP·DPI1.5다. 구간별1초 워밍업 후4초간 연속 입력을 측정한다. Debug OFF, metrics/profile ON. 빌드·테스트와 성능 실행은 겹치지 않는다.

| 첫 비교 | 변경 전 | 변경 후 |
|---|---:|---:|
| WARP 상세 이동·회전/개별 편집 평균 제출 FPS | 35.68~36.06 | 58.95~60.06 |
| 같은 구간 제출 간격 p95 | 34.90~35.01ms | 20.98~21.12ms |
| 같은 구간 프레임당 프로세스 CPU 시간 | 134.91~139.87ms | 95.05~102.16ms |
| GPU 상세/개별 렌더 시간 p95 | 5.62~6.16ms | 4.48~4.84ms |

프로세스 CPU 시간은 모든 앱 스레드의 사용자+커널 CPU 시간 합이며, 표시 준비/fence 대기가 포함된 기존 `cpu_ms` 경과 시간과 다르다. 첫 비교의 프레임당 CPU 비용은 대응 구간별약25~31% 감소했다. 더 많은 프레임을 처리하므로 초당 CPU 사용량도 같은 비율로 줄었다는 뜻은 아니다. DWM·다른 프로세스는 제외된다.

WARP는 변경 전/후를 각각2회 실행했다. 두 번째 비교는 순서를 뒤집어 변경 후→변경 전으로 측정하고, 변경 전 DLL의 해시가 첫 기준 실행과 같음을 확인했다. 상세/개별 구간은 변경 전35.94~36.06FPS·프레임당155.38~163.09CPUms, 변경 후58.95~60.06FPS·92.12~99.71CPUms였다. 대응 구간의 비용 감소는약36~44%이며, 앞선 비교와의 차이를 숨기지 않는다. 두 번 모두 FPS 개선은 재현됐다. GPU는 전/후 각1회 비교다.

런타임 profile에서도 화면 맞춤348→342정점/12→11배치, 상세 이동·회전336→330정점/10→9배치로 실제 이미지 quad1개의 제거를 확인했다. 더 많은 ROI를 요약하거나 품질을 낮춰 얻은 수치가 아니다. 최종 복원된 DLL은 측정한 개선본과 같은 SHA256(`91B63F9357492220E54E6784780DD00D076EAC008F294781F5076BCFEC19085B`)이다.

GPU 평균 제출은 약60FPS이며, 렌더 시간이 줄어도 모니터 표시 대기에 따른 제출 상한은 유지된다. **CPU/GPU 모두 모든 프레임16.67ms 이내라는 엄격한60FPS 수용 조건은 여전히 FAIL**이다. 평균 FPS만으로 목표 달성을 선언하지 않는다.

## 검증

- PASS: 전체 Release 솔루션 빌드 경고0/오류0, Canvas219개 실패·건너뜀0.
- PASS: 추가13개 테스트 — Gray8/16, RGBA/BGRA 첫·마지막 알파, 불완전/투명 타일, 부분 경계 타일, 이동·확대·DPI, 단일 단계 이미지, 미니맵 보존.
- PASS: 생략 조건의 부정을 제거하는 변이 시험에서9개 실패 확인, 소스 복원 후 전체219개 통과.
- PASS: 변경 C#3파일 스타일 검사, `git diff --check`. 범위 밖 코드는 포맷하지 않았다.
- PASS: 같은 backend의 변경 전후 상세/화면 맞춤 PNG SHA256 동일. CPU/GPU 간 픽셀이 같다는 주장은 아니다.
- PASS: native 더블클릭 선택 교체·개별 이동/회전·Undo/Redo·취소 및 개수 검증, 읽기 전용 독립 리뷰.
- NOT_RUN: 다른 CPU·GPU·화면 해상도, 실제24K 파일, 많은 개별 수정, 장시간·복합 부하. 범용 코드 개선이 모든 장비의 같은 향상률이나60FPS를 보장하지 않는다.

원시 자료는 로컬 `artifacts/portable-{before,after}-{warp,gpu}*`에 둔다. 실행 DLL 및 셰이더 해시, CPU 합계, 각 구간의 엄격한 판정은 [보관 결과](opaque-tile-overdraw-results.json)에 기록한다. 반복 측정도 같은 파일 형식을 사용한다. 기존 WPR의 OS 프로파일 권한 오류는 해소하지 않았으며, 함수별 네이티브 스택을 확보했다고 주장하지 않는다.

재현은 기존 `--repeated-roi-benchmark --software-rendering --roi-report ... --metrics ... --render-profile ...` 및 `scripts/Measure-RepeatedRoi.ps1`을 사용한다. GPU 비교는 `--software-rendering`만 생략한다.

## 원칙 검토

| 원칙 | 검토 |
|---|---|
| SRP | 업로더는 픽셀/텍스처 메타데이터, Painter는 화면 그리기 판단을 소유 |
| OCP | 기존 내부 경로만 수정, 새 backend/공개 확장 지점 없음 |
| LSP | GPU/WARP 모두 같은 불투명 판정과 기존 투명/누락 fallback 유지 |
| ISP | 공개 인터페이스 추가 없음 |
| DIP | Core/영상 계약에 DX12 의존성 추가 없음 |
| Information Expert | 실제 픽셀을 받은 업로더와 가시 타일을 가진 Painter가 각각 판단 |
| Creator | 텍스처 생성·해제·버퍼 소유권 유지 |
| Controller | 입력/편집 요청 경로는 변경 대상 아님 |
| Low Coupling | 두 기존 렌더 컴포넌트 내부 메타데이터만 연결 |
| High Cohesion | 이미지 그리기와 관계없는 코드 변경 없음 |
| Polymorphism | 새 대체 구현 없음, 기존 GPU/WARP 공통 동작 보존 |
| Pure Fabrication | GPU 메타데이터는 기존 기술 컴포넌트에 유지 |
| Indirection | 기존 RenderScene/타일 업로드 경계 유지 |
| Protected Variations | 이미지 종류·투명도·로딩 상태의 차이를 렌더 내부에서 처리, 도메인 불변 |
