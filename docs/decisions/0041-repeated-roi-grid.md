# ADR-041 — 1억 개 반복 ROI의 개별 편집 시험

> 후속: 사용자가 메인 편집기 통합과 공통 문서 확장을 승인했다. 현재 버튼·선택·복붙·이력은 [ADR-042](0042-main-editor-repeated-rois.md)를 따른다. 아래 별도 창 설명과 수치는 이전 시험의 이력이다.

- 날짜: 2026-10-13
- 상태: 구현, 엄격한 60FPS 수용은 미달. [실측·제약](../repeated-roi-validation.md).
- 사용자 확정: 반복 격자이되 각 ROI를 개별 선택·편집 가능. `main`의 로컬 변경·검증만 수행하며 커밋/푸시하지 않는다.
- 같은 날 후속: 전체 구조 변경 없이 기존 DX12 표시 준비 대기와 최신 장면 소비 순서를 개선했다. [비교·수명 계약·원칙 검토](../dx12-frame-pacing.md). 전체 구조 변경이 필요하면 사용자에게 먼저 질문한다.

## 문제와 선택

기존 `DocumentState.Rois`의 객체·GUID·공간 색인을 100,020,001개 생성하는 방식은 32GB 장비의 작업 메모리에 맞지 않는다. 실제 배열을 만들지 않고 개수만 표시하거나, 하나의 그림으로 바꿔 개별 편집을 없애는 방식도 요구와 맞지 않는다. 반복 격자의 공통 정보와 개별 수정값을 분리한다. 이는 저장 표현 변경이며 실제 ROI 좌표·선택·이력을 생략하는 예외가 아니다.

메인 화면의 **1억 ROI 테스트**는 별도 편집 시험 창을 연다. 동일한 `Dx12Viewport`와 영상 타일·입력·렌더 스레드를 사용한다. 기존 일반 ROI 문서에 1억 개의 `Roi`를 추가하지 않는다. 이 창의 문서와 이력은 메인 문서와 독립적이며 메인의 검사 레시피 통합 이력을 분리하거나 대체하지 않는다. 일반 ROI의 계층·필터·마스크·검사·복사·저장 기능을 이 시험 문서에 연결한 것은 아니다.

## 구현 계약

1. `RepeatedRoiGrid`는 10,001×10,001=100,020,001개의 사각형을 가진다. 행·열 기반 ID, 간격, 공통 중심·각도와 불변 개별 수정 사전을 저장한다. 기본 격자는 이미지 중심에서 짧은 축의 약45%를 차지한다. 전체 이동·회전은 공통 pose만 갱신하고 개별 수정 사전 identity를 공유한다.
2. 개별 ROI는 더블클릭 또는 행·열 입력으로 선택한다. 이동·회전·중심·너비·높이·각도 수정은 해당 ID의 실제 형상을 대체한다. 원래 자리의 ROI는 상세 셰이더와 히트 테스트에서 제외한다. 밀집한 후보는 실제 도형의 허용 거리 안에서 가장 가까운 중심을 선택하며 동점은 큰 ID로 결정한다.
3. 수정되지 않은 격자 구간은 실제 셀들의 convex hull과 같은 사각형들로 분할한다. 개별 수정 형상과 함께 기존 `RoiSpatialIndex`의 이동/회전 이미지 경계 제한을 사용한다. 모든 셀을 순회하거나, 비어 있는 수정 전 모서리까지 회전 제한에 포함하지 않는다.
4. `RepeatedRoiSession`은 불변 상태와 gesture 전후 Memento를 소유한다. Esc는 원래 snapshot으로 복원한다. 편집 완료 한 번당 이력 한 건이며 선택·탐색·무변경 클릭은 Redo를 버리지 않는다. 이력은 최대200건/보수적 추정1GiB로 제한한다. 한 건이 예산을 넘으면 원상 복구하고 오류를 표시한다. 이는 실제 프로세스 메모리 상한이 아니다.
5. `RepeatedRoiPipeline`은 화면 픽셀에서 격자 셀을 계산한다. 1억 instance를 업로드하지 않는다. 세부 배율에서는 개별 사각형 윤곽을 표시하고, 3 DIP 미만 간격에서는 범위 요약 윤곽과 안내 문구를 표시한다. 수정된 셀은 별도 실제 윤곽으로 표시한다. GPU 자원은 렌더 스레드가 소유하고 두 frame slot의 업로드 공간은 fence 완료 후 재사용한다.
6. 전체 변환 비용은 미수정 셀 개수에 비례하지 않는다. 다만 수정 사전 검색·경계 준비·별도 윤곽 표시는 수정한 셀 수에 비례한다. 1억 셀 모두를 다른 형상으로 수정한 상태의 성능/메모리를 보장하지 않는다. 화면 크기·가시 면적·각도에 따른 픽셀 처리량도 동일하다고 주장하지 않는다.
7. `IViewportInput`은 실제 두 편집 문서의 공통 포인터 경계다. 기존 `Dx12Viewport.Input` 타입은 보존하고 `PointerInput`으로 반복 격자 입력을 연결한다. 메인 편집기에서도 `CS_DBLCLKS`/`WM_LBUTTONDBLCLK`를 받아 기존 선택의 핸들보다 클릭한 실제 ROI 선택을 우선한다. 첫 클릭의 미세 오차로 resize가 확정되지 않도록 시작점 기준2 DIP 임계값을 적용한다.

## 검증과 원칙 검토

전체 생성·변환의 작은 할당량, ID 경계, 수정 전 자리 제거, 조밀한 후보의 선택, 이미지 경계, 전수 형상과 회전 제한 동등성, Undo/Redo/취소를 Core에서 확인한다. 실제 HWND의 클릭→해제→더블클릭→해제와 GPU/WARP 실행을 별도로 확인한다. 측정은 제출 간격·GPU·CPU·입력 함수 시간·메모리·GC를 구분한다. `Present(1)`을 유지하고 제출 횟수를 늘리는 식으로 FPS 기준을 바꾸지 않는다.

| 원칙 | 이번 변경의 검토 |
|---|---|
| SRP | 격자 기하, 편집 이력, 포인터 gesture, WPF 바인딩, DX12 수명을 각각 기존 계층에 둠 |
| OCP | 기존 일반 문서 경로를 보존하고 반복 격자 장면·입력 구현을 추가 |
| LSP | 두 입력 구현 모두 Down/Move/Up/Cancel/탐색 계약 유지; native 메시지 회귀 포함 |
| ISP | 포인터 소비자가 사용하는 동작만 `IViewportInput`에 둠; 문서·검사 기능 강제 없음 |
| DIP | Core에 WPF/DX12/검사 의존성 없음; 창에서 입력·표시 연결 |
| Information Expert | 좌표·히트·불변 격자 분할은 Grid, 이력·이미지 제약 적용은 Session |
| Creator | Grid가 ID/배치 불변식을 검증하고 Pipeline이 GPU 자원을 생성·해제 |
| Controller | HWND는 좌표·메시지를 전달하고 Input이 Session 편집을 요청 |
| Low Coupling | 렌더러는 불변 Grid를 읽으며 앱 ViewModel·검사를 참조하지 않음 |
| High Cohesion | 새 파일은 반복 격자 편집 또는 표시 한 책임만 가짐 |
| Polymorphism | 실제 두 입력 구현을 동일 포인터 계약으로 처리 |
| Pure Fabrication | GPU 파이프라인/업로드 수명을 도메인과 분리 |
| Indirection | ViewModel/RenderScene이 도메인 상태와 UI/GPU를 연결 |
| Protected Variations | 영상 로더·GPU/WARP 선택·일반 문서 이력 계약 보존 |

성능 때문에 설계 원칙·정확성·이력을 완화한 예외는 없다. 원칙 준수와 목표 FPS 달성은 별개이며, 미달과 미검증 범위는 작업 목록에 남긴다.
