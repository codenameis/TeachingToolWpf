# ADR-027 — 논문 형상 매칭의 버튼 기준 CPU 125 ms와 CUDA 80 ms 미만

- 날짜: 2026-10-05
- 상태: 사용자 실행 요청으로 논문 입력·후보·표시 개선 일부 구현. 새 CPU125/CUDA80 ms 목표 수용은 FAIL, 전체 작업 미완료.
- 선행: [ADR-026](0026-8k-shape-search-latency.md). 기존 500 ms 측정/실패 기록을 보존하며 이번 논문 모드의 목표만 대체한다.
- 계획: [상세 단계와 수용 기준](../../tasks/paper-shape-125ms-plan.md). 진행 상태는 [todo](../../tasks/todo.md).

## 배경

사용자는 현재 8K 전체 탐색 CPU가 약 2초이며 CPU/GPU 성능 차이가 작다고 보고했다. 이번에는 논문 기반 패턴 매칭만 개선하고, 검사 실행을 누른 뒤 모두 끝날 때까지 CPU 125 ms 이하·CUDA 80 ms 미만을 요구했다. MIL CUDA/GTX 1070의 80 ms 미만은 사용자 제공 비교값이다. 앱의 8192² 샘플과 저장소의 `kensa.png`에서 임의 부품 하나를 학습한 전체 검색을 모두 확인하도록 지정했다.

소스는 LINE-2D 방향 응답 후보 검색·연속 방향 검증·robust point-to-line 정밀화·원본 추가 윤곽 감점을 조합한 C# 독립 구현이다. `meiqua/shape_based_matching`의 직접 포팅이 아니다. 현재 CUDA는 후보 점수만 담당하고 원본 입력·전처리·최종 검증은 CPU에 남는다. 과거 v4 논문 서비스 중앙값 CPU/GPU 336.9/305.6 ms와 실제 앱 원본 읽기 182.3 ms는 새 목표를 만족하지 못한다.

## 결정

1. 논문 CPU를 먼저 개선한다. 자체 기하/OpenCV는 동작을 보존하고 논문 전용 실행 전략을 선택적으로 연결한다. 작은 공유 최적화도 다른 방식의 회귀를 확인한다.
2. 종료는 서비스 반환이 아니라 같은 실행의 판정·전체 결과·화면 내 필수 검출 윤곽/라벨 표시 완료다. 실제 버튼 입력 수신부터 queue, 클릭 이후 장치/JIT 준비, 원본 읽기, 검색, 원본 판정, 자원 반환, UI 게시, 결과 프레임의 렌더 완료/Present까지 잰다. Present와 물리 scan-out의 차이는 공개한다.
3. 모델/장치 불변 준비와 학습·이미지 열기는 구별해 공개한다. 클릭 이후 발생한 비용을 빼지 않으며 검사별 영상 전처리/탐색을 클릭 이전으로 옮기거나 결과 cache를 재검사로 사용하지 않는다.
4. 원본 읽기·중복 전처리·작업 배치·모델 준비·CPU hot path를 먼저 계측/개선한다. CUDA는 모델 반복 전송·64회 창별 왕복·전체 grid 반환을 줄이고, 필요하면 중립 backend로 병목 단계의 배치 계산 범위를 넓힌다. 각 변경은 동일 정확성·조건의 전체 시간을 비교한다.
5. 8K 샘플 256핀 완전 검출·사선 점수 구분을 유지한다. `kensa.png`는 실제 1024×1536이며 별도 실파일 시험이다. 초기 대상은 메모리 칩, 육안 48개는 독립 annotation으로 확정한다. 8K 결과로 바꿔 부르지 않는다.
6. 후보/특징/각도/배율/최종 검증을 줄여 속도를 맞추지 않는다. 시간 초과·예산 잘림·출력 상한·오류는 불완전 결과다. CPU/GPU의 원본 점수·pose·순서·수명 동등성을 유지한다.
7. 현재 검사별 cache와 활성 작업 메모리 예산을 기본으로 보존한다. 더 큰 상주 메모리나 cache 공유가 필요하면 별도 계약으로 검토하며 미측정 상태에서 채택하지 않는다. 설계 원칙 예외는 승인된 것이 없다.

## 계획 단계의 검증 이력 (구현 전)

계획 수립 단계다. 과거 500 ms PASS를 새 125/80 ms PASS로 바꾸지 않는다. 이번 baseline 실행이 있더라도 CLI/서비스 결과는 버튼→표시 완료 수용 검증과 구별한다. 구현 단계에서는 두 fixture의 첫 실행·반복·정확성·실제 표시 장치 증거로 판단한다. SOLID 5개와 GRASP 9개의 적용 경계는 상세 계획에 기록했다.

계획 중 기존 Release CLI의 논문 kensa 검사 CPU/CUDA 각4프로세스를 실행했다. CPU 첫1906.5 ms, CUDA 첫3323.3 ms(초기 장치 준비 포함), 8회 모두44개·불완전 검색이었다. 후보/검증 예산 초과와 2 Mpx 이하 일반4창 순차 검색을 확인했다. 육안48개 정답 대응은 미확정이며 CLI의 DLL이 v4와 다르므로 소스와 일치하는 새 baseline이 필요하다. [계획의 재현 결과](../../tasks/paper-shape-125ms-plan.md) 및 [원시 ZIP](../data/paper-125ms-baseline-20261005.zip)을 따른다. 이 재현을 성능 달성 또는 현행 소스의 확정 실행 성능으로 표현하지 않는다.

8K 샘플도 기존 v4 benchmark로 재실행했다. 논문 CPU 첫479.3 ms/반복3회 중앙340.3 ms, CUDA 첫395.9 ms/중앙296.9 ms, 8회256개 일대일·CPU/GPU exact·잘림없음이었다. CUDA 준비626.3 ms 별도이며 첫검색과의 합은1022.1 ms다. 기존 도구의500 ms exit0과 새125/80목표 FAIL을 구별한다. kensa와 실행binary가 다르며 두 baseline 모두 버튼→표시 완료 측정은 아니다.

## 사용자 실행 요청 이후 적용

논문 선택형 pipeline, 원본 Gray8 계약과 동일 샘플 픽셀 생성, 첫 단계 학습 특징 재사용·9×9 국소 정수 SIMD, 작은 영상의64 px 피라미드 창, 결과 bitmap atlas·가상 목록을 채택했다. 기하 모델은 기존 검색 경로, OpenCV는 기존 서비스를 사용한다. 원본 추가 윤곽 감점·후보/출력 예산·회전/배율 범위를 유지했다. 공통 픽셀 생성과 hot method JIT 정책은 결과 동등성 회귀로 검증했으며 설계 원칙 예외는 없다.

Canvas 완료 통지는 공급자 비의존 overlay identity와 Present/GPU fence를 사용한다. WPF Rendering 이후 idle 관측은 실제 버튼 입력/DWM 완료를 보장하지 않아 최종 T5로 인증하지 않는다. 마지막 글자 atlas 캐시는 검사 결과를 재사용하지 않으며 원본 cache는 기존 검사별 수명을 유지한다.

같은 측정 도구의 변경 후8K 서비스 반복 중앙 CPU261.7/CUDA227.3 ms로 새 수용은 FAIL이다. kensa는48개 일대일·잘림 없음이지만 한 개 정밀화 Rejected/CHECK를 보존한다. P4 잔여 CPU 계산·앱 지연과 P5 CUDA 확대가 남았다. [구현 실측](../paper-shape-125ms-validation.md)과 [증거 ZIP](../data/paper-125ms-implementation-20261005.zip)에 성공·실패를 함께 기록한다.
