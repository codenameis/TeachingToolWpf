# ADR-060: 첫 이미지 준비 단계 측정과 픽셀을 보존하는 SIMD 축소

- 날짜: 2026-10-16
- 상태: 사용자 요청에 따른 로컬 구현·검증
- 범위: 공통 파일 로더의 삼각 피라미드 계산과 외부 측정 호스트

## 문제

`ken32.png`의 첫 열기가 재열기보다 매우 느리다. 사용자는 단계별 실측과 화질·정확도·설계 원칙을 보존하는 개선을 요청했다. 원본은17280×30720 RGBA8이며, 원본과 표시용 축소6단계를 처음에 준비한다. 카메라의 직접 픽셀 입력과 이 파일 준비 경로를 혼동하지 않는다.

## 결정

1. 기존 `IRasterDecoder`를 감싼 콘솔 측정으로 열기/디코딩/원본 쓰기 및 준비/각 축소 단계/캐시 재열기를 구분한다. WPF 명령→문서 반영→GPU 캡처 완료는 별도 테스트 호스트에서 측정한다. 샘플 앱에 진단 모드를 추가하지 않는다.
2. `TrianglePyramid` 안에서 Gray8/RGBA8의 세로 합산과 RGBA8의 가로 합산을 정수 SIMD로 묶는다. 짝수·홀수 크기의 기존 가중치, 축별 반올림, 가장자리 복제를 유지한다. Gray16과 짧은 행/꼬리/미지원 CPU의 기존 scalar 처리는 유지한다.
3. 새로운 패키지·공개 API·DI 계층을 추가하지 않는다. 기존 스트리밍 버퍼, 병렬 작업 상한, 취소, 소유권, 원자적 캐시 게시를 유지한다.
4. 캐시 형식/식별자를 바꾸지 않는다. 결과 바이트가 같으므로 기존 캐시를 계속 쓴다. 사용 중인 원래 캐시는 보존하고 실험마다 별도 새 캐시를 사용한다.
5. 모든 단계 전체 SHA256과 독립 합성곱 검증으로 픽셀 동등성을 확인한다. SIMD를 끈 프로세스도 시험한다. 정확도는 검사에 전달되는 원본 바이트의 불변성으로 확인하며, 현장 알고리즘 정확도를 새로 검증했다고 표현하지 않는다.

## 결과와 한계

새 애플리케이션 캐시3회씩의 콘솔 준비 중앙값은7.410→6.831초, 축소 단계 합계는1.659→1.127초다. PNG 디코딩 약5초는 여전히 가장 큰 비용이다. PNG 입력 버퍼 확대는 탐색 측정에서 개선이 없어 채택하지 않았다.

WPF의 명령→캡처 중앙값은8.184→8.117초이고 범위가 겹친다. 앱 전체 표시 개선의 반복성은 확인되지 않았다. 캡처는 GPU readback/PNG 인코딩/폴링까지 포함하며 물리 모니터 scan-out이 아니다. OS 파일 캐시를 비우거나 PC를 재부팅하지 않았으므로 물리 디스크 cold-start 결과도 아니다.

재부팅만으로 영구 raw 캐시가 없어지지는 않는다. 원본 변경/경로 변경/캐시 회수 시에는 다시 준비할 수 있다. 실제 카메라 SDK 수집·전송·픽셀 변환·업로드의 속도는 별도 측정해야 한다.
