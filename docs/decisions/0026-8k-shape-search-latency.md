# ADR-026 — 8K 형상 검색의 500 ms 목표와 CUDA 세션

- 날짜: 2026-10-05
- 상태: 채택·구현. 최종 v4 일반 앱 첫 CPU 459.0 ms/준비 후 GPU 375.0 ms, 서비스 benchmark 32회·정상 표시 WPF 서비스 16회·전체 테스트 878개 PASS. 최초 GPU 준비·숨김 창 명령·별도 파일 미달과 과거 수동 실패는 보존한다. [실측](../shape-500ms-validation.md)과 작업 목록의 범위를 따른다.
- 요구: 앱의 8192×8192 PCB 샘플에서 논문/기하 두 방식 모두 256핀을 500 ms 안에 검사하고 사선의 점수를 구별한다. GPU는 같은 결과를 더 빨리 반환해야 한다.

## 확인된 비용

종전 CPU 4의 전체 검사는 약 2.15초였다. 64개 거친 창을 순차 검색하고, 256개 원본 crop마다 같은 scalar 평활화·미분·방향맵 연산을 반복했다. 샘플의 원본 픽셀 생성·명암 변환에도 약 1초가 들었다. CUDA는 매 검사 생성·해제에 반복 약 190~200 ms를 쓰고 작은 crop 전처리를 수백 번 왕복했다.

## 결정

1. 픽셀 값과 판정 수식을 유지하는 SIMD 평활화·Sobel·면적 평균·방향 확산·응답 LUT·명암 변환·샘플 생성 경로를 사용한다. 비지원 CPU에서는 scalar 경로가 동작한다. Gaussian 전처리는 전체 float 임시 영상 2개 대신 수평 5행/평활화 3행 ring buffer를 사용하며 clamp와 산술 순서를 유지한다. 샘플 생성의 최적화는 픽셀 공급의 계산만 바꾸며, 매칭에 샘플 위치나 정답을 전달하지 않는다.
2. 원본 reader는 한 실행 흐름이 소유하고, 완성된 불변 crop만 제한된 CPU worker에 전달한다. 거친 작업 영상 합계 2 Mpx, 원본 병렬 crop 합계 2 Mpx 및 단일 crop 8 Mpx 예산을 유지한다. 빈 슬롯을 다음 작업으로 채우는 공통 스케줄러가 실행 슬롯·활성 픽셀·미게시 결과 수를 제한한다. 완료 순서가 후보 예산과 NMS 동률 결과를 바꾸지 않도록 원래 순서대로 게시하고 취소·실패에서도 worker 종료 후 reader/device를 반환한다.
3. 제안 pose의 점수가 현재 최댓값을 넘을 수 없다고 계산되는 경우에만 점수 계산을 일찍 끝낸다. 원래 후보·회전·배율·반복 횟수·임계값은 유지한다. 실제 gradient와 모델 법선의 상한을 사용하며 float 반올림 여유를 포함한다. 독립된 전체 계산과 최종 pose/score가 정확히 일치해야 한다.
4. `IShapeCandidateScorer`는 방향 bit·양자화 특징을 받아 정수 score grid를 반환하는 중립 계약이다. CUDA가 방향 확산·응답 LUT·여러 템플릿 점수를 일괄 계산하고, 임계값·후보 예산·연속 검증·최종 판정은 공통 CPU 코드가 담당한다. Algorithm과 Canvas에 CUDA/WPF 참조를 추가하지 않는다.
5. 후보 점수 CUDA 혼합 실행에서는 전처리와 원본 정밀 검증을 CPU worker가 담당한다. 입력 단계에 따른 고정 역할 분담이며, GPU 오류를 숨기는 자동 폴백이 아니다. GPU 후보 검색이 사용하지 않는 CPU 선형 응답 plane 8개는 만들지 않으며 원본 판정용 방향 자료는 유지한다. 기존 CUDA 평활화·Sobel 계약은 별도 보존한다. GPU 전체 정규화 실험은 약 1 ULP 차이가 최종 결과에 전파되어 폐기하고 CPU 정규화를 유지했다.
6. `CudaInspectionSession`은 앱 조립 지점/CLI가 소유한다. 최초 장치·커널 준비를 별도로 표시하고, 검사별 lease는 같은 장치와 bounded 작업 버퍼를 재사용한다. 준비 중/검사 중 앱 종료는 해당 작업이 끝난 뒤 해제하며, 오류 후 같은 장치를 조용히 재사용하지 않는다. 영상·검사 결과 캐시는 만들지 않는다.
7. 앱 형상 방식의 기본 CPU 병렬도는 사용 가능한 논리 프로세서 수(1~16 제한)로 둔다. 사용자는 기존 파라미터로 줄일 수 있다. 검사 worker의 수와 메모리 예산을 동시에 제한하고 UI 스레드에서 검사나 장치 대기를 하지 않는다.
8. 기준 장비용 `Publish-Sample.ps1 -InspectionLatency`는 ReadyToRun AVX2와 `TieredCompilation=false`로 게시한다. 일반 빌드·시스템 환경변수와 분리하고 실제 DLL 해시를 기록한다. CPU hot method 5개의 `AggressiveOptimization` 표시는 반복 성능 저하로 제거했으며 직접 축소 2개를 포함한 원본 I/O 6개의 표시는 유지했다. 프로파일별 실측을 다른 배포물의 보장으로 확대하지 않는다.

## 측정과 한계

최종 v4 게시물은 첫/최대 CPU 399.1698 ms를 포함한 서비스 32/32회를 통과했다. 논문 CPU/GPU 반복 중앙값은 336.9/305.6 ms, 기하 321.8/298.8 ms이며 256개 일대일·사선 점수 간격 .0294648·CPU/GPU record 동등을 유지했다. 최초 CUDA 준비 496.3 ms+첫 GPU 검색 342.4 ms는 838.7 ms로 500 ms 미달이다. 최종 878개 테스트/skip 0, 포맷·Release Rebuild·배포, 앱/benchmark의 Algorithm·Inspection·Imaging DLL 해시 일치를 확인했다.

일반 앱을 별도로 실행한 수동 첫 논문 CPU 검사는 459.0 ms(읽기 182.3 ms), 준비 후 첫 GPU는 375.0 ms(읽기 185.4 ms)로 각각 256개를 검출했다. 최초 GPU 준비 표시 470.6 ms는 별도다. 실제 화면과 접근성 기록 3쌍을 보관하고 확대 화면에서 깨끗한 핀 1.000/사선 핀 .957을 확인했다. 최종 기능 smoke exit 0과 SIMD 미사용 샘플 생성 3회귀도 통과했다.

정상 표시 WPF 진단은 서비스·정확성 16/16회, CPU 명령 8/8회, 최초 GPU 준비를 제외한 명령 15/15회가 통과했다. 첫 CPU 서비스 440.4 ms/명령 455.7433 ms지만 첫 GPU 명령은 준비 포함 907.6588 ms로 FAIL이다. 동일 DLL의 숨김 창 진단은 서비스·정확성 16회 PASS와 달리 모든 명령이 1028.5~2281.0 ms로 실패했다. 숨김 창의 스케줄링 영향은 추정이며 원인 확정·해결은 미완료다. 두 원본 JSON의 종합 FAIL을 유지하고 정상 표시의 통과를 모든 실행 조건의 보장으로 확대하지 않는다. 명령 완료와 화면 Present 완료도 구별한다.

[고정 수용 기준](../../tasks/shape-500ms-plan.md)의 원본 읽기 포함 서비스 wall time으로 판단한다. 최초 JIT, 장치 준비, 학습, 반복 검사 시간을 서로 구별한다. CPU/GPU 실행 순서를 교대로 두며 warm median 하나만으로 500 ms를 통과 처리하지 않는다. 측정용 JSON 직렬화는 모든 timed run 이후 한 번만 수행한다. 실제 앱 표시에는 검색 시간과 최초 GPU 준비를 함께 보여주도록 연결했으며 네이티브 화면 검증 상태는 작업 목록을 따른다. 동일한 샘플 통과를 임의의 실제 촬영 영상 전체의 성능으로 표현하지 않는다.

v2 서비스 32회는 첫 CPU 473.9 ms를 포함하여 모두 500 ms 이내, 256핀 일대일·점수 간격 .0294648·CPU/GPU record 동등을 통과했다. 반복 중앙값은 논문 CPU/GPU 374.6/349.0 ms, 기하 CPU/GPU 356.2/336.6 ms다. 주 측정 CUDA 준비는 별도 492.4 ms다.

실제 WPF 두 프로세스의 서비스 32회도 모두 500 ms를 통과했다. 첫 CPU 서비스는 482.8/483.0 ms, 전체 명령은 497.6/498.8 ms로 여유가 1.2~2.4 ms뿐이다. 학습·화면 준비는 별도이며 각 명령 전 공개 렌더 통지의 750 ms 정지를 관찰했다. 모든 부하나 화면 Present까지의 500 ms 보장을 뜻하지 않는다. GPU 최초 준비 600.9/514.2 ms가 포함된 명령은 1006.9/946.7 ms로 FAIL이다. 나머지 준비된 명령은 통과했지만 두 WPF JSON의 종합 FAIL을 변경하지 않는다.

v1 별도 Gray8 파일의 CPU 4는 핀 약 790 ms, 큰 ROI 약 1.8초, 회전·잡음 약 600 ms로 정확성 PASS/속도 FAIL이며 최종 v4 전체 파일 재측정은 하지 않았다. v1 실제 앱 첫 논문 CPU 522.5 ms FAIL과 반복 458.7/462.2 ms도 보존한다. 최종 v2 테스트는 877 PASS/skip 0, 포맷·Release 빌드·배포를 확인했다. 현장 데이터, Linux, 이번 변경의 24K 속도는 미검증이다. 상세 수치·해시·원본 보고서는 [검증 문서](../shape-500ms-validation.md)에 둔다.

## 실제 앱 첫 실패 후 추가 I/O 결정

RGBA/BGRA 정수 변환을 AVX2 16픽셀 인접 곱셈·합산으로 계산한다. 150G를 22G+128G로 분리해 signed byte 포화를 피하고 기존 가중치·반올림·알파 무시·lane 순서를 보존한다. 2배/4배 타일 축소는 `InspectionTileReducer`가 독립 소유 `PixelBuffer`에 직접 쓰며 4배도 두 단계의 2×2 반올림을 유지한다. 이 책임은 검사 I/O의 버퍼 소유 경계에 두고 알고리즘의 공통 피라미드 정책을 대체하지 않는다. 다른 배율·좁은 경계·미지원 CPU는 기존 계산을 사용하며 factor 1의 stride도 행 단위로 처리한다. 취소·실패 시 미게시 결과 버퍼를 반환하고 기존 cache 예산을 유지한다.

64 Mi픽셀/폭 512/9회 중앙값의 부분 연산 측정에서 RGBA 18.6430→7.6267 ms, BGRA 18.5128→7.8156 ms, 2배 축소 6.2095→1.4358 ms, 4배 축소 7.6939→1.4727 ms였다. 4배 축소의 측정 반복당 managed 신규 할당은 21,018,624→10,240 byte이며 pool 보유량이나 전체 메모리 상한이 아니다. 부분 연산 이득을 전체 검사 이득으로 더하지 않는다. 증거는 `artifacts/gray-avx2-micro/results.jsonl`, `artifacts/tile-reducer-micro/results.jsonl`이다.

전수 RGB·tail·독립 반복 축소·반올림·취소 집중 16개와 v2 전체 suite 877개는 PASS다. `--shape-target-smoke --shape-target-show`는 기존 앱 기본값과 실제 ViewModel을 통해 프로세스별 16회 검사하고 명령 wall time/표시 서비스 시간을 구분한다. GPU 준비까지 포함한 최초 명령의 500 ms FAIL과 이전 v1 첫 522.5 ms 실패도 보존했다. v1 수동 실행과 v2 화면 안정 관찰, 서비스 교대 순서와 WPF 모드별 순서는 서로 다르므로 차이를 모두 코드 효과로 돌리지 않는다. 설계 원칙 예외는 추가하지 않는다.

## 원칙 검토

v2 일반 앱 첫 검사 536.8 ms(읽기 192.7 ms)는 별도 FAIL로 보존했다. 화면 안정 관찰을 사용하는 WPF 진단의 통과로 이 결과를 대체하지 않는다. v4 후보에는 `SampleDirection`의 `AggressiveInlining` 한 줄과 샘플 X 마스크·잡음 계산 재사용만 추가한다. 동일 bilinear 산술과 판정 계약을 유지한다. I/O 6개 `AggressiveOptimization` 제거는 v3-probe 지연 악화로 복원했으며 최종 후보에도 유지한다. v3-hoist 첫 543.1/485.0 ms와 v4-inline 첫 450.7/408.5 ms의 원본을 모두 보존했다. v4 서비스 32/32회·정확성 통과와 최종 일반 앱 성능을 구별하며 아래 원칙 검토는 유지한다.

| 원칙 | 검토 |
|---|---|
| SRP | gradient·방향맵·후보 검색·원본 읽기·작업 스케줄·장치 수명 책임을 분리 |
| OCP | 중립 후보 점수 계약으로 CUDA 구현을 주입 |
| LSP | 픽셀/정수 점수/최종 pose와 score 동등성, 취소·실패·해제 계약 유지 |
| ISP | 전처리·후보 점수·장치 사전 준비를 별도 작은 계약으로 제공 |
| DIP | Algorithm은 중립 타입만, CUDA 조립과 세션 소유는 앱/CLI |
| Information Expert | gradient 상한은 gradient, 응답 주소·LUT는 방향맵, 픽셀 변환은 영상 어댑터 |
| Creator | 모델·영상 자료와 CUDA 버퍼는 각각 학습기/전처리기/장치 소유자가 생성 |
| Controller | UI는 준비·검사 요청만 수행하고 판정 연산을 갖지 않음 |
| Low Coupling | 원본 reader·CPU worker·CUDA가 명시적 불변 데이터와 lease로 연결 |
| High Cohesion | 수치 kernel과 자원 수명에 서로의 업무 정책을 섞지 않음 |
| Polymorphism | 실제 CPU/GPU 점수 구현만 대체하며 가짜 공급자는 추가하지 않음 |
| Pure Fabrication | 스케줄러·CUDA 세션은 명확한 기술 책임에 한정 |
| Indirection | libvips native 호출과 CUDA는 각각 작은 플랫폼 경계에 격리 |
| Protected Variations | SIMD 미지원 CPU·Windows/Linux ABI·기존 직렬화 이름의 변경을 경계에서 처리 |

사용자 승인이 필요한 설계 원칙 예외는 적용하지 않았다.
