# ADR-009 — 대량 편집 준비와 UI 응답성

상태: 적용. 2026-10-02. 성능 수치·실행 조건·미검증 범위는 [저사양 조건 성능 기록](../low-spec-performance.md)에 둔다. [ADR-001](0001-quality-and-edit-history.md), [ADR-007](0007-bulk-paste-and-minimap.md), [ADR-008](0008-retained-roi-rendering.md)의 정확한 문서·이력·GPU 소유권 계약을 유지한다. ADR-007의 대량 붙여넣기에서 이력 생성과 목록 구축을 UI에서 수행하던 경계를 이 결정으로 확장한다.

## 문제

ROI 그리기와 이동 preview의 반복 비용을 줄여도 전체 선택·삭제·붙여넣기·이동 확정·Undo/Redo는 많은 값을 순회한다. 이 작업을 UI 스레드에서 수행하면 GPU가 계속 표시할 수 있어도 입력과 WPF 상태 갱신이 멈춘다. Undo 준비는 ViewModel·이미지 조정자·실제 적용 경로에서 같은 결과를 반복 계산했고, 목록의 항목 교체는 WPF 선택 해석과 컨테이너 갱신을 유발했다.

목표는 원본 ROI를 생략하거나 이력을 줄여 작업량을 숨기는 것이 아니라, 중복 계산을 없애고 대량 준비 동안에도 탐색·취소 입력을 처리하는 것이다. UI에서 명령을 받은 시간, 준비 완료까지의 시간, Dispatcher 지연, 렌더/GPU 시간은 별도로 측정한다.

## 결정

### 단일 준비 작업과 확정 경계

1. 앱은 문서를 바꾸는 준비 작업을 한 번에 하나만 실행한다. 기다리는 편집 명령을 무제한 적재하지 않는다. ViewModel의 편집 작업과 `ImageCoordinator`의 이미지/이력 작업은 `CanEdit`로 서로 중복 실행을 막는다. 필터·렌더 작업의 기존 별도 소유권은 유지한다.
2. UI에서 현재 불변 문서, 선택, 세션 revision, preview epoch와 필요한 명령 입력을 확보한다. 작업 스레드는 결과 문서·변경 이력·즉시 사용할 인덱스 및 필요한 ROI 목록을 준비한다. 작업 스레드가 현재 세션이나 WPF 컨트롤을 수정하지 않는다.
3. UI로 돌아오면 취소와 결과의 유효성을 검사하고 한 번만 게시한다. `PreparedEditorChange`는 소유 세션, 문서/선택/이미지 변경 revision, preview epoch, 사용 완료 여부를 검증한다. 이동 preview의 delta 변경도 revision에 반영하므로 준비 시작 뒤 바뀐 preview를 옛 결과가 덮어쓰지 않는다.
4. 준비 중에는 ROI 변경과 선택 변경 명령을 잠그되 pan/zoom·미니맵 탐색은 허용한다. `InteractionController.NavigationOnly`가 포인터의 편집 시작과 hover 조회를 막고 탐색 입력은 기존 뷰 명령으로 보낸다. 준비한 ROI 편집의 확정은 그동안 변경된 현재 viewport를 유지한다.
5. 전체 선택·삭제·큰 마퀴 선택·대량 붙여넣기와 대량 preview 확정을 이 경계에 연결한다. 4,096개 초과 문서의 방향키 이동도 같은 준비 경로를 사용한다. 작은 편집의 기존 동기 경로도 같은 Core 규칙과 이력을 사용한다. 회전/resize의 드래그 샘플마다 수행하는 형상 계산이나 모든 동기 명령이 자동으로 작업 스레드로 바뀐 것은 아니다.

`PreparedEditorChange`는 불변 결과와 검증 토큰을 운반하고, 사용 완료 표시는 UI에서만 바꾼다. 실행 도중 작업 스레드가 mutable 세션을 검색하는 서비스 로케이터나 일반 작업 실행 엔진을 추가하지 않는다.

### 이력 준비와 재사용

`EditHistory.CaptureUndo/CaptureRedo`는 현재 명령·방향·cursor·history revision·소유 이력 식별자를 상수 시간에 확보한다. `HistoryStep.Prepare`가 불변 입력 문서에 delta를 적용하고 `PreparedHistoryStep`을 반환한다. `Validate`는 source 전송 전 검증에 쓰며 `Commit`에서도 다시 호출한다. source의 ROI 맵·선택 참조와 이미지, history 식별자·revision·cursor·명령이 맞아야 적용한다.

동일 이미지의 빈 문서를 다시 여는 이력처럼 문서 값이 같아도 cursor는 달라질 수 있다. 따라서 세션의 문서 revision만으로 이력 결과를 검증하지 않는다. 이미 사용한 결과나 다른 이력의 결과는 거부하고 cursor는 한 번만 이동한다.

ROI만 복원하는 Undo/Redo는 준비 중 변경된 현재 viewport를 보존한다. 이미지 변경 이력은 기록된 viewport를 복원한다. 형상·ID·이름·필터·부모 관계·선택은 기록된 값으로 복원하며 Undo 시 계층을 재판정하지 않는다.

기존 동기 `PreviewUndo/PreviewRedo/Undo/Redo`도 유지한다. 정확히 같은 입력 `DocumentState` 참조·방향·명령·history revision인 경우에만 한 슬롯의 준비 결과를 공유한다. 입력이나 방향이 달라지면 다시 준비하고, 성공한 새 명령·Undo/Redo 뒤 슬롯을 비운다. 실패한 예산 검사나 no-op 때문에 Redo를 제거하지 않는다. 캐시는 명령별 전체 문서를 보관하는 이력 구조가 아니라 최대 한 건의 임시 준비 상태다.

명령 수와 추정 바이트 예산은 기존 200개/1 GiB를 유지한다. 전체 원본 이미지·프레임·GPU 리소스를 복제하거나 이력에 보관하지 않는다. 준비 문서는 기존 immutable 노드를 공유하고 필요한 변경만 만든다. 프로세스 전체 메모리와 임시 준비 메모리는 이력 추정 바이트와 별도로 측정한다.

### 붙여넣기와 클립보드

복사 시 불변 ROI 값과 집합 bounds를 함께 보관한다. `RoiClipboard.Capture`는 해당 값 배열·bounds·다음 붙여넣기 번호를 순회 없이 확보한다. 위치/축소 계산, 새 ID·순서 부여, 포함 관계 판정은 확보한 입력으로 작업 스레드에서 수행한다.

`PreparedEditorPaste`의 확정은 일반 편집의 owner/revision/epoch 검사에 더해 클립보드 배열의 동일성, 붙여넣기 번호와 다음 ROI 순서를 검사한다. 준비 중 새 복사나 다른 붙여넣기가 실행되면 옛 결과를 거부한다. 성공할 때에만 번호와 순서를 진행시키고 한 명령으로 기록한다. 준비 중 탐색한 viewport는 유지한다.

### 취소·no-op와 라이브 소스 교체

- 후보 순회·delta 적용·계층/목록 준비의 취소 지점과 UI 확정 직전에 `CancellationToken`을 검사한다. 취소·실패·stale 결과는 문서·선택·이력 cursor·Redo를 확정하지 않는다. 준비 중 사용자 pan/zoom은 되돌리지 않는다.
- 동일 ROI 맵이면 이력 후보 전체 순회를 건너뛴다. 후보 값이 같은 경우 `RoiChange`도 만들지 않는다. 이동량 0이나 실제 변경 없는 preview는 빈 편집으로 종료하고 preview 표시 종료를 알린다. 단순 선택은 이력에 넣지 않는다.
- 취소는 협력적이다. 개별 네이티브 호출·정렬·인덱스 구축처럼 취소 지점 사이의 작업이 즉시 중단된다고 보장하지 않는다. 늦은 결과가 UI에서 확정되는 것은 별도로 차단한다.
- 이미지/소스 교체는 새 source 준비와 이력 검증을 기존 라이브 종료보다 먼저 수행한다. 기존 라이브를 닫기 직전이 취소를 받아들이는 마지막 시점이다. `Live.CloseAsync`를 시작한 뒤 도착한 Esc만으로 준비된 새 source를 폐기하지 않고 교체를 완료한다. 그렇지 않으면 문서 교체는 취소되었는데 기존 라이브와 마지막 프레임만 사라지는 상태가 생긴다.
- history 유효성은 GPU source 전송 전과 실제 이력 확정에서 검사한다. 파일 개방 실패·취소 가능한 준비 구간의 취소는 기존 source와 이력 위치를 보존한다. 종료 이후의 late-cancel 정책을 모든 작업의 취소 무시로 확대하지 않는다.

### 불필요한 순회와 WPF 갱신 감소

`RoiSnapshot`은 변경 ID를 한 번 순회하여 목록 버전·공간 데이터·부모 관계 변경을 함께 판정한다. 이전/다음 ROI 맵과 다른 spatial seed가 있을 때의 값을 재사용한다. 공간 인덱스 재구축 기준을 넘으면 개별 변경 배열을 계속 키우지 않는다. 이전 Lazy 팩터리 체인을 보유하지 않고, 부모 관계가 같으면 자식 인덱스를 공유한다. 이름·필터·부모 메타데이터는 공간 조회에서도 최신 값을 사용한다.

완전한 하위 트리 삭제는 살아남은 ROI의 최소 포함 부모를 바꾸지 않는다. 해당 삭제 경로에서는 기존 부모 관계를 보존하고 불필요한 전체 재계층을 수행하지 않는다. 일부 형상 변경·새 ROI 추가·붙여넣기는 기존의 정확한 후보/포함 판정을 유지한다. 클립보드 bounds와 불변 선택의 명령 가능 여부도 같은 입력에서 반복 계산하지 않는다.

전체 ROI의 공통 이동도 포함 tolerance가 일정한 범위에서만 재계층을 생략한다. `RoiTranslationSelection.PreservesHierarchy`가 이동 전후 bounds의 모든 좌표 절댓값이 1,000,000 이하인지 검사하며, 그 밖의 큰 좌표는 동기·비동기 경로 모두 기존 정확한 재판정을 수행한다. 절대 좌표에 따라 tolerance가 달라지는 경우를 단순 평행 이동 불변성으로 덮지 않는다.

ROI 목록의 전체 값/정렬 인덱스와 표시 페이지를 분리한다. `RoiRows`의 메타데이터 갱신은 UI 소유이며 표시 페이지는 독립 배열이다. 작업 스레드에서 만든 목록은 완성 후 UI에 넘긴다. 렌더 스레드가 WPF 목록을 읽지 않는다.

표시 항목 수가 같으면 `RoiListSlot`과 실현된 WPF 컨테이너를 유지하고 이름·종류·들여쓰기 속성만 필요한 경우 알린다. 항목 수가 바뀌면 backing collection을 한 번 갱신하고 `Count`/`Item[]` 및 단일 `Reset`을 통지한다. 전체 갱신과 선택 복원 동안 바인딩 어댑터가 선택 이벤트의 역전파를 막는다. Ctrl 선택은 다른 페이지의 선택을 보존하고, 수정키 없는 단일 클릭은 화면 밖 선택도 해제한다. 목록 자동 페이지 이동은 실제 선택 변경에만 반응하여 pan/zoom이 수동 페이지 탐색을 되돌리지 않는다.

## 대안과 결과

최종 준비 작업과 UI 행 값 준비는 `EditPreparation`에서 실행한다. 단일 논리 코어의 UI/렌더 경합 측정 뒤 준비 callback 동안 worker priority를 `BelowNormal`로 제한했다. 공유 ThreadPool 스레드이므로 `finally`에서 원래 우선순위를 복원하며 async 작업을 이 범위 안에서 기다리지 않는다. UI·렌더 priority는 올리지 않는다. 작업 개수 제한과 취소 계약은 그대로이며, OS 스케줄링과 GC에 따른 긴 꼬리 지연까지 없어진다는 의미는 아니다.

UI에서 모든 변경을 동기 실행하면 소유권은 단순하지만 대량 순회의 입력 지연이 남는다. 매 입력마다 독립 작업을 만드는 방식은 자원과 결과 순서를 통제하기 어렵다. 작업 스레드가 가변 문서를 직접 수정하는 방식은 렌더·히트 테스트·Undo가 읽는 상태를 불안정하게 만든다. 따라서 단일 준비 작업과 불변 결과, 명시적인 검증/게시 경계를 선택했다.

새 범용 인터페이스나 병렬 history writer는 추가하지 않았다. `EditorSession`은 응용 명령과 게시, `EditHistory`는 기록과 cursor, 스냅샷은 파생 인덱스, `ImageCoordinator`는 source 수명, ViewModel은 작업 상태와 WPF 연결을 맡는다.

## 클린 코드와 패턴 검토

`Prepare`·`Validate`·`Commit`의 이름으로 부작용 경계를 구분한다. 일반 대량 편집 준비를 공통 경로로 모으고 history·clipboard 검증은 각 책임에 둔다. 원본을 바꾸는 예외 무시나 성공으로 위장한 취소는 사용하지 않는다. 새 외부 의존성·전역 가변 상태·GPU 복제는 없다.

Command/Memento는 원자적인 편집과 정확한 복원을 담당한다. immutable snapshot은 스레드 간 값 전달과 인덱스 공유를 담당한다. 기존 State 방식의 제스처는 입력을 관리하고, Observer는 성공 게시·preview 종료·목록 속성 변경을 전달한다. WPF 목록 어댑터와 source 어댑터는 도메인 외부 API를 격리한다. 패턴 수를 늘리기 위한 추상화는 추가하지 않았다.

| Creator | 세션은 준비 편집과 확정 상태를, 이력은 해당 cursor의 단계를, 목록 컨트롤은 자신의 슬롯을 생성한다. GPU 수명 소유자는 그대로다. |
| Controller | ViewModel은 명령·진행·취소를 연결하고 세션이 검증/이력을 관리한다. 포인터 콜백이 직접 도메인 값을 수정하지 않는다. |
| Low Coupling | worker→UI는 불변 값과 revision, source→문서는 명시적 validate/commit 경계로 연결된다. |
| High Cohesion | 준비/확정과 이력/클립보드/목록 소유권별로 코드를 모으고 WPF 선택 규칙을 Core에 넣지 않는다. |
| Polymorphism | 기존 영상 loader/viewport 계약과 제스처 계약을 유지한다. 새 변형 요구가 없는 준비 데이터에 불필요한 상속 계층을 만들지 않는다. |
| Pure Fabrication | `EditHistory`, 준비 결과, `RoiRows`/목록 바인딩은 복원·스레드 전달·WPF 비용을 도메인 형상에서 분리한다. |
| Indirection | 불변 준비 결과가 worker와 UI 게시 사이를, `ImageCoordinator`가 source 전송과 문서 이력 사이를 중개한다. |
| Protected Variations | WPF 선택 비용이나 스레드 스케줄링 변화가 ROI의 형상·포함·ID·Undo 규칙을 바꾸지 않도록 경계를 둔다. |

설계 원칙 예외는 없다. 이력 예산을 줄이거나 정확한 ROI·선택·계층을 생략하여 성능을 맞추지 않는다.

## 검증과 한계

회귀 검증은 준비 결과의 중복 사용, 방향·source·history revision 변경, 동일 이미지의 값이 같은 상태, owner 불일치, 취소, 준비 중 pan/zoom, preview 변경, clipboard 변경, 예산 실패와 Redo 보존을 포함한다. 부모 연쇄 삭제/Undo/Redo와 혼합 메타데이터/형상/부모 변경의 인덱스 일치를 유지한다. UI에서는 페이지를 넘긴 다중 선택, 일반 클릭의 화면 밖 선택 해제, 슬롯 재사용과 단일 Reset, source 전송 전 실패 및 라이브 종료 이후 late-cancel 경계를 확인한다. 실행 결과와 수치는 [성능·검증 기록](../low-spec-performance.md)을 따른다.

전체 값의 생성·삭제·복원·선택과 목록 구축에는 여전히 적어도 O(N)의 원천 연산량이 남는다. 정렬·영속 맵 변경·계층 후보 밀도에 따라 O(N log N) 이상이 될 수 있다. 비동기 준비는 이 비용을 없애지 않으며 모든 작업이 일정 시간에 끝난다고 보장하지 않는다. 일반 복사, 일부 동기 명령, 회전/resize preview 등의 비용도 별도로 남는다.

기준 장비의 CPU 사용 가능 수를 제한한 시험은 CPU 여유가 작은 조건의 대용 지표다. 실제 저사양 CPU의 캐시/메모리 특성이나 저사양 GPU의 성능을 재현했다고 주장하지 않는다. 실제 저사양 GPU·현장 PCB 분포에서의 성능은 미검증이며, 기존 최소 8K/24K 요구나 검증 기준을 낮추지 않는다.
