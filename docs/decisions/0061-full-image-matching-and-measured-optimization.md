# ADR-061 — 세 방식의 8K 전체 검색과 측정 기반 개선

상태: 사용자 승인 범위에서 구현·로컬 검증. CPU125ms/CUDA80ms 달성과 구별한다.

## 배경

사용자는 정확도와 검색 조건을 보존한 속도 개선, 실제8K 전체 검색, 방식별 파라미터를 요청했다. 기존2Mpx 거부와8K 안의512×512 검사만으로는 전체 검색 요구를 충족하지 못했다. 이 요청은 ADR-055/059의 검색 크기 제한을 대체한다. 기존 PoseMatch와 논문 형상 경로는 변경하지 않는다.

## 결정

1. 공통 검색과 선택형 CUDA는 최대67,108,864픽셀을 처리한다. WPF에서 선택 영역 검색을 끄면 원본 전체를 읽는다. 중간 읽기 버퍼만2Mpx씩 나누며 해상도나 검색 영역을 자동 축소하지 않는다. 이미지 피라미드는 기존 설정/생성 조건을 사용한다.
2. 전체 최상위 후보 점수와 전역 후보 예산은 유지한다. 2Mpx보다 큰 중간/원본 단계의 특징 맵만 후보 주변에서 지연 준비한다. 템플릿 최대 반경+거리 전파32px+미분 여백을 보존하고, 원본 경계 자세 보정도 같은 후보 주변에서 수행한다. 검사/레벨별 캐시는 최대32개 및 추정512MiB를 기준으로 제한한다. 실행 중 참조·원본·최상위 맵·GPU 버퍼는 별도이며 프로세스 전체 메모리 상한이 아니다.
3. 독립 방향 맵/후보 보정/스칼라 응답 행은 최대4작업으로 계산한다. 원래 후보 번호에 결과를 저장하고 중복 제거/사용자 중심 판정은 순차 실행한다. 행 임시 버퍼를 갖는 SIMD scorer는 병렬 호출하지 않는다. 방향 간 최소값은 같은 float 연산의 SIMD로 구한다.
4. Sub-NCC의 새8K 재현에서4/8누락을 발견했다. 축소 원판의 밝기 무늬가 위치 위상에 따라 다른 봉우리를 선택하는 것이 원인이었다. 가장 작은 영상으로 자세를 다시 이동시키지 않고, 다음 큰 영상의 **전체 내부 픽셀**로 후보 주변을 보정한다. 첫 보정 반경은6픽셀이며 이후 기존 보정을 따른다. 전역 후보 수·중복 억제 조건·최종 점수0.75를 그대로 유지한다. 정확도 수정이므로 Sub-NCC의 이전 평가 횟수/미세 자세가 완전히 동일하다고 주장하지 않는다.
5. Line2D의 축소/원본 특징 수, Sub-NCC의 축소 표본 수/학습 명암차, Chamfer의 특징 수/거리 단위/방향 비용은 각 프로젝트의 불변 옵션이다. 기본값은 기존 상수다. 앱은 선택한 방식의 설정만 표시하고 변경 후 재학습 전 검사를 막는다. 숫자 오류를 이전 값으로 실행하지 않는다. 세션 설정이며 영구 레시피 저장 기능을 추가하지 않는다.
6. `AsyncCommand`는 같은 생성 스레드에서 시작할 때 소유 SynchronizationContext를 사용하고 호출자의 문맥은 즉시 복원한다. WPF 타입 의존성은 추가하지 않는다. 검사 도중 낮은 우선순위의 호출 문맥이 완료 처리까지 전파되는 문제를 재현 테스트로 확인했다.
7. 로그는 읽기/준비/후보/보정/원본 검증/게시/명령 완료/표시를 나눈다. 성능 시험은 실제 WPF 버튼 Automation Invoke로 실행한다. 첫 호출과 반복, 제한 영역과 전체8K, 알고리즘 시간과 UI 포함 시간을 구별한다.

## 검증과 한계

[실측·재현법](../cpu-matching-performance.md)에 입력/조건, 회귀 결과, 속도와 메모리를 기록한다. 전체 검색 데이터는 네 모서리·중앙·4096좌표 양쪽의 알려진 Kensa 변환8개다. 기존 Kensa 제한 영역 및 합성 조건을 함께 비교한다. 합성8K 성공을 실제 생산 이미지 전수 검출률로 표현하지 않는다. 출력/후보 상한 초과·취소는 여전히 불완전 경고다.

전체 구조/외부 의존성 변경, 점수/후보 축소, 커밋/푸시는 없다. 다른 작업의 이미지 로딩/이상 감지 변경은 보존한다.
