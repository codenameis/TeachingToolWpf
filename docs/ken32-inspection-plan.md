# ken32 정확도 우선 검사 계획

2026-10-16 사용자 결정: 검출 정확도를 먼저 확보하고, 검사 운영 방식에서 속도를 줄이는 방법을 찾는다. 이후 주 벤치마크 입력은 로컬 `ken32.png`다. 기존 Kensa/합성 8K는 회귀 시험으로 보존한다. 이 문서는 확인된 입력과 다음 검증 계획이며, ken32 검출 완료나 새 운영 경로 구현 보고가 아니다. 로컬 수정·검증만 수행한다.

## 입력과 현재 한계

| 항목 | 확인 결과 |
|---|---|
| 원본 | 저장소 루트의 `ken32.png`, 로컬에만 보존 |
| PNG IHDR 직접 확인 | 17,280 × 30,720 = 530,841,600픽셀 |
| 파일 크기 | 169,119,065바이트 |
| SHA-256 직접 확인 | `3E482155A9A0C86F5E85821B62D8CD2CBF704B89747C4FCCADF40C0EE21C156A` |
| 단일 검색 한도 | `PyramidSearch.MaximumSearchPixels`: 67,108,864픽셀 |
| 연속 Gray8 입력 한도 | `GrayImage`: 80,000,000픽셀, 생성 시 복사 |
| ken32 전체 매칭·정답 라벨·버튼→표시 | NOT_RUN |

원본은 약 5.31억 픽셀로 기존 8,192² 합성 입력의 약 7.91배다. 한도 상수만 높이거나 축소 영상을 대신 검사한 뒤 원본 전체 검색이라고 기록하지 않는다. 기존 원본 영역 읽기 기능으로 메모리를 제한하면서 전체를 덮는 분할 입력을 먼저 검증해야 한다. 분할 경계에서 회전된 대상이 잘리지 않도록 여백과 전역 좌표 병합이 필요하다.

[이전 파일 로딩 기록](first-image-load.md)의 PNG 디코딩 약 5초·앱 캐시 준비 약 6.83초는 과거 측정이다. 이번에 다시 측정한 값이 아니며 검사 속도가 아니다. 최초 파일 열기, 준비된 이미지의 검사 명령→표시, 실제 카메라 연속 처리량은 별도로 기록한다. 기존 CPU 125ms/CUDA 80ms 미달을 유지하고, 다른 장비의 0.5초를 ken32 전체 검사에서 달성했다고 해석하지 않는다.

## Matrox와 MLCC 장비에 대한 확인 및 추정

공식 제품 설명에서 Pattern Matching은 정규화 명암 상관(NGC)과 계층 검색을 사용한다. Geometric Model Finder는 윤곽 같은 기하 특징으로 위치·회전·배율을 찾는다. 따라서 현장에서 부르는 “Matrox 패턴”만으로 어느 방식인지 결정할 수 없다. [Zebra 공식 기술 사양](https://www.zebra.com/content/dam/zebra_dam/en/tech-specs/imaging-library-tech-specs-en-us.pdf), [MIL 공식 도움말의 두 모듈](https://aurorahelp.zebra.com/aurorail/MILXSP4/MILXSP4HelpFiles/helpcontents.html).

MIL은 기준 위치에 맞춰 상대 좌표계와 검사 ROI를 이동하는 fixturing 절차를 제공한다. [공식 fixturing 절차](https://github.com/Zebra-Aurora-Imaging-Library/DOC_PUBLIC_AIL11_MD/blob/main/UserGuide/C29_Fixturing/S02_Steps_for_fixturing.md). 다중 버퍼 수집과 프레임별 처리 콜백을 사용하는 C# 예제도 제공한다. 이 예제는 평균 처리 시간이 수집 시간보다 길면 프레임을 놓칠 수 있다고 명시한다. [공식 MdigProcess 예제](https://aurorahelp.zebra.com/aurorail/MILXSP4/MILXSP4HelpFiles/extfile/zz_MIL_Examples_mdigprocess.cs.136/zz_MIL_Examples_mdigprocess.cs.136.htm).

사용자가 언급한 MLCC 장비에 대한 다음 설명은 **추정**이다. 해당 장비 코드·검사 영역·픽셀 수·불량 종류·시간 측정 구간을 확인하지 않았다.

1. 조명과 이송 피치를 안정화하고 부품이 올 레인·구간을 알고 있다.
2. 기준 마크/대표 부품의 패턴 또는 윤곽으로 위치를 보정한다.
3. 각 예상 위치에서 이진화·연결 영역·윤곽을 구하고 유무, 위치, 기울기, 폭/길이와 외형 이상을 확인한다. 명암 무늬가 필요한 검사는 별도 국소 패턴 검증을 사용할 수 있다.
4. 라인스캔 입력의 도착 구간부터 처리하고, 다음 구간 수집과 이전 구간 검사를 겹친다. 이는 처리량을 높일 수 있지만 한 검사의 지연 시간을 자동으로 줄여 주지는 않는다.

단순 외형의 윤곽 측정과 모든 위치·각도에서 템플릿을 찾는 작업은 계산량과 검사 목적이 다르다. 0.5초가 부품 하나, 스트립 하나, 전체 완성 영상 중 무엇인지, 수집·화면 표시를 포함하는지 확인 전에는 직접 비교하지 않는다. 대칭 외형만 있는 부품은 0°와 180°를 구분할 근거가 없을 수 있으므로 비대칭 특징 또는 동등 각도 정의가 필요하다.

## 구현·검증 순서

1. **정답부터 마련한다.** ken32에서 검사할 템플릿과 대상 종류를 고정하고 정답 위치·각도·정답의 허용 오차를 기록한다. 중앙/가장자리/분할 경계, 유사 부품, 배경, 저대비·부분 가림을 포함한다. 원본에 불량 사례가 없다면 별도 변형 시험으로 표시하고 현장 불량 검증으로 표현하지 않는다. 전체 라벨이 없는 상태에서 전수 검출이라고 주장하지 않는다.
2. **원본 전체를 읽는 기준 경로를 만든다.** 기존 원본 영역 읽기와 겹침 분할을 이용한다. 원본 해상도, 전역 검색 범위, 점수, 각도·배율, 초과 후보 검사와 결과 상한 검증을 유지한다. 전체 픽셀 범위의 누락, 경계 누락, 중복, 원본 좌표 환산을 검사한다. 8/16등분 자체를 성능 해법으로 가정하지 않는다.
3. **운영용 경로는 별도로 비교한다.** 기준 위치 검출 → ROI 좌표 보정 → 각 부품의 국소 정밀 검사로 구성한다. 이 단계는 전체 검색과 검색 영역이 다르므로 동일 조건 최적화라고 부르지 않는다. 레시피의 전체 검사 위치를 방문하고 유무·위치·각도를 실제 픽셀로 검증한다. 같은 모듈이라는 이유로 검사 결과를 복제하지 않는다.
4. **보정 오차를 검사한다.** 넓은 영상에서 여러 기준점의 잔차를 확인한다. 라인스캔 늘어짐·국소 변형을 단일 평행 이동/회전으로 설명할 수 있는지 먼저 확인한다. 국소 ROI 여백은 측정된 오차를 포함해야 하며 보정 실패·대응 모호함은 명시적으로 재검색/재검 대상으로 처리한다. 예상 개수를 채웠다는 이유로 누락이나 추가 부품 검사를 생략하지 않는다.
5. **그다음 운영 비용을 줄인다.** 전체 원본 회전 복사 대신 검사 좌표를 변환하고, 필요한 영역만 읽으며, 고정 템플릿 준비와 작업 버퍼를 재사용한다. 정확한 결과와 읽기 범위 검증 후 병렬도를 측정한다. 실제 카메라 수집·라인 조립은 현재 범위 밖이며, 이 문서가 해당 기능 구현을 승인한 것은 아니다.
6. **시간을 끝까지 잰다.** 보정, 영역 읽기/변환, 매칭/윤곽 검사, 병합, UI 게시·표시를 나누되 실제 검사 명령→표시를 총시간으로 기록한다. CPU/CUDA, 첫 실행/반복 실행, 중앙값/상위 지연, 피크 메모리와 처리 대상 수를 함께 보고한다. 스트리밍 처리량과 개별 검사 지연을 구분한다.

원본 전체 매칭은 정확도 기준으로 보존한다. 운영용 ROI 검사는 따로 이름과 검색 조건을 기록하여, 작업량을 바꾼 개선과 같은 조건의 알고리즘 개선을 혼동하지 않는다. 기존 PoseMatch 전체 탐색 경로는 변경하지 않는다.
