# 전체 후보 검사와 위치 정확도 수정

2026-10-16. [ADR-063](decisions/0063-exhaustive-candidates-and-fine-pose-ranking.md). 로컬 수정·검증했으며 추가 커밋·푸시하지 않았다. 검증 데이터의 위치 오류·후보 잘림은 수정했지만 **CPU125ms/CUDA80ms는 여전히 미달**이다.

## 실패와 수정

Sub-NCC는 원본8K의256핀 중48개에서1px를 넘는 위치 오류가 있었다. 작은 원판 표본이 긴 핀과 사선 배경의 일부를 비교해 잘못된 위치에 더 높은 점수를 줬고, 원본 전체 템플릿 검사 전에 올바른 후보를 억제했다. 원본에서 추출한 두256×256 회귀는 수정 전29.822/30.072px 오류로 실패했다.

이제 원본 검증이 끝날 때까지 서로 다른 위치 가설을 보존한다. 중간에서는 정확히 같은 자세만 합치고, 원본 점수로 최종 중복 제거를 수행한다. 기존 최소 점수0.75·각도-30~30°/10°·배율1·피라미드3·출력256·검색 영역은 같다.

후보2048개를 초과하면 버리던 큐는2048개씩 검사하는 묶음 처리로 바꿨다. 이 값은 세 CPU 방식에서 작업 묶음의 크기이며 전체 후보 제한이 아니다. 실제 후보 수와 묶음 수를 로그와 상태에 표시하고 취소/오류를 정상 완료로 바꾸지 않는다. 다른 매칭 방식의 예산 의미는 유지한다.

기존 제한 영역 회귀에서는 Chamfer의 CPU/CUDA 최종4개 자세는 같지만 후보603/607개·평가267960/269140회가 달랐다. 방향 보간의 GPU 중간 반올림 차이가 동점 봉우리를 바꾼 것이다. 기존1e-7 허용 오차 테스트를 정확한 동등성 검사로 강화하자2.21e-8 차이로 실패했다. float 곱셈 뒤 반올림과 double 곱셈 호출 경계를 명시해 CPU의 중간 반올림을 보존했다. CUDA가 명시적 반올림 없는 곱셈/덧셈을 결합할 수 있다는 [NVIDIA PTX 산술 규칙](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#floating-point-instructions-mul)과 실제 추출 PTX를 확인했다. 점수 문턱이나 동점 판정의 허용 오차를 추가하지 않았다.

## 입력과 독립 기준

- Kensa: 원본1024×1536, 학습 ROI중심200.5/184·89×52, 메모리 패키지48개. 수동으로 식별한48개 주변에서 별도 OpenCV ECC Euclidean 정합으로 기준 자세를 작성했다. 검색에는 이 좌표를 전달하지 않는다. **독립 영상 정합과의 일치이며 물리 교정 정답이나 생산 검출률 보장은 아니다.**
- 기본8K:8192×8192,16모듈·256핀. 기존 생성기 정의와 학습 ROI의 상대 위치가 정답이다. 검색은 원본 전체이며 정답 좌표로 탐색을 제한하지 않는다.
- 기존 희소8K: 전체8192×8192에 알려진 회전/이동 패키지8개. 밀집 반복 모듈과 별도로 검증한다.
- 자동 회귀: 제한 영역·음성·회전·배율·위상29조건, CPU/CUDA 비교. 원본18V의6실행은 전수 라벨이 없는 알려진 대상 검사로 구별한다.

새 재현 데이터는 `samples/CpuMatching.Modules`에 있다. `cases.json`은 라이브러리 픽셀 인덱스 좌표, `kensa-reference.json`은 WPF 픽셀 중심 좌표다. 두 좌표의 차이는0.5px다. 원본 SHA256과 기준 생성 설정은 `reference-provenance.json`에 기록했다.

## 측정 및 검증

정확도 수정 후 전체 후보를 검사하는 실행을 성능 최적화 기준으로 사용한다. 과거 후보를 버리던 실행이 더 빨랐다는 사실을 숨기지 않는다. 입력/옵션·검출 결과의 모든 숫자·평가 횟수·후보/묶음 수의 전후 동일성을 별도로 비교한다.

Ryzen5 5600H/32GB/RTX3060Laptop6GB, Windows x64, .NET10 Release. WPF에서는 조건별 첫 실행을 포함한3회를 순차 측정한다. 검사 버튼 Automation Invoke→원본 읽기→검색→결과 게시→DX12 Present/fence와 WPF Rendering까지 포함한다. 학습·앱 시작과 물리 입력 대기/모니터 scan-out은 제외한다. 첫 CUDA 장치 준비는 검사에 포함한다. 측정 중 빌드/테스트를 병행하지 않았다. 3회 중앙값과 최댓값을 기록하며 작은 차이는 열·스케줄링 변동과 구별하기 어렵다.

### 전체 검출·자세

Kensa/기본8K의3방식×2장치×3회 = **36회 모두** 검출 수·위치≤1px·각도≤1°·배율 오차≤0.03·잘림 없음·표시 완료를 통과했다. CPU/CUDA18쌍과 반복 결과는 모든 숫자가 정확히 같다. 최적화 전 정확도 수정 버전36회와 입력 옵션·검출 결과·평가 횟수·후보/묶음 수도 정확히 같다.

36회 자료는 변경 없는 Line2D/NCC24회와 CUDA 보간 수정 후 다시 실행한 Chamfer12회를 합쳤으며 원시 파일 출처를 JSON에 기록했다. 엄격한 CUDA 보간 후 Chamfer8K 후보 단계는 약1094→1785ms로 늘었다. 전체 시간은 실행 변동을 포함해25806→24239ms였으므로 보간 수정 자체를 속도 개선으로 주장하지 않는다. 후보 동등성을 위해 유지했다.

자동 테스트는 **CPU19 + CUDA66 + WPF/검사299 =384개 PASS**, Release 빌드 경고0/오류0다. 수정 전 실패한 원본 핀3종, 후보 묶음의 약한 유효 대상 보존, 취소, 캐시의 동일/상이 픽셀, CUDA 방향 점수의 정확한 동등성을 포함한다. 기존29조건×3방식×2장치174건은 입력 SHA256·옵션이 이전과 같고 CPU/CUDA87쌍의 결과·평가 횟수·후보/묶음 수가 정확히 같다. 완전 정답168건 PASS, 원본18V6건은 알려진 대상만 확인했다. 비교용 OpenCV 실패는 세 방식의 실패로 세지 않으며 원시 결과에 보존한다.

변경 C# 파일의 공백·스타일·명명 검사는 PASS다. `scripts/Format-Code.ps1 -Verify` 전체 검사는 작업 범위 밖 기존54파일의 줄바꿈 등 형식 오류로 FAIL이며 관련 없는 파일을 일괄 수정하지 않았다.

원시 결과·실패 재현·전후 비교 스크립트·소스/입력 해시는 [검증 ZIP](data/cpu-full-search-accuracy-validation.zip)에 있다. 전체 입력과 기준 파일은 [재현 데이터 안내](../samples/CpuMatching.Modules/README.md)를 따른다. 실제 촬영8K·다른 장비·장시간·노이즈/조명 조건 전체에 대한 성능 보장은 NOT_RUN이다.

## 측정으로 남긴 최적화

- **자세 캐시 교체:** 처음 채운 몇 각도만 계속 보관하던 캐시를 같은 용량의 FIFO로 바꿨다.2K Sub-NCC 분리 시험의 첫 실행2350→1694ms, 동일 결과/평가 횟수를 확인했다.
- **서로 다른 맵을 기준으로 용량 계산:** 같은 픽셀 맵을 가리키는 많은 위치 별칭 때문에 다른 유효 맵이 퇴출되던 문제를 수정했다. 자동 회귀에서 불필요한 맵 준비3→2회를 확인했다.8K Chamfer 분리 시험121.1→50.0초였다.
- **가까운 후보를 연달아 계산:** 병렬 작업은256px 구역 순서로 실행하고 출력은 원래 후보 번호에 저장한다.8K Chamfer 분리 시험50.0→27.2초였다. 결과/평가 횟수/4937후보·3묶음은 정확히 같았다.
- **제거한 실험:** 작은 영상의 경계 보정기를 묶음 사이에서 공유한 실험은 Kensa Line2D 첫 실행에서4~6% 차이만 관측돼 변동과 효과를 구분하기 어려웠다. 원복했다.

분리 시험 수치는 각1회이며 UI를 포함하지 않는다. 최종 성능 판단에는 위의3회 WPF 결과를 사용한다. 캐시 용량·병렬 작업 수·표본·점수·보정 범위는 늘리거나 줄이지 않았다. 동일 타일 공유는 Line2D/Chamfer에만 적용하며 모든 픽셀이 같을 때만 허용한다. 실제 촬영 모듈의 노이즈나 결함이 있으면 해당 맵을 새로 준비한다.
